# The Zombies Site

The site in `zombies/site/`, for `zombies.enbraile.vip`, where the group starts attempts on a map and talks to the coach, Cari. It lists the maps Claude has published, and members start or join an attempt on one and talk in its shared chat, where Cari answers with the prepared hints, with a zone on the map under those that give a place ([Zones](#zones)), and follows their progress, holds when no prepared line fits, and takes the group's revisions and ratings for Claude, who can watch an attempt from Claude Code while it is played, close its gaps, read code's audit of every reply and step in as Cari; a member in a Discord voice channel can bring Cari into the call and ask her by voice ([Voice](#voice)); what is still to come is in [Zombies Coach](../../../work-in-progress/zombies-coach/discovery.md). Its look is in the [Site Design System](../reference/design-system.md).

Players see an **attempt**: one go at a map's easter egg, in English and Spanish "attempt" and "intento", at `/attempts/<id>`. The code, the tables, the API routes and the terminal's commands call it a **run**, and so does this doc wherever it describes them ([Decisions](#decisions)).

## How It Is Built

It mirrors the [DJ panel](../../../dj/panel/explanation/panel.md): a Vite + React page, and one Hono function holding every route in `api/_lib/app.ts`, bundled into one file at build ([Hosting](#hosting)). A signed-out reader is sent to the [root site](../../../home/site/explanation/site.md) and back: the function reads the session from the root's `/api/me` with the reader's cookie, so the site keeps no sign-in tables of its own. It asks once per request, and the reply that opens a page, `/api/maps`, `/api/maps/<game>/<map>` or `/api/runs/<id>`, carries the reader as `viewer`, so a page load asks the root once and the site has no `/api/me` of its own. Locally, `DEV_USER_ID` stands in for a session: it holds a comma-separated list of members, each `<id>` or `<id>:<name>`, and `GET /api/dev/sign-in/<id>` sets a cookie that makes that browser one of them (the first one otherwise), so one machine can be two members of one attempt. The route answers 404 wherever `DEV_USER_ID` is unset, as it is on every Vercel deployment. The chrome is in English or Spanish, following the reader's `lang` cookie as the other sites do.

Maps live in their own Postgres database, never pkmn's, through Drizzle with `pg` as in [the pkmn site](../../../pkmn/site/explanation/site.md); the migrations in `drizzle/` run in the Vercel build. Its tables:

| Table | Holds |
|-------|-------|
| `maps` | One row per published map, keyed by game and map slug, with its latest version |
| `bundle_versions` | Every published bundle, numbered per map, with the SHA-256 of its canonical JSON and who published it, always `claude` |
| `map_images` | Each map image published, announcement or survey, keyed by the SHA-256 of its bytes, with its type and the bytes |
| `runs` | One row per run: its map, the language Cari speaks, who started it, when Cari last asked the round, and the lease that lets one of Cari's replies run at a time |
| `run_history` | A run's earlier history, imported from the terminal session it continues: each line the players typed there or the coach answered, in order, with when it was said |
| `call_lines` | Each line said in the run's Discord call while Cari was in it, from the bot's transcripts: the speaker's Discord ID and server name, the text, when speech started and the clip's length; never read by the coach model |
| `run_members` | Each time a person joined a run, with when they left it; a unique index over the rows not left keeps a person in one run at a time |
| `messages` | The run's chat, each line from a member or from Cari, its `kind`: `chat`, a member's `revision`, or Cari's `ack` of one, and `posted_by`, `claude` on a line Claude posted as Cari |
| `run_knowledge` | The knowledge entries known in a run; an entry without a row is unknown |
| `hint_cards` | A hint card: the ladder it belongs to (a step, or one of its parts) and the Cari line it hangs under |
| `deliveries` | Every rung given, in order: its card, ladder, rung, Alt, level, the wording as delivered, its `mentions` and `reveals`, the bundle version and who asked |
| `run_steps` | A run's progress, never shown to players: each step or part the players started or finished, and when Cari told them a blocked step was not possible yet |
| `heads_ups_given` | Each heads-up Cari gave in a run, so none is given twice |
| `gaps` | Each time Cari held: the line asked, what the model said it was about, the holding line said, the bundle version, and the run's marks, open ladders, done steps and last lines at that moment; then the last version Cari was offered it again on, and when a later version's rung answered it and which delivery that was |
| `feedback` | Each revision (its text, its message and the Cari line it refers to, with that line's card and newest rung) and each member's rating of a card (`obvious`, `right` or `vague`, one per member per card, the newest rung it was given on) |
| `coach_calls` | Every Claude call: model, tokens, latency, stop reason, refusal and its category, the rules code caught the model breaking, and any error |
| `audits` | Each reply of Cari's in which code found a rule broken: the Cari line it became (none when nothing was posted) and the findings |

## Map Bundles

A bundle is everything the live coach will need about one map, as one JSON document checked by the zod schema in `shared/bundle.ts`: the map's name in each language, which drawn plan stands for it, its announcement image if it has one (the file name, the SHA-256 of its bytes, its type and its size in pixels), its survey image if it has one (a community overhead map of the whole level, the same facts), the zones on its rungs, the knowledge entries with their `known` or `unknown` marks, the steps (`requires`, conditions, `optional`, the `onSuccess` line, the ladder, part ladders and heads-ups), the map's own calibration notes, and the dossier and sources as the durable copy. Every rung, each of its Alts (with `when` it replaces the rung) and every `onSuccess` line carries its wording in Spanish and English, the knowledge entries it `mentions`, which must already be known, and those it `reveals`; a heads-up carries its `mentions` only. The schema rejects a `mentions`, `reveals` or `requires` that names nothing, repeated IDs, and a bundle with no step that is not `optional`. A zone is an ellipse on the survey image, `{ x, y, rx, ry }`, its centre and radii as fractions of the image's width and height; a rung or Alt carries one only when it gives a place, and the schema rejects a zone on a level 1 or 2 rung or on an Alt for one ([Zones](#zones)).

A real map's bundle is not written by hand: `npm run compile -- <dir>` builds it from the files the ee-coach skill prepares in that map's dir ([Research and dossier building → Compile and publish](../../../../.claude/skills/ee-coach/references/research.md#4-compile-and-publish)) and writes `<dir>/bundle.json`. It reads `map.json` (the names, the art plan, and the file names of the announcement image and the survey image), each image it names, rejecting one that is missing, over 4 MB or not a JPEG, PNG or WebP file, `hints.md` and `hints.es.md` paired line by line, the `L4 as spoken` and `Conditions` of each step in `dossier.md` (each indented `- ` item one condition, an indented line without one joined to the item above), `knowledge.md`, the map's `calibration.md` every file under `sources/` and `zones.json`, which maps a rung's address as compile's messages name it (`step 5 L3`, `step 5 part 1 L3`, `step 5 Alt 2`) to its zone, and checks what the schema cannot: that each zone names a rung that exists, of level 3 or 4, and that a map with zones names a survey image, that both languages hold the same lines with the same IDs, that a line reveals only what it mentions, and that no card text carries a step, hint or level number. Its messages name a file and line or a step and rung, never the text, and its summary is counts only, so its output can be quoted where the players read.

`npm run publish -- <dir>` reads `<dir>/bundle.json` and checks it. When the bundle has an announcement or survey image, it checks that each file in the dir still has the bundle's digest and uploads it first, to `PUT /api/claude/images/<sha-256>`, which stores it unless one with that digest is stored already; the bundle route answers `missingImage` to a bundle whose announcement or survey image is not stored. It then sends the bundle to `PUT /api/claude/maps/<game>/<map>` with `CLAUDE_TOKEN`. The function stores it as a new version, published by `claude`, unless its digest equals the latest one's, so publishing the same bundle twice leaves one version; an older bundle published again becomes the newest version, which is how a map is reverted. Real maps' bundles stay in the gitignored `zombies/maps/<game>/<map>/` ([Repository Layout](../../../general/explanation/repository-layout.md#decisions)); the one committed bundle is the made-up test map in `zombies/site/test-map/`, Harrow Station.

`/api/claude/` is the site's machine API, and it is Claude's: only Claude Code calls it, from the terminal, and every route under it answers 403 to any request without `CLAUDE_TOKEN` as its bearer token, whatever cookie it carries. What it writes is recorded as Claude's, as `published_by` is on a bundle version; the watch stream and the step-in below are under it too, and a line Claude posts as Cari carries `posted_by` `claude`.

`GET /api/claude/runs` lists every run with its map, language, starter, members, when it started and last spoke, and its counts of history lines, lines, call lines, rungs, gaps and feedback. `GET /api/claude/runs/<id>` returns the whole run for a debrief: the run, every membership, its imported history, every line with its `kind`, every line said in the call (`call`), the cards and every rung delivered, the feedback, the gaps, the marks known (with their names and when) and those still unknown, the progress in `run_steps`, the heads-ups given and every Claude call. `POST /api/claude/runs` imports a run coached from the terminal: the map, the language, the members with their Discord IDs (the first is the starter), the knowledge entries known, every rung given in order (its step or part, rung and Alt, and who asked), each step or part started, done or told blocked, and the heads-ups said. It checks every handle and rung against the latest bundle, that no Discord ID is listed twice and that each ladder's rungs come in order, and answers with the issues, by ID and position only, if any fails; otherwise it creates the run with each member moved into it, one card per ladder under a fixed Cari line ("De la sesión anterior." or "From the last session.") holding that ladder's rungs in the bundle's wording for the run's language, the marks (the bundle's baseline, the entries listed, and what every rung given mentions and reveals), the progress, with every step a done step `requires` done too as `record_progress` does, and the heads-ups, all at the moment of the import. `POST /api/claude/runs/<id>/history` adds to an existing run the conversation the terminal session had, as its earlier history: each line `member` or `cari`, its text and when it was said, in order and every one earlier than the run, which it checks and answers with the issues by position only; it refuses a run that already has a history, so it is sent once. The run page shows that history above the run's own lines, the coach's replies as Cari's and the players' under the name "Terminal". `npm run import -- <dir> <name>=<discord id> ...` sends the dir's gitignored `import.json`, with each member's Discord ID, which a subagent writes from the map's `session.md` and `knowledge.md`, and prints the run's ID and counts; `npm run import -- <dir> --history <run id>` sends the dir's gitignored `history.json`, which a subagent writes from Claude Code's transcripts of the terminal session, and prints the counts of lines. `npm run runs` prints the list, with no hint text in it; `npm run runs -- <id>` writes the whole run, its audits included, to the gitignored `zombies/maps/<game>/<map>/runs/<id>.json` and prints only its counts, since the log holds rungs and the gaps name what the players asked.

`GET /api/claude/runs/<id>/events?after=<cursor>` is the watch stream: the run's map and every event since the cursor, oldest first, each with its kind, its row's ID, its time and its details, and the cursor to ask from next. The kinds are a member's line (`line`) and Cari's (`cari`, with the cards under it), a line said in the call (`call`, with the speaker's name, Discord ID and text, timed when the site stored it), each rung given (`hint`: card, ladder, rung, Alt, level, wording, version), a revision, a card rating (sent again when a member changes it), a gap held and a gap answered, a member joining or leaving, a step or part started, done or told blocked (`progress`), a reply's audit findings (`audit`, with the Cari line it became), and a new bundle version of the run's map (`published`); a Cari line Claude posted says `by` `claude`. The cursor is the last event's time in microseconds, and the route leaves out the last second, so a row whose transaction began a moment before it committed is not skipped. `npm run watch -- <id>` follows it every 2 seconds for `Monitor`: it writes every event, the earlier ones first, to the gitignored `zombies/maps/<game>/<map>/runs/<id>.events.jsonl` and prints one line per new event with its time, kind, member name, card or gap ID, version or rating, and never any text from the chat or the bundle, such as `21:19:13 gap 1 held`, `21:19:30 call Marina`, `21:19:42 cari with card 2`, `21:20:05 cari (claude) with card 3` or `21:20:30 audit on cari line 12: number-shown`, so the terminal the players may read shows no hint and no question.

`POST /api/claude/runs/<id>/say` is Claude's step-in: a line posted in the run as Cari, for when the model is lost. It takes `text`, an optional `hint` (a ladder by its bundle `step` and `part`, an `alt` index, and `answer` for a level 4 rung) and an optional `gap` that the hint answers, and needs text or a hint. It waits for the run's lease, as a reply does, and holds to the same rules as the model: the hint is the ladder's next rung, given only when its step is ready and not done, never on an optional step the players have not started, level 4 only with `answer`, and only when its `mentions` are known; the text may name nothing unknown except what that rung mentions or reveals, and no step or hint number, nor brackets. A refusal answers with its code alone (`namesUnknown`, `numberShown`, `notReady`, `optional`, `answerUnasked`, `unknownMention`, `noSuchGap`, `gapWithoutHint`, `busy` and the like); otherwise the rung goes on a new card, the marks learn what it mentions and reveals, and the line, stored with `posted_by` `claude`, reaches every member's next poll and the model's later turns like any of Cari's. `npm run say -- <id> <file>` sends a step-in written to a JSON file, so its text never appears on a command line, and prints only the line's and card's IDs or the refusal.

The maps page reads `GET /api/maps`, which returns each map's game and map IDs, its names, its `art` plan key, its image's digest and size in pixels (or none), test flag and version and nothing else from the bundle, so no solution reaches a browser. The same reply carries, for each map, how many attempts it has, how many are beaten and whether the reader is in one, and the reader's own attempt. A map's view, `/maps/<game>/<map>`, reads `GET /api/maps/<game>/<map>`: the same map fields, every attempt on it and the reader's own attempt. Each attempt carries its language, its starter, everyone who ever played it (those in it first), whether someone is in it, whether it is the reader's, whether it is beaten and when it was last played, the newest of its start and its last line. Every screen outside an attempt puts the reader's own in the header as a "Your attempt" pill that leads back to it.

A map with an image shows it on its row, in its view's banner and at the head of its join view in place of the drawn plan; a map without one, such as the test map, keeps its plan. The page loads it from `GET /api/images/<sha-256>`, the one route a page uses that needs no sign-in: it answers the stored bytes with `public, max-age=31536000, s-maxage=31536000, immutable`, so Vercel's CDN and the browser keep it and a later page load never reaches the function for it. Until it has loaded, its frame is a skeleton the size it will take; if it fails to load, the plan shows instead.

An attempt is **beaten** once every step of the latest bundle that is not `optional` is recorded done in `run_steps` (its row for the whole step, not a part's). Both replies work it out in the query from the bundle's `steps`, so a later bundle with a new required step makes an earlier attempt not beaten until that step is done too. Beaten is only a mark: the attempt stays open and can be joined and played on like any other, and the replies say nothing about which steps are done or how many are left.

## Attempts

Each map's row on the maps page opens the map's view, which lists every attempt on the map and holds Start an attempt with the language Cari speaks inline (Spanish unless they pick English): `POST /api/runs`. The list puts the reader's own attempt first, then the others someone is in, most recently played first, then the rest, newest first; the beaten ones carry their mark wherever they fall. Anyone signed in can join any attempt with one tap on its row there, or from its link, `/attempts/<id>`, which shows the join view to a reader not in it and the attempt to a member (`POST /api/runs/<id>/join`); an attempt's "Copy link" gives that link. A person is in one attempt at a time, so starting or joining one leaves the one they were in, which a line under the actions says, without a step to confirm it. Nothing closes or ends an attempt, not even when it is beaten: one everyone has left stays on its map's list and can be joined again.

A new attempt's knowledge marks are the latest bundle's `known` entries plus every entry known in the starter's earlier runs on that map (an imported run takes the terminal's marks instead, as above); each member who joins adds what was known in their own earlier runs there.

The run page polls `GET /api/runs/<id>/messages?after=<last id>&rungsAfter=<last rung id>` every 2 seconds for new lines, the current members and every hint card that gained a rung or arrived with a new line, each card carrying its rungs' wording, each rung's zone, and whether it shows More. `POST /api/runs/<id>/messages` adds a member's line and answers with Cari's reply as it is spoken. Both answer 403 to anyone not in the run.

## Zones

A rung that gives a place, at level 3 and sometimes level 4, can carry a zone, and its card shows it under the rung's text as the `run-zone` boards draw it: the survey image inset in the slip with the zone over it as a hatched red ellipse, its red edge on a pale halo so it reads on a dark image, and one ring pulsing out from it ([Site Design System](../reference/design-system.md)). Levels 1 and 2 never show one. The card's rungs take their zones from the map's latest bundle when the card is read, by the rung and Alt delivered, so a zone fixed and published mid-run shows on the cards already given; the survey image's digest and size come with each zone, never in the map's own fields, so the overhead map reaches a browser only with the first zone. A bundle with zones and no survey image, which only the hand-written test map has, draws the zone on the map's drawn plan instead, on a ruled sheet. The ee-coach skill finds the survey image and places and blind-checks the zones at prepare ([Research and dossier building → Zones](../../../../.claude/skills/ee-coach/references/research.md#3b-zones-one-agent-with-dossier-access-then-a-blind-check)).

## Revisions and Ratings

A line is a revision when its text starts with `REVISION:` (or `Revisión:`, in any case) or when it is sent with the composer's Revision toggle pressed, as the `run-revision` boards draw it; the mark is dropped from the stored text. A revision never reaches the model: it is stored with `kind` `revision`, a `feedback` row records it with the last Cari line before it that was not an acknowledgement (and that line's card and newest rung, when it has one), and Cari answers at once with a fixed line in the run's language, "Anotado, gracias." or "Noted, thanks.", stored as an `ack`, in the same streamed reply shape as any other but with no Claude call. The chat shows a revision with its tag and "re: Cari time · for Claude". Every line whose `kind` is not `chat` is left out of the conversation the model reads.

Every card's foot holds the three ratings (too obvious, right, too vague) in Cari's language. A tap is `PUT /api/runs/<id>/cards/<card>/feedback`, which keeps one rating per member per card, the latest, with the card's newest rung at that moment; each reader's poll returns their own rating on each card. Ratings never reach the model either. Claude reads both from the run read above and folds them into calibration and the hints in the ee-coach debrief.

## Cari

Cari is Claude, `COACH_MODEL` (Haiku 5.5, `claude-haiku-5-5`, unless set) with `ANTHROPIC_API_KEY`, called by the function on every member's line; without a key she stays silent. The model never writes a hint: it acts through six tools, and code decides what each may do.

- **`give_hint`** hands over the next rung of one ladder, or one of that rung's Alts. Code gives only a rung whose `mentions` are all known in the run (its `reveals` may still be unknown, since it is the line meant to give them away), one per reply, level 4 only when the model says the players asked for the answer, and records the delivery and adds the rung's `mentions` and `reveals` to `run_knowledge` in the same transaction.
- **`mark_known`** takes the players' words; code marks known every unknown entry whose name, in either language and without its article, appears both in them and in a member's line among the last 24, so the model cannot mark something only a rung named.
- **`record_progress`** records a step or part as started or done, by its handle. A step marked done marks every step it `requires` done too, since they had to come first. On a step done, code marks known what its `onSuccess` line mentions and the players named in the chat, says that line when all it mentions is known, and hands over on a card the first rung of a ready step, the one the model names with `next` or else the first in the bundle's order; the model passes `quiet` only when the players said what they are doing next. A part done just closes that part's ladder.
- **`heads_up`** says one of an open step's heads-ups, word for word, once per run.
- **`hold`** is for a question no listed hint covers. Code says one of three prepared holding lines in the run's language, in turn by how many gaps the run has, records a gap with the model's few words on what was asked and the run's state, and ends the reply; it is refused after a hint in the same reply. Claude writes and checks the missing line from the gap, and publishes it ([ee-coach → Watch a run](../../../../.claude/skills/ee-coach/SKILL.md#watch-a-run-from-claude-code)). From then the gap is listed to the model under "Held earlier", with the line that was asked, on the run's next reply; `give_hint` takes a `gap` number, and a rung given with one records that gap answered and by which delivery. A run still waiting when the version lands, whose newest gap is open and has no member line after it, gets the reply at once: the publish route runs a turn for it in which the model may only give a hint, told that new hints were written for that question, and a hint arrives under a new Cari line on everyone's next poll while anything else is dropped. Either way a gap is offered once per new version, so a question no new line answers is not raised on every reply, and `publish` prints how many waiting runs were answered at once.
- **`ask_round`** adds the run's fixed question about the round to the reply, at most once every 10 minutes and never in a reply that gives a hint.

The prompt is a system prompt distilled from the ee-coach skill's session rules, then the run's state, sorted the way the skill keeps its open threads:

- **Open threads:** each ladder the players started or were given a rung of, with the rungs given and the next rung and Alts code would allow.
- **Ready:** the first rung of each ladder not opened yet whose step's `requires` are all done and whose `mentions` are known, never an optional step's.
- **Optional, not started:** listed only so the model can record one the players start themselves; code refuses any rung of an optional step until then.
- **Blocked:** steps whose `requires` are not all done, each listed once the players have opened it or, for a required step, once its title names nothing unknown.
- **Done**, and the heads-ups and conditions of the open threads.

A step or part is named by its title only when the title names no unknown entry, so the model can tell which one the players are talking about without learning what they have not met; otherwise it is only its handle. An Alt, heads-up or condition whose text names an unknown entry is left out. Ladders are named by handles (`s2`, `s2p1`), never by their step's title, so the dossier and the titles stay out of it, and an unknown entry's name reaches the model only inside a rung meant to reveal it, which is one of the rungs it may give. The last 24 lines of the chat are the conversation, with each card's rungs under Cari's line in brackets; a run's imported history is never part of it.

A blocked step gets no hint of its own. The first time the model asks for one, code says a fixed line in the run's language, the skill's "this isn't budging… maybe it isn't the moment", and records it; each later ask hands over the next rung of the step that is missing, followed down its own `requires` to one that is ready, so the ladder aimed at the blocker is made of that step's checked rungs and names nothing they lack before those rungs do.

Her own words are streamed to the asker sentence by sentence as newline-delimited JSON, while the run page shows her row "transmitting" with the blinking caret; a sentence naming an unknown entry, holding brackets, showing a step or hint number ("paso 2", "la última pista", "quedan dos pistas", "2/4"), or repeating a line code said or a rung given is dropped and recorded as a violation instead. When the reply ends, her line and its card are stored together and every member's next poll shows them. When the reply fails before she has said anything or given a card (the call to Claude, or the turn itself throwing), the stream ends with a `failed` event, so the asker's page says she did not answer instead of falling silent; a refusal stays silent. A card's More asks `POST /api/runs/<id>/cards/<card>/more`, which gives the ladder's next rung onto the same card in code, without a model call, when that rung is allowed; when it is not, the model is told More was pressed and chooses an Alt or asks what they see. More shows only on the newest card of its ladder, never when the next rung is level 4, and never once its step or part is done; a poll after a step is done sends that step's cards again without it.

Each Claude call is a row in `coach_calls`, and each rung a row in `deliveries`, so a run's whole hint history can be read back against its marks.

Every reply is audited by code when it ends. The findings are every violation its calls recorded, plus three checks on the reply as a whole: `unknown-in-reply` when the posted line names an entry still unknown, `rung-skipped` when a rung it handed over sits past a rung of its ladder never given in the run, and `optional-offered` when it handed over a rung of an optional step that was not open before the reply, which happens when the model records the step started itself and then hints it. A reply with any finding gets a row in `audits`, which `watch` prints; what code cannot judge (a paraphrased hint, a choice offered, the wrong ladder for the question) is left to Claude's reading of the reply ([ee-coach → Watch a run](../../../../.claude/skills/ee-coach/SKILL.md#watch-a-run-from-claude-code)).

## Voice

Cari hears and speaks in the group's Discord call through the bot's [zombies module](../../bot/explanation/bot.md); the site keeps the run and the coach, and the bot holds no run state and calls no model. The two talk over HTTP with the bot's `INTERNAL_SECRET` as the bearer token both ways, as the [DJ panel](../../../dj/panel/explanation/panel.md) calls the bot; `BOT_URL` is where the site finds the bot.

- **The offer:** the run page asks `GET /api/runs/<id>/voice` every 10 seconds while it is visible, and the function asks the bot's `GET /zombies/voice` for the reader. When the reader is in a voice channel, the voice panel at the rail's foot (a bar under the strip on a phone) names it with a **Bring Cari in** button, or says why Cari cannot join it (the bot's role cannot reach it, or it is full); once Cari is in that channel it turns red, on air, and says to say «cari» and the question ([Site Design System → Voice panel](../reference/design-system.md#components)). With the reader in no channel, or the bot unreachable or not configured, it is not shown.
- **Bringing her in:** the button posts `POST /api/runs/<id>/voice/join`, which calls the bot's `POST /zombies/join` for the reader and answers `{ channelId }`, 409 with the bot's refusal (`notInVoice`, `noAccess`, `full`), or 503 `botOffline`. Both routes are for the run's members only.
- **Hearing:** the bot sends what follows «cari» to `POST /api/voice` as `{ userId, text }`. The function finds the run the speaker is in (a person is in one run at a time), posts the words in its chat as the speaker's line and runs Cari's turn on it as if typed, so every member sees both in the chat. It answers `{ reply }`: what Cari said, followed by the text of any hint she handed over on a card in that turn, which the bot speaks. A line starting `revisión:` or `revision:` is stored as a revision and answered with its acknowledgement. A speaker in no run, or a turn in which Cari said nothing, answers `{ reply: null }`, and the bot stays silent. A turn that fails answers 500, which the bot logs and also meets with silence. A turn waits up to 30 seconds for the run's lease while another reply runs, and the bot gives up after 25, so a «cari» asked during another member's reply can land in the chat with its answer and not be spoken.
- **Keeping the call:** while Cari is in the call the bot sends every line said there to `POST /api/voice/transcript` as `{ userId, name, text, at, ms, broughtBy }`, with the same bearer token. The function files it under the speaker's run, or, for a speaker in no run, under the run of `broughtBy`, the member who brought Cari in, and stores it in `call_lines`; it answers `{ kept }`, `false` when neither is in a run. The lines reach the watch stream and the Claude read of the run for the watch loop and debriefs, and nothing else: the run page, the coach model and the audits never read them, so the live model still gets only what follows «cari».

Typed questions get text answers only, and a run keeps working without the bot: the site never needs it to answer in the chat.

## Moving Between Pages

The page moves between screens itself, with `history.pushState` (`src/route.ts`), so the header stays and only the content under it changes. Each page's last reply is kept in memory (`src/store.ts`), keyed by what it shows: the maps list, a map, an attempt. Coming back to a page shows that reply at once and asks for it again in the background, swapping the fresh one in place when it lands, so what another member did since shows up as soon as that reply is in, without a skeleton; if the refresh fails the page keeps what it showed, and the next visit asks again. A page shows its skeleton only when nothing about it is known yet. A reply less than a second old, or one already on its way, is used rather than asked for twice. Pointing at a link, focusing it or pressing it starts that page's request, unless its reply is under 15 seconds old, so it is usually in by the time the page opens. A map opened from the maps list draws its banner from the list's row while its attempts load, and an attempt's log keeps the lines it already polled, so coming back to it asks only for lines after them. The maps list keeps the scroll position it was left at, whether the reader comes back by Back or by a link to it.

The store lives only in the open tab and empties on every full load. Signing in, switching members with the dev sign-in route and switching the language all reload the page, so one member's replies never reach another, and an attempt the reader joins or starts is asked for afresh rather than shown from a copy taken before they were in it.

## Load Time

Every API reply carries a `Server-Timing` header (Hono's `timing` middleware): `viewer` for the root lookup, `db` for opening the Postgres connections, one entry per query (`maps`, `runs`, `run`, `members`, `mine`) and `total`. A browser's network panel shows it, as does `curl -sD - -o /dev/null` with the reader's cookie.

A page load makes one API call. `/api/maps` runs three queries side by side (`maps`, `runs`, `mine`): the published maps, every run with whether it is beaten, and the reader's current run; `/api/maps/<game>/<map>` runs four (`maps`, `runs`, `members`, `mine`), its map's runs and everyone who joined them in place of every run; `/api/runs/<id>` runs its four (the run, the published maps, its members, the reader's current run) side by side. Before 2026-11-15 a page load also called `/api/me`, so it made two root lookups and `/api/maps` ran four queries one after another over every run ever made; from 2026-11-15 to the attempts list it listed only runs with someone in them.

## Hosting

Vercel serves the site from the owner's Hobby team as the project `enbraile-zombies`: the Vite build's static `dist/` and the API as one Vercel Function in the same project. Unlike pkmn's and the DJ panel's, the function is not built by Vercel from a file in `api/`: `npm run build` ends with `scripts/build-api.ts`, which bundles `api/_lib/handler.ts` (the Hono app as a Node request listener) with esbuild into `.vercel/output/functions/api.func/`, copies `dist/` to `.vercel/output/static/` and writes the routes, and Vercel deploys that [Build Output API](https://vercel.com/docs/build-output-api) directory as it stands. The routes serve a file when one matches, send every `/api/` path to the function and every other path but `/assets/` to `/index.html`. The coach and the Anthropic SDK, over a third of the bundle, sit in chunks of their own that the function loads on the first reply that asks Cari, so a page load never parses them ([Load Time](#load-time)). The function runs in Frankfurt (`fra1`, in `vercel.json` and the function's `.vc-config.json`), beside its Neon database (`aws-eu-central-1`). The database is the Neon project `zombies`, its own and never pkmn's, with a `main` branch for production and a `dev` branch for previews. The `zombies-site.yml` workflow deploys pushes to `main` touching `zombies/site/` to production, and other branches' pushes as previews, which Vercel's Deployment Protection keeps to the team ([How to Deploy the Vercel Projects](../../../general/how-to/deploy-vercel-projects.md)). The function also reads `ANTHROPIC_API_KEY` and `COACH_MODEL`, set in Production. `zombies.enbraile.vip` is on the project's domains and has, since the owner added it on 2026-11-15, a DNS-only (grey-cloud) `CNAME` to the Vercel target in the `enbraile.vip` zone on the owner's Cloudflare account. It is DNS-only for the reason pkmn's is: Cloudflare's proxied IPs are blocked by Spanish ISPs during LaLiga matches ([The pkmn Site → Decisions](../../../pkmn/site/explanation/site.md#decisions)). The root site lists the domain in its `trustedOrigins`, so sign-in returns to it. Setting it up is in [How to Run and Deploy the Site](../how-to/run-and-deploy-the-site.md#9-set-up-production-once).

## Decisions

- **The site is the brain, the bot only an interface:** the site's function holds map bundles, run state and chat, calls Claude and enforces the hint rules in code; the bot turns «cari …» into a call to the site's API and speaks the answer. **Why:** the bot runs on the homelab and has other jobs, so the site must work with the bot down. A bot-module brain was proposed first and rejected. _(owner, 2026-11-15)_
- **No numbers, no step list, the UI is never a hint:** no step or hint numbers anywhere (the terminal's "Step 5 · hint 2/4" is not shown), no list of steps, and no buttons or suggestions that tell players what to try. _(owner, 2026-11-15)_
- **Hints as cards:** one shared chat with Cari, where hints arrive as cards with a generic "more" control and the three feedback controls (too obvious, right, too vague); a level-3 zone shows under its card. _(owner, 2026-11-15)_
- **Cari's voice only:** no chimes or clips on a new hint, since a cue would itself carry meaning. _(owner, 2026-11-15)_
- **One `bundle.json` per map dir:** `publish` takes the dir that holds a map's files, and `compile` writes the bundle there. _(the agent's choice, 2026-11-15)_
- **Bundle IDs from the prepare files' numbers:** steps become `step-<n>`, a step's part ladders `part-<n>` in order, and knowledge entries their `K` IDs in lowercase, so the bundle needs no second set of names to keep in step with `hints.md`. _(the agent's choice, 2026-11-15)_
- **`reveals` written by hand in the hints:** each line lists after its `Mentions` the IDs it is meant to give away (`Reveals:`), rather than `compile` guessing them from step order, since players choose the order. _(the agent's choice, 2026-11-15)_
- **Several Alts per rung, each with its `when`:** prepared hints hold more than one Alt for a step, each replacing one named rung in one situation. _(the agent's choice, 2026-11-15)_
- **L4 stays in the dossier:** `compile` takes level 4 from the dossier's `L4 as spoken`, so `hints.md`, which the blind check reads, never holds an answer; the Spanish copy holds it as `L4`. _(the agent's choice, 2026-11-15)_
- **A bundle's baseline marks:** a knowledge entry is `known` in the bundle only when `knowledge.md` marks it `known`; `revealed` counts as `unknown`, since it records what one terminal session gave away rather than what the players brought. _(the agent's choice, 2026-11-15)_
- **Names per language, art as a drawn plan:** the map's name is stored in both languages, since in-game names differ by language, and its row shows one of three drawn plans chosen in the bundle's `art`, since no game's art went on the site; from 2026-11-15 a map's announcement image replaces the plan wherever it has one, and the plan stays for a map without one. The keys stay `teal`, `rust` and `furnace` from the first take's tinted silhouettes, standing for the boards' Harrow Station, Saltmarsh Asylum and Kessel Works plans. _(the agent's choice, 2026-11-15)_
- **The radio log look:** the owner found the first boards "very AI", so the site was redrawn as the group's radio log (transcript rows, dispatch slips, survey sheets, condensed type and five flat inks on paper), which replaces the first take. _(owner, 2026-11-15)_ The third take replaced its look and kept its identity, below.
- **A map's label is its game:** the boards label the made-up maps "Sample"; a published map that is not the test map shows its `game` instead, as the bundle holds no other short line about it. _(the agent's choice, 2026-11-15)_
- **A rung's `reveals`:** the discovery lets a rung mention an unknown thing when it is the rung meant to reveal it; the bundle says which rung that is with `reveals`, next to `mentions`. _(the agent's choice, 2026-11-15)_
- **Versions numbered per map, deduplicated by digest:** the SHA-256 of the bundle's JSON with sorted keys, so key order in the file never makes a new version. _(the agent's choice, 2026-11-15)_
- **Start an attempt on the map's view, not its row:** the boards first drew Start a run on every map's row, but a button that did nothing until runs existed would have been a dead control, so it was left off; since the third take a map's row opens its view, which holds Start an attempt ([Attempts](#attempts)). _(the agent's choice, 2026-11-15; rewritten 2026-11-16)_
- **Several local members:** `DEV_USER_ID` takes a list and each browser picks one of them, so a Claude-run check can be two members of one run; it exists only where `DEV_USER_ID` is set, never in production, which keeps Discord through the root as the DJ panel does. _(owner, 2026-11-15)_
- **The player picks the map:** a run is started from the map the players are playing, picked from the maps list as the boards draw it. _(owner, 2026-11-15)_
- **Closing a run is not built yet:** there is no way to close or end a run, and a run never ends by itself, not even when its last required step is done. _(owner, 2026-11-15)_
- **A run ends only when the players say so:** when closing is built, a run ends only when the players ask for it and confirm. _(owner, 2026-11-15)_
- **Progress kept in `run_steps`, never shown:** what the players started and finished lives on the run for the coach and later for debriefs, and no route a browser calls returns it, since a list of threads would be a hint. _(the agent's choice, 2026-11-15)_
- **The L1 after a step done is chosen in code:** `record_progress` hands it over itself, from the ready steps, so a step done always gets its `On success` line and an L1 in the same reply even when the model forgets, and an optional step is never among them. _(the agent's choice, 2026-11-15)_
- **Titles only when they name nothing unknown:** a step's title reaches the model once the players have met everything it names, so it can record a step they report without seeing what they have not found. _(the agent's choice, 2026-11-15)_
- **Done implies its `requires`:** a step reported done marks the steps it requires done, since the bundle's `requires` say they had to come first. _(the agent's choice, 2026-11-15)_
- **The blocked ladder from prepared lines:** the skill's blocked-thread ladder has no lines of its own in the bundle, so its first rung is one fixed line per language in code and the rest is the missing step's own ladder, which keeps every word prepared and checked. _(the agent's choice, 2026-11-15)_
- **`On success` learns what the players named:** a step done marks known the entries its `On success` line mentions that a member named in the chat, so the line is said when the players reported it in their own words even if the model did not mark them first. _(the agent's choice, 2026-11-15)_
- **Code drops repeats:** a sentence of the model's that repeats an `On success` line, a fixed line or a rung already given is dropped, since Haiku echoed lines code had just said. _(the agent's choice, 2026-11-15)_
- **Knowledge follows the people:** a run's marks start from the bundle's baseline and the starter's earlier runs on the map, and each member who joins adds what their own earlier runs on it knew, so the marks are never lowered by who joins. _(the agent's choice, 2026-11-15)_
- **One link per attempt:** `/attempts/<id>` is both the attempt and its join page, chosen by whether the reader is in it, so a link sent to a friend opens the join view the boards draw. _(the agent's choice, 2026-11-15)_
- **Ladders by handle:** the model sees a ladder as `s<n>` or `s<n>p<m>` from the bundle's order rather than its step's title, since titles name things the players may not know. _(the agent's choice, 2026-11-15)_
- **More in code first:** a card's More gives the next rung without a model call when the knowledge marks allow it, so it is instant and deterministic, and goes to the model only when they do not; an Alt is chosen by the model from what the players said in the chat. _(the agent's choice, 2026-11-15)_
- **The answer is asked for in words:** More never gives level 4; the model gives it only with `answer` set, when the players asked for it in the chat, as the skill's "Level 4 only when they clearly ask for the answer". _(the agent's choice, 2026-11-15)_
- **Marks from the players' words:** `mark_known` takes what the players said and code matches it against the knowledge names and the members' recent lines, so the model needs no list of unknown entries to mark one and cannot mark one the players never named. _(the agent's choice, 2026-11-15)_
- **Sentence-by-sentence streaming:** Cari's words reach the asker a sentence at a time rather than token by token, so a sentence naming an unknown entry is dropped before anyone reads it. _(the agent's choice, 2026-11-15)_
- **The speaker's run is their one current run:** `run_members` keeps a person in one run at a time, so a Discord ID is enough to find where a spoken line goes, and nothing else has to be said. _(the agent's choice, 2026-11-15)_
- **A spoken line is a chat line:** it is stored as the speaker's message and answered by the same turn as a typed one, so the chat, the audit and the watch loop see voice and text alike. _(the agent's choice, 2026-11-15)_
- **The spoken reply carries the hint:** a hint is a card in the chat, and a player mid-round cannot read it, so the reply the bot speaks is Cari's words followed by the rungs she handed over in that turn. _(the agent's choice, 2026-11-15)_
- **The voice panel only while in a channel, polled:** the boards draw the panel for a reader in a channel; it is left out otherwise, and asked for every 10 seconds, since only the bot sees voice states and a member joins a channel without touching the site. _(the agent's choice, 2026-11-15)_
- **One reply at a time per run:** a lease on the run's row, held up to 60 seconds, waited on up to 30 (a line still waiting then gets no reply) and released only by the reply that took it, keeps two members' questions from getting two rungs of one ladder at once; Neon's pooled connections rule out a session advisory lock. _(the agent's choice, 2026-11-15)_
- **A card per reply:** a hint asked for in the chat comes on a new card under Cari's line, and More adds the next rung to the card it was pressed on, as the boards draw it. _(the agent's choice, 2026-11-15)_
- **The machine API is Claude's:** the token and routes first named "admin" are `CLAUDE_TOKEN` and `/api/claude/`, since only Claude uses them, from the terminal, to publish bundles and later to read and watch runs and step in as Cari; what they write is attributed to Claude. A browser admin like pkmn's (`npm run admin:create`, `/admin`) is not wanted now. _(owner, 2026-11-15)_
- **No tag in the header:** the header holds the wordmark, the language switch and the name chip; the "Radio log · enbraile.vip" tag is gone from the site, the boards in `zombies/site/design/` and the design-system doc. _(owner, 2026-11-15)_ Since the third take the header also holds the "Your attempt" pill outside an attempt.
- **The third take:** the owner found the radio log's flow awkward and its UI clumsy and hard to read, and asked for clickable map rows and a remake by Claude design; the canvas's "Third take" boards replace the radio log's: every map row opens a map view with its attempts and Start an attempt (which attempts it lists is "Attempts, all listed" below), a shared link lands on the join view, a "Your attempt" pill leads back to the reader's attempt, and the look is a warm dark theme with Atkinson Hyperlegible Next body text, keeping the run as a log and hints as dispatch slips. _(owner, 2026-11-15; rewritten for attempts 2026-11-16)_
- **The map view has its own reply:** `/maps/<game>/<map>` reads `/api/maps/<game>/<map>`, which holds the map, every attempt on it and the reader's attempt, so the maps page's reply carries only each map's counts and does not grow with every attempt on every map; a map not on file answers 404 and shows "No such map on file." Until the attempts list it took its map out of `/api/maps`. _(the agent's choice, 2026-11-15)_
- **Join in one tap from the map view:** an attempt's row on the map view joins it at once and opens it, as the board's row links straight to the run, so picking a map and joining is two taps; the join view is for a shared link. _(the agent's choice, 2026-11-15)_
- **A map row counts attempts:** a map's row on the maps page says how many attempts it has and how many are beaten ("3 attempts · 1 beaten", "none beaten" at zero), and "you're in it" when the reader's attempt is on it, in place of the boards' one run's chips and starter; the maps boards were not redrawn for it. _(the agent's choice, 2026-11-15)_
- **A failed reply says so:** a reply whose Claude call failed before Cari said anything ends with a `failed` event and the run page offers to try again, rather than a silent Cari the players cannot tell from a choice to stay quiet. For a line, trying again posts the line a second time, since a run has no way to ask for a reply without a line; for More, it presses More again. _(the agent's choice, 2026-11-15)_
- **One spacing scale:** every padding, margin and gap in the site's CSS is a step of a 4px scale (`--sp-1` to `--sp-20`), but for the few baseline offsets the [design system](../reference/design-system.md#spacing) names; the boards' in-between values (6, 10, 14, 18, 22px) move to the nearest multiple of 8, so the built screens can sit a few pixels off the boards. _(the agent's choice, 2026-11-15)_
- **Titles fit their longest word:** a map's name in a large condensed title shrinks until its longest word fits its column instead of breaking mid-word, since names differ by language and the published maps' Spanish names are longer than the boards' made-up ones. _(the agent's choice, 2026-11-15)_
- **Attribution as a column:** a bundle version's `published_by` is a column that only ever holds `claude`, set by the route rather than defaulted by the database, so a later writer through another path has to name itself. _(the agent's choice, 2026-11-15)_
- **Holds from prepared lines:** a hold says one of three fixed lines per language, chosen in code, rather than words of the model's, so the line a gap gets is never improvised (her own words around it still pass only the sentence filters above); the line may ask what they see, as the discovery allows. _(the agent's choice, 2026-11-15)_
- **Revisions as lines of the chat:** a revision is stored in `messages` with its own `kind`, so it shows in the log where the boards draw it, and in `feedback`, which carries what it refers to; the history the model reads takes `chat` lines only. _(the agent's choice, 2026-11-15)_
- **A revision refers to Cari's last line:** a revision has no picker for the line it is about, so it refers to the last line Cari said before it that was not an acknowledgement, and Claude reads the log around it. _(the agent's choice, 2026-11-15)_
- **The toggle lets go after a send:** the Revision toggle turns off once its revision is sent, so the next line goes to Cari as play unless it is pressed again. _(the agent's choice, 2026-11-15)_
- **One rating per member per card:** a member's later tap replaces their earlier one, and the rating records the card's newest rung, so a card that grew under More is judged on what it said last. _(the agent's choice, 2026-11-15)_
- **Runs read to a gitignored file:** `npm run runs -- <id>` writes the run under the map's gitignored dir and prints counts, since the log holds hint text the players may read off the terminal. _(the agent's choice, 2026-11-15)_
- **An import is the terminal's record:** an imported run's marks are the bundle's baseline, the entries the session's `knowledge.md` marks known or revealed and what its rungs mention and reveal, without what its members knew in earlier runs on the map, so the run reads back exactly as the terminal left it; members who join later still add their own. _(the agent's choice, 2026-11-15)_
- **Imported rungs on one card per ladder:** the terminal's hints were lines of its conversation rather than cards, so each ladder's rungs given there are one card under a fixed Cari line, as if grown with More, and only lines from the bundle are imported; a hint the terminal improvised has no rung to import and is folded into the hints at the debrief first. _(the agent's choice, 2026-11-15)_
- **The call in a table of its own:** call lines are stored in `call_lines`, not `messages`, so they never enter the chat, the coach model's conversation or the run's line numbering, and a watch event's time is when the site stored the line rather than when it was said, so a late line is never behind the cursor. _(the agent's choice, 2026-11-15)_
- **The terminal's conversation as a history of its own:** a terminal session's lines are imported into `run_history`, not `messages`, so they sit above the imported cards without renumbering the run's lines, the coach model, the watch stream and the audits never read them, and the run's last-played time stays the site's; the players' lines show under "Terminal", since the transcripts do not say which member typed each, and the coach's replies under Cari as they were written, Markdown included. _(the agent's choice, 2026-11-15)_
- **Neon from the Vercel Marketplace, without its variables:** the Neon organization is managed by Vercel and refuses a project made with `neonctl`, so the `zombies` project comes from the integration with `--no-connect`, and `DATABASE_URL` is set by hand per environment with `sslmode=verify-full`, as pkmn's table has it, rather than the integration's own variables. _(the agent's choice, 2026-11-15)_
- **Attempts, all listed, beaten and playing marked:** a run is called an attempt wherever a player sees it ("attempt", "intento", `/attempts/<id>`); a map's view lists every attempt on it, newest first, each with who played it, its language and when it was last played; a beaten attempt carries a mark of its own, and the attempts someone is in are highlighted at the top of the list, the reader's first. This replaces listing only the runs with someone in them. _(owner, 2026-11-15)_
- **Runs inside, attempts outside:** the tables, code, API routes, the machine API and the terminal's commands keep the name `runs`, so no migration renames data; only what a player reads and the page URLs say attempt. _(the agent's choice, 2026-11-15)_
- **Beaten means every required step done:** an attempt is beaten once every step of the latest bundle that is not `optional` has its done row in `run_steps`; it stays open, since nothing closes an attempt, and the mark says nothing about which steps are done. _(the agent's choice, 2026-11-15)_
- **A bundle needs a required step:** the bundle schema refuses a bundle whose steps are all `optional`, so `compile` and the publish route both turn it away, because with no required step the beaten check has nothing left to find undone, so every attempt on it would be beaten from the moment it started. Every easter egg has a required step, so such a bundle is a mistake. _(the agent's choice, 2026-11-16)_
- **Last played is the newest line:** an attempt's "played" time is its last line's, or its start when it has none, since a line is the only trace a playing group leaves on it. _(the agent's choice, 2026-11-15)_
- **The page's first reply names the reader:** `/api/maps`, `/api/maps/<game>/<map>` and `/api/runs/<id>` return `viewer`, and the header takes the name chip from whichever of them loaded, so one page load makes one root lookup; `/api/me` went with the call that used it. _(the agent's choice, 2026-11-15)_
- **The connections open while the root answers:** a member route checks out four Postgres connections at once and hands them back, the widest set of queries a route runs side by side and never past the pool's free room, so idle ones are reused and missing ones opened, at the same time as it asks the root who the reader is, rather than after, so on a cold start the database handshake and Neon's wake overlap the root lookup instead of following it. It only opens connections and runs no query before the reader is known, and only for a request that carries a cookie; a signed-out reader with some other cookie, such as `lang`, waits for it before the 401 that sends them to sign in. A failed connect is dropped and the route goes on. _(the agent's choice, 2026-11-15)_
- **`pg` kept over Neon's serverless driver:** with the handshake overlapping the root lookup, the driver's handshake is no longer on a page's critical path, while the serverless driver would need the WebSocket pool for the interactive transactions and advisory locks `startRun`, `joinRun`, `storeVersion` and the coach use, and a second driver for the local Postgres. The `Server-Timing` figures from a signed-in production load decide whether to revisit it. _(the agent's choice, 2026-11-15)_
- **One bundled function, handed over as Build Output API:** a function Vercel builds from `api/` is compiled file by file with its `node_modules` beside it, which a cold start reads one file at a time; bundled with esbuild it loaded in 50 ms locally instead of 330 ms, and a cold preview answered in 0.75–0.81 s instead of 1.7–2.0 s. Vercel compiles whatever function it finds in `api/` its own way, so the build writes the function, the static files and the routes to `.vercel/output/` instead, and `api/index.ts` is gone; `scripts/dev-api.ts` still serves the app unbundled locally. `vercel.json` sets `fluid: true`, the project's default, so the hand-made function keeps Fluid compute. _(the agent's choice, 2026-11-15)_
- **The coach loaded on the first reply:** `api/_lib/app.ts` imports `coach.ts` when a reply first needs Cari, so its chunks and the Anthropic SDK's, over a third of the bundle, are not parsed on a cold page load. _(the agent's choice, 2026-11-15)_
- **A map's real art on the site:** the maps list, a map's view and the join view show the map's real art in place of a drawn plan, as the hints will show the real overhead map. _(owner, 2026-11-15)_
- **The announcement image is a map's art:** the art shown is the map's official announcement image, the reveal art a map normally gets, which the ee-coach skill looks for among the map's sources during research and saves with the map's files. _(owner, 2026-11-15)_
- **Unfound areas in a map image are fine:** an image may show areas the players have not found, so the image is not checked for layout or for areas the knowledge marks unknown; it is checked only for being the official art and for showing no easter-egg step or solution. Map images still never go into a tracked file, and anything that reads a map's dossier, hints or knowledge still runs in a subagent. _(owner, 2026-11-15)_
- **Map images in Postgres, behind an immutable URL:** an image is stored once in `map_images`, keyed by the SHA-256 of its bytes, and served by the function at `/api/images/<sha-256>` with a year-long public cache, so the CDN serves it after the first request. That keeps it in the Neon project the bundles already use, on its free plan, rather than a store that would need its own setup on the Vercel team. The bundle carries only the digest, so a new image is a new bundle version and an unchanged one is not uploaded twice. _(the agent's choice, 2026-11-15)_
- **Zones as ellipses in fractions of a survey image:** a zone is the boards' ellipse, stored as its centre and radii in fractions of the survey image, so it does not depend on the image's pixel size or the card's width; one survey image per map, the overhead map a community draws of the whole level. Zones live in the map dir's `zones.json`, keyed by the rung's address, rather than in `hints.md`, since a place is the same in both languages and the hint files stay text the blind check reads. _(the agent's choice, 2026-11-15)_
- **A zone from the latest bundle, its image only with it:** a card's zones are looked up in the latest bundle by the rung delivered rather than copied into `deliveries` with the wording, so a misplaced zone fixed mid-run is fixed on cards already given; and the survey image travels with each zone rather than in the map's published fields, so no page shows the overhead map before a hint gives a place. _(the agent's choice, 2026-11-15)_
- **The test map's zone on its drawn plan:** a bundle with zones and no survey image draws them on its drawn plan, so the committed test map can show a zone without any map image in the repo. _(the agent's choice, 2026-11-15)_
- **Images need no sign-in:** the image route is open, as the browser's request for an image would otherwise make every load a lookup at the root, and a public answer is what lets the CDN keep it; a map's announcement image is public art, and its URL is learnt only from a signed-in reply. _(the agent's choice, 2026-11-15)_

- **A watch stream, not a push:** Claude Code follows a run by polling `/api/claude/runs/<id>/events` every 2 seconds, as the run page polls its messages, since Vercel Hobby has no websockets and `Monitor` turns each printed line into an event. _(the agent's choice, 2026-11-15)_

- **The watch prints no text:** `watch` prints kinds, names and IDs only and keeps every event in a gitignored file, so the main conversation, which the players may read, never shows a rung, a question or a line of Cari's; whatever reads the text does it in a subagent. _(the agent's choice, 2026-11-15)_
- **A held gap is answered by the model naming it:** after a new version Cari sees the held questions with the line asked, and a rung counts as the answer only when the model gives it with that gap's number, rather than code guessing which new rung fits which question. _(the agent's choice, 2026-11-15)_

Since no run ends, a run left on an open gap gets its answer whenever the version lands, even long after. The turn that answers at once can only give a hint, and says nothing if none fits. _(the agent's choice, 2026-11-15)_
- **Offered once per version:** a held question is offered on the first reply after each new version and then marked tried at it, so the model is not asked about the same question on every line. _(the agent's choice, 2026-11-15)_
