# Runtime Reference

Facts about Añil's runtime under the bridge, verified on the build we play. Each section names the build and how the fact was checked. [Runtime Design](../explanation/runtime-design.md) holds the decisions built on them; [How to Run the Harness](../how-to/run-the-harness.md) the commands.

Every section but the first was verified with Wonder's harness (`~/workspace/wonder`), which `anil` copies, and is kept as recorded there: its commands are `wonder …`, its bridge module `WonderBridge` in `wonder_*.rb` files, its port 24711, its data root `~/.local/share/wonder/` and its working copy `Pokemon Anil-wonder`. In `anil` these are `anil …`, `AnilBridge`, `anil_*.rb`, 24731, `~/.local/share/enbraile/anil/` and `Pokemon Anil-enbraile` ([Runtime Design → Project Layout](../explanation/runtime-design.md#project-layout)). Wonder's `wonder_run.rb` (run records) is not in `anil`'s bridge, so a fact below that names a run, a `save` record entry or the panel describes Wonder only; so do facts cited from commands and modules `anil` does not have yet (`check` and its record entries) or will not have (`know`, `game deploy`). Wonder's `wonder_rules.rb` (the rules hooks) is in it, as `anil_rules.rb` ([Rules Engine Design](../explanation/rules-engine-design.md)). Wonder's Run Records and Panel sections describe Wonder only and stay in Wonder's runtime reference.

### Frame Rate

With `vsync` and `syncToRefreshrate` off, `Graphics.frame_rate` is honoured exactly up to 60. Above that the real rate keeps rising with no fixed cap, but falls short of the target. `frame_rate` reads back the value set, and `Graphics.frame_count` advanced one per rendered frame. Frames counted in the probe's poll over 5 s per setting, on the title screen and on map 1 during the Oak intro (`Scene_Map`):

| `Graphics.frame_rate` | Title screen (fps) | Map 1 (fps) |
|----------------------:|-------------------:|------------:|
| 40 (default) | 40.0 | |
| 60 | 60.0 | 60.0 |
| 120 | 110.6, 112.8 | 111.1 |
| 240 | 129.7, 126.9 | 128.0 |
| 1000 | 161.7, 161.1 | 162.9 |

The shortfall is the same on both scenes, so it is not the animated title.

The bridge protocol as built: one JSON object per line each way on `127.0.0.1`. A request is `{"id", "cmd", ...}`; every reply is `{"id", "tick", "ok", "result", "error", "events", "events_gap", "caller", "payloads", "digest"}`; any request may carry `since`, and `events`, `events_gap` and `since` are described in [Events](#events), `caller` and `payloads` in [Context](#context), `digest` in [Session Record](#session-record). Requests after `hello`: `eval` (`source`) answers `class` and `inspect`; `stack` answers `frames`; `shot` answers `file`, a BMP name in the session directory; `rng` answers `calls`; `read` (`paths`, a list of `[name, path]` or `[name, path, depth]`, plus optional `depth`, `calls` and `stop`) answers `values` and `errors` keyed by name, as described in [State Read](#state-read); `advance` and `control` are described in [Input and Lockstep](#input-and-lockstep), `speed` in [Speed](#speed), `snapshot` in [Snapshots](#snapshots), `pause` and `status` in Wonder's Panel section, `sound` in [Sound](#sound), `note` in [Session Record](#session-record). The first request on a connection must be `hello` (`client`, and an optional `role` of `driver` or `control`), which answers `protocol`, `bridge_hash`, `build`, `pid`, `tick`, `session`, `role`, `snapshot` (the snapshot the session booted into, or `null`) and `event_seq` (the number of the latest event, 0 before the first); any other first request, an unknown command or a line that is not JSON gets `ok: false` with the error, a line in `bridge.log` and the game keeps running.

An event on the wire is `{"seq", "tick", "kind", "data"}`. `battle_text` carries `data.text` and `data.via` (the method: `pbDisplay`, `pbDisplayPaused` or `pbDisplayBrief`); `debug_log` carries `data.text`. `reveal` carries `data.battler` (the battler index, always odd: only the opposing side is recorded), `data.side` (1), `data.trainer` (the trainer id, `LIDER1:Brock:0`, or null in a wild battle), `data.slot` (the Pokémon's index in its trainer's own party, or in the wild party; while an Illusion holds, the index of the Pokémon it appears as), `data.fact` and `data.via` (the hooked method, or `text`). When an Illusion breaks, each fact filed under the disguise during that battle moves to the true Pokémon's slot, with a `reveal` for that slot whose `via` is the wrapped method that cleared it (`triggerOnBeingHit`, `pbOnLosingAbility` or `triggerOnSwitchIn`) when the fact is new there, and the same for the true Pokémon's ability `ILLUSION` (`own` when it is the Pokémon's `ability_id`). A `fact` is `{"kind": "move" | "ability" | "item", "id", "own"}` as [State → Reveals](state.md#reveals) stores it, given only when it is new to that store, or `{"kind": "send_out", "species", "illusion"}` with the species the databox shows (an Illusion's disguise) at every send-out, which is not stored. The `reveal` follows the `battle_text` it was matched in. Safari battles (`SafariBattle`, not a subclass of `Battle`, with its own display methods) give no `battle_text` events. Text that is not valid UTF-8 is sent as `{"class": "String", "bytes": <hex>}`, as [State Read](#state-read) does. Any request may carry `since`, a non-negative integer (anything else is refused); its reply's `events` lists the ring's events numbered above it, oldest first, at the tick the reply is sent, so a deferred `advance` or `snapshot` reply carries everything up to its end. A request without `since` gets `events: []`. `events_gap` is true when events numbered above `since` have already left the ring, which keeps the newest 1,000. In `record.jsonl` an event is `{"tick", "kind": "event", "seq", "event", "data"}`, with the event's kind under `event`. Event numbers go on rising across snapshot restores, while ticks step back.
