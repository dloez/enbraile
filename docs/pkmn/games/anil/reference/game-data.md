# Game Data Reference

The build's compiled GameData files for species, moves, abilities, items, types, trainer types and trainers, the statuses its scripts register, and what the game holds once the Randomlocke mod is loaded. All of it was verified on the build we play with our own tooling. The reader and its cache are `src/anil/harness/gamedb.py` (`anil db`). The design is [Game Database Design](../explanation/game-database-design.md). Its facts were verified with Wonder's harness and are kept as recorded there; [Runtime](runtime.md) maps Wonder's commands, modules and paths to `anil`'s.

## Data Files

Verified 2026-10-03 on `es-v4.14`. `wonder db --rebuild` read `game/base/es-v4.14/Data/` with `rubymarshal`. `wonder db check` then compared every entry's instance variables, and the order of each `DATA` hash, with the running game, and found no differences. That ran in session `20261003-023840` (save `gamedb-1`, at the title screen, the mod loaded); the trainer files were added and checked the same way in session `20261003-024814` (same save, at the title screen). Each file is a hash from the ID to one GameData object; the ID is a symbol in every file but `trainers.dat`. The hash order is the order of the game's `DATA`, which is PBS order. Strings come back as `RubyString`s, IDs and enum-like values as `Symbol`s, and absent values as `nil`. Every object in these files also carries `@pbs_file_suffix` (an empty string).

## Statuses

Statuses are not in a data file. `S/117_Status.rb` registers them with `GameData::Status.register`, keeping `@id`, `@real_name` (default `"Sin nombre"`), `@animation` (default `nil`) and `@icon_position` (default 0). In the file order they are `NONE` (`Ninguno`), `SLEEP`, `POISON`, `BURN` and `PARALYSIS`, then a pair guarded by `Settings::FREEZE_EFFECTS_CAUSE_FROSTBITE` (`true` in `S/002_Settings.rb`): `FROZEN` when it is false, `FROSTBITE` when it is true. Both are `Congelado`, with animation `Frozen` and icon 4. With the mod, the live list is `NONE`, `SLEEP`, `POISON`, `BURN`, `PARALYSIS`, `FROZEN`, with `FROZEN` in the place of `FROSTBITE` and keeping its fields ([Battle Mechanics](battle-mechanics.md)). `wonder db check` found the cache's six equal to the live `GameData::Status` in session `20261003-023840`.

## Types and Matchups

`GameData::Type#effectiveness(attack)` (`S/129_Type.rb`) checks the defending type's lists in a fixed order: `@weaknesses` gives 4 (super effective), then `@resistances` gives 1, then `@immunities` gives 0, and anything else gives 2. `Effectiveness.calculate(attack, *defend)` multiplies `effectiveness / 2.0` over the defending types, starting from 1.0. All 361 single-type pairs computed this way from `types.dat` equal the live `Effectiveness.calculate` (session `20261003-023840`). For example, Fairy is hit for ×2 by Poison and Steel and ×0.5 by Fighting, Bug and Dark, and takes nothing from Dragon.

## Data the Mod Changes

The data files are untouched, and the mod changes only the loaded objects ([Randomlocke Design → Applying the Caps](../explanation/randomlocke-design.md#applying-the-caps)). In the loaded `GameData::Species` objects, each allowed species-form has the types from `randomlocke/data/types.txt`. 37 species differ from `species.dat` (`CHIKORITA` is `[GRASS, FAIRY]` in the file and `[GRASS]` live). Of those, 33 are retyped and 4 (Farfetch'd, Jynx, Smoochum, Altaria) only list their types in another order. In statuses, `FROSTBITE` becomes `FROZEN`. Moves, abilities, items (until a TM is rolled, below), types, trainer types and trainers are loaded unchanged: the randomizer rolls a trainer's team when it is loaded, not in `GameData::Trainer` ([Randomizer → Trainers](randomizer.md#trainers)), and `wonder db check` found all 685 trainers equal to the file in session `20261003-024814`. With Brock 0's first `level` set to 13 by eval, the check failed on that trainer alone. No move, item or ability in the data files mentions frostbite.

Items stay as loaded only until a TM is rolled. The randomizer's `GameData::Item#move=` (`P/Random Pokemon & Moves + Randomizer EX (Abilities)/003_Items.rb:9-13`) stores the rolled move in `$PokemonGlobal.tm_move_map` and also in the shared item object's `@move`. Three calls give a TM the move it keeps: a random item or field TM (`random_item`, `:180`, and `determine_random_item`, `:249`) and a TM mart's first visit (`tm_mart`, `:327`), each with the `GameData::Move` that `random_move_for_tm` returns, where the file holds a symbol. A TM mart draws its TMs through `random_tm` and `find_unique_tm` (`:218`, `:312`), which sets each TM it samples to a symbol move (`:372`) before `:327` overwrites the TMs kept, so a TM it sampled and passed over because the bag held it keeps a symbol move. `randomize_tm_moves` (`:300`) has no live caller: its one call (`:328`) is commented out. In session `20261003-032503` (snapshot `tmc-a`, save `tmmove-verify`), `wonder db check` passed on all 887 items with 60 TMs in `tm_move_map`, since a boot loads the items fresh from the file whatever the save holds. Ruta 1's TM75 ball (map 3 event 9), picked up with `wonder interact`, gave TM75 teaching Doble Golpe (`DOUBLEHIT`). The check then failed on TM75 alone (`@move cached 'SWORDSDANCE', live '#<GameData::Move>'`), and the live `@move` was the same object as `tm_move_map[:TM75]`. `GameData::Item#move` returns the `tm_move_map` entry when there is one and `@move` otherwise. What a snapshot restore leaves in `@move` is in [Runtime → Snapshots](runtime.md#snapshots). Since then the check accepts a TM's `@move` when `tm_move_map` gives it ([Game Database Design → The Check](../explanation/game-database-design.md#the-check)).
