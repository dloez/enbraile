# Level Caps

How Añil's Level Caps EX plugin caps the player's and trainers' levels, as seen in the running game. The owner's decision that the cap is a hard cap is in [Randomlocke Design → Scope](../explanation/randomlocke-design.md#scope); the cap for each badge, as players read it, is in [Rules → Level Cap](../../../series/1/reference/rules.md#level-cap). Its facts were verified with Wonder's harness and are kept as recorded there; [Runtime](runtime.md) maps Wonder's commands, modules and paths to `anil`'s.

Verified 2026-10-02 on `es-v4.14` with the Randomlocke mod and the bridge, by `wonder check level-cap` (`packages/harness/src/harness/check.py`), in session `20261002-105939` (save `lvcap-1`). The game was started by `wonder run --hidden` on an empty save and driven from the title through the intro to the bedroom with 0 badges. The check passed three times there: twice alone, and once inside `wonder check all`, whose `replay` replayed the session as `20261002-110338` with no digest mismatch ([Runtime → Checks](runtime.md#checks)). The rows on the later caps and on switch 29 come from the extended check, which passed twice in session `20261002-122944` (save `lvcap-2`), a new game started the same way and driven through the intro to the bedroom with 0 badges; its switch settings, levels and battles all ran inside its snapshot. The extended check passed again inside `wonder check all` in session `20261002-130841` (save `all-hof-1`), booted into the snapshot `lvcap2-new` taken in the bedroom of session `20261002-122944`, on the bridge deployed after the restore kept the snapshot's TM-compatibility table ([Runtime Design → Snapshots](../explanation/runtime-design.md#snapshots)); `replay` replayed it as `20261002-130934` with no digest mismatch ([Runtime → Checks](runtime.md#checks)). Code citations are to `P/Level Caps EX/`.
