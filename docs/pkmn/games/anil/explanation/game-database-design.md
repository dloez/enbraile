# Game Database Design

How the harness knows the build's static game data: every species and form, move, ability, item, type, status, trainer type and PBS trainer as the game sees them with the Randomlocke mod applied, and every item ball, hidden item, gift and mart on the maps, read from the build's compiled data files into a cache of our own, with every fact tagged by what a player can know of it. Scoped with the owner on 2026-10-03. The core battle data, the trainers, the locations and the live reads of the run's rolled data were built the same day. The code is `anil.harness.gamedb`, with the live reads in `anil.harness.random` and the check in `anil.harness.check`. It is copied from Wonder's game database design (Wonder: `docs/subsystems/harness/explanation/game-database-design.md`), where it was built and checked against the game, without Wonder's agent and control panel. Sessions named as evidence ran under Wonder's harness, whose commands, files and bridge module read `wonder` where `anil`'s read `anil` ([Runtime Reference](../reference/runtime.md)).

Game facts cited here are owned by Game Data (Wonder: `docs/domains/game/reference/game-data.md`), the location facts by World → Item and Gift Events (Wonder: `docs/domains/game/reference/world.md` → Item and Gift Events) and what the randomizer does to them by Randomizer → TMs and Items (Wonder: `docs/domains/game/reference/randomizer.md` → TMs and Items), where each one names how it was verified. The database needs only Python in WSL and the extracted build; a running game is needed only for the live reads and `anil db check`.

## What the Database Does

Harness code looks up any entry by its symbol and gets a typed record carrying its tag. Records exist for species and forms (`CHIKORITA`, `CHARIZARD_1`), moves, abilities, items, types, statuses, trainer types (`LIDER1`) and trainers (`LIDER1:Brock:0`), and a type matchup can be computed for one or two defending types. A record holds what the game holds: Spanish names, base stats, official types, abilities, growth rate, PBS learnsets with tutor and egg moves, evolutions, move power and category, item prices and pockets, the type chart, and each trainer's type, items, lose texts and PBS team. A location says where an item, a gift Pokémon or a mart's stock is found and what the randomizer does to it. It also holds whether the Randomlocke's allow-lists allow the species, move or ability, and its English Pokémon Showdown name. The owner inspects any entry with `anil db <kind> <symbol>`.

What the game loads is not what its files hold. The mod restores the official types of the allowed species-forms and swaps frostbite back to freeze, in memory only ([Randomlocke Design → Applying the Caps](randomlocke-design.md#applying-the-caps)). The cache applies the same changes when it is built, so a lookup answers what a battle will see, and `anil db check` proves the result equal to the live `GameData`, apart from a TM's `@move` that `tm_move_map` explains ([The Check](#the-check)).

## Scope Edges

In: the core battle data, the trainers and the locations listed above, and the live reads of what this run's randomizer has rolled, for its own side, its opponents and its TM marts ([Live Reads](#live-reads)).

Out: damage and threat calculation, the rules engine, megas (the Randomlocke bans them), Shadow Pokémon, contests, battle facilities and cups, the phone, berry plants, ribbons, dungeons and Pokémon metrics: the first two are other harness parts that consume these lookups (Damage Calc Design (Wonder: `docs/subsystems/harness/explanation/damage-calc-design.md`), Rules Engine Design (Wonder: `docs/subsystems/harness/explanation/rules-engine-design.md`)), and the Randomlocke never uses the rest. Wild encounter slots stay in the world cache that navigation reads ([Navigation Design](navigation-design.md)).

The database never makes the game roll anything early: a trainer's team, a map's wild table or a species' learnset is read only once the game has rolled it on its own, and before then only its PBS base data is known. A fact an opponent keeps hidden until it shows it in battle is tagged `opponent_hidden`.

## The Cache

`anil.harness.gamedb` reads `species.dat`, `moves.dat`, `abilities.dat`, `items.dat`, `types.dat`, `trainer_types.dat` and `trainers.dat` with the `rubymarshal` helpers of `anil.harness.world`. Every instance variable of each GameData object is turned into plain JSON (symbols and strings become strings) and stored as the entry's `raw`, beside its position in the file, its name, its allow-list flag and its Showdown name. Statuses come from the build's status script section in the extracted scripts. The overlay is applied before anything is written:

- **Official types:** each species-form in `src/anil/mod/data/types.txt` gets those types as its `@types`. The types the file held are kept in a `retyped` table for every species whose types changed, reorders included (37: 33 retyped and 4 reordered).
- **Freeze:** `FROSTBITE` is replaced by `FROZEN` at its position, keeping its fields, and the `FROZEN` registration the build skips is dropped.
- **Allow-list flags:** species, moves and abilities are marked allowed if `src/anil/mod/data/` lists them. Items, types, statuses and trainers have no allow-list.
- **Names:** the Spanish name is the game's own `@real_name`. The Showdown name comes from `src/anil/mod/data/showdown.txt`, and is `None` where the file has none.

Trainers need no overlay: the mod leaves their loaded data as the files hold it (Game Data → Data the Mod Changes (Wonder: `docs/domains/game/reference/game-data.md` → Data the Mod Changes)). A trainer's key is its `[trainer type, name, version]` triple, stored joined by colons.

The typed lookups (`species`, `move`, `ability`, `item`, `game_type`, `status`, `trainer_type`, `trainer`, `matchup`) build their records from `raw`, so a field added later needs no rebuild. `family` gives a species' evolutionary family as the game's `get_family_species` does: from the base form down the prevolutions to the root, then every evolution from it, which tells whether a wild Pokémon is a dupe of an owned species. The matchup follows the game's own rule over the defending types' lists (Game Data → Types and Matchups (Wonder: `docs/domains/game/reference/game-data.md` → Types and Matchups)).

## Locations

The locations are mined from the world cache's `scripts` table ([Navigation Design → Static World](navigation-design.md#static-world)), not by reading the maps again, so building the database opens the world cache, building it when it is stale. Each page's script commands are joined into blocks as the game runs them (a 355 command with the 655 lines after it, or one script branch), Ruby comment lines are dropped, and every call of these is a location:

| Call | Kind | What it names |
|------|------|---------------|
| `pbItemBall`, `pbReceiveItem` | `item_ball` on a page shown as an item ball (`objeto`, `megapiedra`) or as a tile; `hidden_item` on a page with no graphic and the action-button trigger; `item_gift` on any other page (a person, a touch or autorun event) | The item, or the choices of a `[...].sample`, and the quantity |
| `$bag.add` | as above | The item and quantity, never randomized |
| `pbAddPokemon`, `pbAddPokemonSilent`, `pbAddToParty`, `pbAddForeignPokemon` | `gift_pokemon` | The species and level, from the call or from a `Pokemon.new(:SPECIES, level)` assigned on the same page to the variable it passes |
| `pbPokemonMart` with a list | `mart` | The stock, in order |
| `RandomizedChallenge.tm_mart` | `tm_mart` | How many TMs it rolls, with the page's fixed `pbPokemonMart` list (the stock if the randomizer were off), which is not listed again as a mart |

Each location keeps its map, event, position, page and command, the call's text, and `random`, what the randomizer does to it when it happens:

- `none`: the location gives what it names. An item the plugin never randomizes (a key item, an HM, a mega stone, or one in its `UNRANDOMIZABLE_ITEMS`), a call passing `false` as its fourth argument, `$bag.add`, a fixed mart, or a gift species in `UNRANDOMIZABLE_POKEMON`.
- `item`: the item is replaced by a random one at pickup.
- `tm_move`: a TM or TR keeps its item but is given a random move, or is replaced by a random item when the bag already holds it.
- `species`: a `pbAddPokemon` or `pbAddPokemonSilent` of a named species, which the plugin makes through `Pokemon.new` with randomizing resumed, so the species is replaced.
- `stock`: a TM mart's stock is rolled on its first visit and kept.
- `run_time`: decided by state the static data cannot see: a species or item held in a variable, a `.sample` whose choices the randomizer treats differently, or a `Pokemon.new` made outside the plugin's wrapper, which keeps its species while a wild draw has paused randomizing.

The two `UNRANDOMIZABLE_` lists are read from the randomizer plugin's `000_Config.rb` in the extracted build. Every location is tagged `world`. The Battle Point shops (`pbBattlePointShop`) and the BW key-item scene (`pbGetKeyItem`, which only shows an item that a `pbReceiveItem` beside it gives) are not locations.

## Live Reads

`anil.harness.random` reads what this run's randomizer has rolled from the running game, with one bridge `read` of instance variables: the ability table (`$randomized_data`), the learnsets (`$PokemonGlobal@random_moves`), the TM compatibility (`@tm_compatibility_random`), the TM moves (`@tm_move_map`), the starters (variables 803–805), the Pokédex owned flags (`$player.pokedex@owned`), the wild tables (`@random_encounter_table`), the remembered trainer teams (`@random_trainer_teams`) and the TM marts' stock (`@tm_mart`). Layouts as read are in Randomizer → Reading the Caches (Wonder: `docs/domains/game/reference/randomizer.md` → Reading the Caches). Nothing is cached on our side: the data belongs to the save, and one read is cheap.

The read calls no method of the game's objects beyond `$player.pokedex` and `$game_variables[v]`, because the getters roll: `GameData::Species#abilities` rolls the whole ability table when it is missing, `Pokemon#getMoveList` a learnset, `compatible_with_move?` a compatibility answer, and `Pokemon#ability_id` sets `@ability`. So a starter's or a trainer Pokémon's ability is worked out in Python from its ivars and the table, as `ability_id` does it for a Pokémon whose `@ability` is not set yet, with the species' real abilities for Shedinja and `MEWTWO_5` (Randomizer → Reading the Caches (Wonder: `docs/domains/game/reference/randomizer.md` → Reading the Caches)). Learnsets are keyed by species-form (`ZIGZAGOON_1`), since the owner's configuration rolls one per form. Shedinja's and `MEWTWO_5`'s ability table entries are left out, because the game uses their real abilities (Randomizer → Abilities (Wonder: `docs/domains/game/reference/randomizer.md` → Abilities)). A cache the game has not made yet reads as not rolled (`None`), and a species missing from a cache as not rolled for that species.

Each record carries its tag:

- An ability table entry, a learnset and a species' TM compatibility are `own` when the Pokédex marks the base species of the entry owned, else `unowned_random`. Ability table entries and learnsets are keyed by species-form (`CHARIZARD_1`), and the owned flag by base species, so the form's base species comes from the cache's species entries.
- A TM's rolled move is `world`.
- A starter's species is `world`. Its moves and ability are tagged `own` or `unowned_random` by its species.
- A wild table is read per map and encounter type, its slots as stored: each slot's species is `opponent_species`, its chance and level range `world`. A map or type missing from the cache is not rolled; the cache holds a map's table from its first wild draw (Randomizer → Wild Encounters (Wonder: `docs/domains/game/reference/randomizer.md` → Wild Encounters)).
- A remembered trainer team is keyed by its trainer's id joined as the static trainers are (`LIDER1:Brock:0`), and the trainer is `world`. Each Pokémon's species-form is `opponent_species`; its level, moves, ability, held item, nature and IVs are `opponent_hidden`. A trainer missing from the cache has not been loaded yet.
- A TM mart is keyed by its `tm_mart` id (1, 2, 3, the first argument of the event's call, Randomizer → TMs and Items (Wonder: `docs/domains/game/reference/randomizer.md` → TMs and Items)). Its stock is `world`, each TM with the move `@tm_move_map` gives it now.

## The Check

`anil db check` attaches to the running game and reads, for each kind, the order of the `DATA` hash's keys and every object's instance variables (in batches of 200 entries, by eval), with a `GameData::Move` held in a variable read as its id. It compares them with the cache's `raw`, then compares all 361 single-type matchups with `Effectiveness.calculate`. It prints `pass` or `FAIL` with two lines per kind (the ids in order, and every entry equal) and one for the matchups, names the first five differing entries on each line with the fields that differ, notes the matchups against Fairy and Dragon, writes a `check` entry through `note`, and exits 1 on a failure. Comparing every instance variable, not chosen fields, means a plugin change the overlay misses shows up as a difference.

Items are the one kind the run itself changes: rolling a TM rewrites that item's `@move` in the running game, while a boot or restore loads every `@move` from the file (Game Data → Data the Mod Changes (Wonder: `docs/domains/game/reference/game-data.md` → Data the Mod Changes), [Runtime Design → Snapshots](runtime-design.md#snapshots)). So the check also reads `$PokemonGlobal.tm_move_map`, and a TM item passes when its `@move` equals the cached data-file move or, for a TM in the map, the map's rolled move, with every other field equal; anything else fails. After the items line it names the rolled TMs it accepted, on two lines: those whose `@move` still held the data-file move and those whose `@move` held the rolled one, each with the map's move. Session `20261003-112058`, booted into `tmc-a` (save `tmcheck-1`, a copy of `caps3-3`), passed with 887 of 887 items and named the 60 TMs of the map with the data-file move and none with the rolled one. After Ruta 1's TM75 ball (map 3 event 9), picked up with `anil interact` after an eval moved the player to (6, 39) facing it, rolled TM75 to Alud (`AVALANCHE`), it passed again and named TM75 `AVALANCHE` with the rolled move. After an eval set TM01's `@move` to `:SPLASH`, it failed on TM01 alone (`@move cached 'BLIZZARD', live 'SPLASH'`). The items line was then relabelled to name the rolled moves it accepts, and session `20261003-112219`, booted into `tmc-a` the same way, passed with 887 of 887 items under the new label.

## Commands

- `anil db` opens the cache (building it when it is missing or stale; `--rebuild` forces it) and prints its path, stamp and counts.
- `anil db species|move|ability|item|type|status|trainer-type <SYMBOL>` prints one record, one field per line, ending with its tag. The symbol matches without regard to case.
- `anil db trainer <TYPE> [<NAME> [<VERSION>]]` prints one trainer with its trainer type and each PBS team member; when more than one trainer matches it names them and stops.
- `anil db matchup <ATTACK> <DEFEND> [<DEFEND>]` prints the multiplier.
- `anil db locations [<MAP>]` prints every location, or one map's, grouped by map: kind, what it names, `random`, event, position, page and command, and the tag. `anil db` prints the counts of each kind.
- `anil db random [<SPECIES>]` reads the running game. Without a species it prints the owned species, how many species-forms the ability table and the learnsets hold and how many species the TM compatibility holds, or that one is not rolled, every rolled TM move and the three starters, then every wild table with its slots, every remembered trainer team with each Pokémon's level, moves, ability, item, nature and IVs, and every TM mart's stock, each with its tags. With one it prints that species-form's ability table entry and learnset and its base species' TM compatibility, each with its tag, or says which is not rolled, and that the table is not used for Shedinja and `MEWTWO_5`.
- `anil db check` runs the check against `anil run`'s game.

## Decisions

- **Four data sets: the core battle data, the trainers, the item and gift locations, and the live reads of the run's rolled data** ([Scope Edges](#scope-edges)), all four of the sets proposed. _(owner, 2026-10-03)_
- **Static data from the compiled `.dat` files with the mod's changes applied in Python**, rather than dumped from live `GameData` (every rebuild would need a game boot) or parsed from PBS text (the game loads the `.dat` files, and PBS can drift from them). The check catches any plugin change the overlay misses. _(settled 2026-10-03, owner)_
- **Its own stamped SQLite cache,** `gamedb/<build>.sqlite` in the data root, not tables in `world.sqlite`, where navigation and the database would rebuild each other. The stamp is `<reader version>:<build>:<scripts hash>:world<world reader version>:randomlocke<mod version>:<hash of the mod's data files>`. A build is written beside the cache and renamed into place, as the world cache is. The cache is derived data, so deleting it is safe. _(settled 2026-10-03, owner; stamp layout 2026-10-03, the world reader version added with the locations 2026-10-03)_
- **Symbols are the keys:** `RARECANDY`, `CHIKORITA`, `CHIKORITA_1` for forms, as the game, `$bag` and the menu verbs use them. Spanish names come from the game's data, and English Showdown names from `showdown.txt`. _(settled 2026-10-03, owner)_
- **Knowledge tags:** five, one per fact. They are `world` (data as such: base stats, official types, moves, abilities, items, the type chart, locations, marts and wild slots), `opponent_species` (a rolled trainer team's or wild table's species), `opponent_hidden` (an opponent's moves, ability, item, level, nature and IVs), `own` (the rolled learnset, ability-table entry and TM compatibility of a species the Pokédex marks owned), and `unowned_random` (the same for a species never owned). "Owned" is the game's own Pokédex flag, which needs no record of ours. Every record the static lookups return is `world`, except the trainer parts below. _(settled 2026-10-03, owner)_ The `Tag` type also holds a sixth, `revealed`, for what an opponent shows in battle, which no record here carries. _(owner, 2026-10-03)_
- **A trainer and its type are `world`; its own items and each PBS team member are `opponent_hidden`.** A PBS member's level is the level the opponent loads with when under the cap, and its held-item slot decides whether the opponent holds an item (Randomizer → Trainers (Wonder: `docs/domains/game/reference/randomizer.md` → Trainers)), so the member carries the level and item facts the tag covers. Its PBS species is not `opponent_species`, which names a rolled team's species, and every PBS species tested was replaced by the roll; it stays with the member's tag. The trainer's own items are an opponent's, which stay hidden. **Decided 2026-10-03, forced by evidence:** the settled tags and the randomizer facts force `opponent_hidden` for the members' levels and items and the trainer's items. **The PBS species is `opponent_hidden` too (owner, 2026-10-03):** it is the team before the roll and tells nothing true about the opponent, so showing it would only invite planning around Pokémon the rolled team does not have; the harness still caches and checks it.
- **A typed Python API for harness code, and `anil db` for the owner,** every result carrying its tag. _(settled 2026-10-03, owner)_
- **Never rolling early:** the live reads only read the randomizer's caches, so the game's RNG is left untouched and a fact exists for the database only once the game has rolled it. _(settled 2026-10-03, owner)_
- **The live reads take the randomizer's caches, the starters and the Pokédex owned flags straight from the running game, and nothing of them is cached on our side** ([Live Reads](#live-reads)). Why: the data belongs to the save and one read is cheap, and keeping per-save data out of the per-build cache means the cache never goes stale with a save. _(owner, 2026-10-03)_
- **One `entries` table holding each object's whole instance-variable set as JSON,** not a column per field. The check can then compare every variable with the live object, and the typed records read fields from it without a schema change. _(settled 2026-10-03)_
- **Statuses read from the build's `*_Status.rb` script section in `game/extracted/<build>/scripts/`,** because no data file holds them. The `GameData::Status.register` blocks are parsed for `:id`, `:name`, `:animation` and `:icon_position`, with the class's own defaults. The freeze overlay then keeps one `FROZEN` at `FROSTBITE`'s place with its fields. **Decided 2026-10-03, forced by evidence:** freeze is part of the overlay the scope settled, and the six statuses exist only in that script (Game Data → Statuses (Wonder: `docs/domains/game/reference/game-data.md` → Statuses)).
- **Locations are rows of their own `locations` table, one per call,** keyed by map, event, page, first command of the script block and the call's place in it, with the kind, the items as JSON, quantity, species, level, `random`, the map's name, the event's position and the call's text. They are built with the rest of the cache, which therefore depends on the world cache: the stamp carries the world reader version, so a change to the world reader rebuilds the database too. _(build choice, 2026-10-03)_
- **The kind of an item location comes from its page's graphic and trigger,** because Añil's item balls, hidden items and NPC gifts all call `pbItemBall` or `pbReceiveItem` and its event names (`EV017`) say nothing (World → Item and Gift Events (Wonder: `docs/domains/game/reference/world.md` → Item and Gift Events)). _(build choice, 2026-10-03)_
- **`random` says what the randomizer does, in six values, not a yes or no,** because a TM keeps its item and changes its move, and some gifts depend on run-time state. The rules mirror the plugin's `determine_random_item`, `unrandomizable_item?` and `Pokemon#initialize` (Randomizer → TMs and Items (Wonder: `docs/domains/game/reference/randomizer.md` → TMs and Items)), with the two unrandomizable lists read from the plugin's config rather than copied. _(build choice, 2026-10-03)_
- **A TM's rolled move is `world`, and so is a starter's species; a starter's moves and ability follow its species' owned tag.** The settled tags name per-species data only, and a TM's move is per item: the bag and the mart show it, it is already the item's own `@move` once rolled (Game Data → Data the Mod Changes (Wonder: `docs/domains/game/reference/game-data.md` → Data the Mod Changes)), and item records are `world`. The lab's Poké Balls name the three starters before one is taken (Runtime → Randomlocke Mod (Wonder: `docs/domains/game/reference/runtime.md` → Randomlocke Mod)), so their species are seen, but their moves and abilities come from their species' learnset and ability table entry, which `own` and `unowned_random` cover. **Decided 2026-10-03, forced by evidence:** the settled tags and these game facts leave no other fit.
- **The live reads read instance variables with the bridge's `read` and work a starter's ability out in Python,** never calling a getter of the rolled data, since the getters roll or write ([Live Reads](#live-reads)). The tag of a species-form entry uses its base species, as the game's `owned?` does (`S/294_Player_Pokedex.rb:165-168`). _(build choice, 2026-10-03)_
- **A wild slot's chance and levels, a remembered trainer and a TM mart's stock are `world`; an opponent's species is `opponent_species` and the rest of it `opponent_hidden`.** The settled tags name wild slots and marts `world`, a rolled team's or wild table's species `opponent_species`, and an opponent's moves, ability, item, level, nature and IVs `opponent_hidden`; a trainer and a TM's move are already `world` above. **Decided 2026-10-03, forced by evidence:** the settled tags leave no other fit.
- **A trainer Pokémon's ability is worked out in Python as a starter's is,** since a team is stored as it is loaded, before anything calls `ability_id` (`P/Random Pokemon & Moves + Randomizer EX (Abilities)/006_Trainers.rb:55-57`), and battles fight a copy (Randomizer → Trainers (Wonder: `docs/domains/game/reference/randomizer.md` → Trainers), "Remembered teams"). It matched `ability_id` for every remembered trainer Pokémon of `tmc-a` (Randomizer → Reading the Caches (Wonder: `docs/domains/game/reference/randomizer.md` → Reading the Caches)). _(build choice, 2026-10-03)_
- **The check lives in `anil.harness.check` and is run by `anil db check`, not `anil check`.** It needs only an attached client and no driver, and it runs at any point of a session, the title screen included. _(settled 2026-10-03)_
- **A rolled TM is checked against `tm_move_map`, not skipped:** a TM item's `@move` passes when it equals the cached data-file move, or, for a TM that `$PokemonGlobal.tm_move_map` lists, that map's rolled move; anything else fails, and the output names each rolled TM accepted. Every other field is compared exactly. Why: a roll rewrites `@move` in the running game while a boot and load of the save holds the data-file move (Game Data → Data the Mod Changes (Wonder: `docs/domains/game/reference/game-data.md` → Data the Mod Changes)), so the check passes in any session only when the run's own rolls explain every difference, and still fails on a wrong cache or an unexplained move. _(owner, 2026-10-03)_
