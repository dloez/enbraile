# Runtime Design

How the `anil` tooling in `pkmn/games/anil/` gets Pokémon Añil, installs it with the group's Randomlocke mod and, with the bridge, runs, reads and drives it: the game files, the build table, deploy and its layers, the stamp, the injected Ruby bridge and its protocol, launch, saves, the clock, typed state and context, events, input and control, speed, lockstep, snapshots, session records and replay, and the investigation commands. It is copied from Wonder's runtime (Wonder: `docs/subsystems/harness/explanation/runtime-design.md`), where it was built and checked against the game, without Wonder's agent, its run records and its control panel ([Left Out](#left-out)). The mod itself is in [Randomlocke Design](randomlocke-design.md); facts verified on the game are in [Runtime Reference](../reference/runtime.md); how to install is in [How to Install the Game](../how-to/install-the-game.md) and how to run the harness in [How to Run the Harness](../how-to/run-the-harness.md).

The code is `src/anil/install/` (`builds.py`, `game_files.py`, `deploy.py`, `windows.py`), the mod in `src/anil/mod/`, the bridge in `src/anil/bridge/` (its Ruby in `ruby/`, and the Python side of the protocol in `protocol.py`, `client.py` and `sources.py`), the harness in `src/anil/harness/` (`lock`, `launch`, `session_log`, `investigate`, `context`, `state`, `changes`, `steps`, `drive`, `snapshot`, `replay`, `showdown`; the layers built on it, `world`, `navigate`, `progression`, `dialog`, `menu`, `storage`, `gamedb`, `random` and the game database's `check`, have their own designs: [Navigation Design](navigation-design.md), [Dialog Design](dialog-design.md), [Menu Design](menu-design.md) and [Game Database Design](game-database-design.md)), the settings in `src/anil/settings.py`, and the `anil` command in `src/anil/cli.py` with its state view in `src/anil/state_text.py`. Script references are to Añil's `game/extracted/es-v4.14/`: `S/` for a `Scripts.rxdata` section and `P/` for a plugin.

## What the Runtime Does

From WSL, `uv run anil install` fetches and verifies the game into `pkmn/games/anil/game/`, then deploys it with the mod to a Windows working copy, so a new game started there is the Randomlocke. `anil install --harness` adds the bridge, and `anil run` then launches the game held at its first tick until a driver attaches or `anil control take` hands it over. Against the running game, the harness reads typed game state and the current "waiting-for" context, drives the game in lockstep at any speed preset, takes and restores seeded snapshots, and records every session so `anil replay` reproduces it exactly. Investigation commands (eval, call stack, screenshot, RNG counter, the Showdown export) work against a live session. Everything built on it (navigation, dialogs, menus, the game database's live reads, battles, the rules guard, and later `anil check`) goes through this layer.

## Environment

WSL2 with Windows interop: `Game.exe`, `tasklist`, `taskkill`, `cmd.exe` to resolve `%USERPROFILE%`, `wslpath` to convert paths, and `powershell.exe` to start the game without activating it, to list processes after a failed launch, and to find, place, hide and show the game window. Networking mode is `mirrored` (Windows is the server and WSL the client on `127.0.0.1`), a Windows desktop session is needed (hidden windows still run), `$WSL_DISTRO_NAME` builds the `\\wsl.localhost` paths, and the bridge port sits outside the Linux ephemeral range. The working copy sits on the Windows filesystem, because `Game.exe` runs there and reading about 830 MB of assets across the WSL boundary is slow and untested. Only the game runs on Windows; nothing is installed there.

## Re-running and Rollback

Fetch reuses a base or archive whose hashes match. Deploy copies the base only when the build changes, the last copy did not finish, or `--full` is passed, and writes only the overlay files whose content changed, so a second `anil install` copies nothing. Deleting the working copy and installing again resets the game side; removing the data root resets the harness's saves, snapshots and sessions; players' own saves live in Añil's save folder, `%APPDATA%\Pokemon Anil`, which neither install nor the harness touches. A stale lock from a killed harness is detected by checking whether the recorded PID is alive. Code is reverted through git.

## Observability

Install prints what it did: which source fetch used, what was copied or extracted, each overlay file written, and the stamp. `anil_stamp.json` in the working copy records what is deployed ([Deploy](#deploy)). Under the harness, the bridge logs to `sessions/<id>/bridge.log` through the `\\wsl.localhost` path: the handshake, requests (with each eval's source and result), the hooks it installs, and every exception. A bridge exception never crashes the game; it becomes an error reply and a log line. The harness logs with stdlib `logging` to `sessions/<id>/harness.log` and the console, and records unknown contexts with their call stack in `sessions/<id>/unknown_contexts.jsonl` ([Context](#context)).

## Decisions

### Project Layout

- **One uv project, `anil`,** in `pkmn/games/anil/`, Python 3.12, with its code in `src/anil/` (`install/`, `mod/`, `bridge/`, `harness/`, `cli.py`, `state_text.py`, `settings.py`) and the `anil` command a click group (`anil.cli:anil`). ruff and ty are its dev group, with Wonder's ruff configuration (line length 100, Python 3.12). Why: nothing outside Añil reuses the parts, so Wonder's workspace members became one project. _(owner, 2026-10-21)_
- **The bridge and the harness keep Wonder's module split inside the project:** `anil.bridge` holds the Ruby sources as package data and the Python side of the protocol and knows nothing about the harness; `anil.harness` holds launch, sessions, state, driving, snapshots and replay. Wonder's `harness.settings` is merged into `anil.settings`, the one settings class, and Wonder's `cli/state_text.py` is `anil/state_text.py`, since the CLI is one module. Pillow joins the dependencies for the screenshot conversion. _(2026-10-21, build choice)_
- **The layers on the runtime come over as Wonder built them, with two seams moved:** `ID_SEPARATOR` lives in `anil.harness.state`, which `gamedb` and `random` import, where Wonder's `state` imported it from `gamedb`; and `anil.harness.check` holds only the game database check with the result plumbing it needs (`CheckResult`, `record`, `report_result`, `LIVE_ERRORS`), into which `anil check` will bring the rest of Wonder's `check.py`. Why: the state reader came over before the game database, and `anil db check` came with the database while the mod's checks did not. _(2026-10-21, build choice)_
- **The Open Sheet export scripts stay outside the project and its gate:** `export_data.py` and `generate_export_data.py` keep their paths and their own inline script metadata, and the gate's ruff and ty leave them out. Why: players run `export_data.py` from its raw GitHub URL, and neither script was written to the project's gate. _(2026-10-21, build choice)_
- **Names follow the discovery's renames:** `WONDER_*` settings become `ANIL_*`, the stamp is `anil_stamp.json`, the launch file `anil_launch.json`, the bridge's version file `anil_version.rb`, the PowerShell type `[Anil.Win]`, the bridge module `AnilBridge` in `anil_*.rb` files (with `AnilJSON`, `AnilVersion` and `AnilRestoreScene`), its aliases `anil_bridge_*`, the instance variables it sets on game objects `@anil_*`, and the client names `anil …`. In-game messages naming Wonder are reworded ([Saves](#saves)). _(owner, 2026-10-21)_
- **Wonder Guard, Wonder Skin and Wonder Room keep their names** in the mod's data (`abilities.txt`, `moves.txt`, `showdown.txt`), in the bridge's list of shown field effects (`WonderRoom`, `anil_events.rb`) and in the damage calc (`WONDERGUARD`, `WONDERSKIN`, `WONDER_SKIN_ACCURACY` and `WonderRoom`, `calc.py`), so `grep -rn -i wonder pkmn/games/anil/src` prints those lines and nothing else. Why: they are the game's and Showdown's names for two abilities and a move, which the allow-lists, the Showdown export, the game's `PBEffects` and the calc's ability names and unmodelled field effects must match; renaming them would break all of them. _(2026-10-21, forced by evidence)_

### Game Files

- **The game lives in a gitignored `game/` folder beside `src/`:** `game/archives/<build>.zip` (the archive, kept), `game/base/<build>/` (the pristine unpack) and `game/extracted/<build>/` (the game's scripts, read-only, for investigation: `scripts/` for `Scripts.rxdata` and `plugins/` for `PluginScripts.rxdata`). `game/` is found from the code's own location, not the working directory. It holds the game as downloaded, the input to install, not its output. _(owner, 2026-10-21; from Wonder, settled 2026-09-30)_
- **Fetch takes the first source that holds:** `game/base/<build>/` whose `Scripts.rxdata` and `PluginScripts.rxdata` match their pinned hashes; else `game/archives/<build>.zip` whose SHA-256 matches, unpacked; else a copy of the build's archive from the owner's Windows downloads into `game/archives/`, verified and unpacked. An archive that fails its hash is rejected and deleted. Extraction runs whenever `base/` is created, and also when `base/` is valid but either half of `extracted/` is missing. `--no-cache` skips the local copies. A zip placed in `game/archives/` by hand is picked up the same way. _(from Wonder, settled 2026-09-30, rewritten for Añil 2026-10-02)_
- **Nothing is half-written:** the archive is copied into `<build>.zip.part`, hashed and renamed only once verified. Unpacking strips the archive's single top-level folder into a staging folder beside `base/<build>/`, checks both script hashes there and only then replaces `base/<build>/`. Extraction writes into a staging folder swapped in when complete: `scripts/NNN_Name.rb` per section, and `plugins/<plugin>/<file>` per plugin file with the plugin's own subfolders kept, each half with an `_index.txt` (position, code length, name) and every file read-only. Plugin and file names keep their own spelling, with only characters a path can't hold replaced by `_`. Why: a half-written archive, base or extraction must never be taken for a good one. _(from Wonder, settled 2026-09-30)_

### Builds

- **Spanish Añil v4.14, keyed by build:** the build table `anil.install.builds.BUILDS` holds, per build, the name (`es-v4.14`), the archive's path under `%USERPROFILE%` (`Downloads\POKEMON ANIL v4.14.zip`, resolved through interop, since Añil has no download link to fetch from), the archive SHA-256, the pristine `Scripts.rxdata` and `PluginScripts.rxdata` SHA-256s and the language. `--build` (default `es-v4.14`) picks one. Why: facts verified on one build don't carry to another. _(from Wonder, settled 2026-10-02)_

### Data Root

- **Layout under `~/.local/share/enbraile/anil/`:** `saves/<name>/` ([Saves](#saves)), `snapshots/<name>/` ([Snapshots](#snapshots)), `sessions/<id>/` ([Session Records and Replay](#session-records-and-replay)), the derived caches `world/<build>.sqlite` ([Navigation Design → World Cache](navigation-design.md#world-cache)) and `gamedb/<build>.sqlite` ([Game Database Design → Decisions](game-database-design.md#decisions)), and `game.lock`, the lock for the one running game. _(owner, 2026-10-21; from Wonder, settled 2026-09-30; the caches 2026-10-21)_
- **Config through pydantic-settings, no secrets:** `ANIL_DATA`, the data root; `ANIL_GAME_DIR`, the Windows working copy, default `%USERPROFILE%\Documents\Pokemon\Pokemon Anil-enbraile`, resolved through interop, so it sits beside Wonder's own working copies and the owner's playable copy without touching them; `ANIL_BRIDGE_PORT`, default 24731, so Wonder's games (24711, 24721) can run alongside. _(owner, 2026-10-21)_

### Deploy

- **Deploy builds the working copy from `game/base/<build>/` and the overlay, with no staging copy:** copy the base into the working copy only when its stamp is missing, names another build or records an unfinished copy, or with `--full`; write the overlay; then write the stamp. Why: the 830 MB base crosses to Windows once per build while a mod or bridge change deploys in under a second, and a broken working copy can be deleted or redeployed with `--full`. _(from Wonder, settled 2026-09-30)_
- **Only changed overlay files are written:** each overlay file is compared with the one in the working copy and written only when its bytes differ, and the command says how many were written. Why: the acceptance for install is that a second run copies nothing; Wonder rewrote the whole overlay on every deploy. _(2026-10-21, build choice)_
- **The overlay is layered, the mod then, with `--harness`, the bridge:** each layer brings its files and its preload list, written over the base in order; a layer that would rewrite a file of an earlier layer, or `mkxp.json`, is refused; base files are overwritten freely. The `randomlocke` layer is the mod ([Randomlocke Design](randomlocke-design.md)): its generated `randomlocke_version.rb`, `randomlocke_allowlists.rb` and `randomlocke_showdown_names.rb`, then `randomlocke.rb` and `showdown.rb`. The `bridge` layer is `anil_version.rb`, then `anil_json.rb`, `anil_read.rb`, `anil_context.rb`, `anil_drive.rb`, `anil_speed.rb`, `anil_audio.rb`, `anil_record.rb`, `anil_events.rb`, `anil_snapshot.rb`, `anil_rules.rb` and `anil_bridge.rb`. A plain `anil install` deploys the mod alone, as players get it; `anil install --harness` deploys both, so every harness run plays the Randomlocke with the bridge on top. Bridge files a harness deploy left behind stay in the working copy after a plain install, but `mkxp.json` no longer preloads them. _(from Wonder, settled 2026-10-02; the bridge behind `--harness`, owner, 2026-10-21)_
- **`mkxp.json`** is the shipped one parsed after its `//` comment lines and trailing commas are dropped, and written back as plain JSON with every shipped key kept and the layers' preload files appended to any `preloadScript` list it has (Añil's has none). The shipped `preload.rb` is never listed, because it raises when preloaded ([Runtime Reference → Player and Engine](../reference/runtime.md#player-and-engine)). _(from Wonder, settled 2026-10-02)_
- **Frame sync is off with the bridge and as shipped without it:** `anil install --harness` sets `vsync` and `syncToRefreshrate` to false, because the bridge's speed and lockstep need the game's own frame rate, not the display's refresh, to pace rendering ([Runtime Reference → Frame Rate](../reference/runtime.md#frame-rate)); a mod-only install keeps both as shipped, as Wonder's players zip did. _(from Wonder, settled 2026-10-02; frame sync with the bridge only, owner, 2026-10-21)_
- **Stamp:** `anil_stamp.json` in the working copy holds the build, whether the base copy finished, the commit (`+dirty` when `pkmn/games/anil/` has uncommitted changes), the bridge hash (null for a mod-only install), the deploy time and a SHA-256 per overlay file. It is written as unfinished before a base copy starts, so an interrupted copy is redone on the next install. The dirty check covers `pkmn/games/anil/` only, since changes elsewhere in the repository never reach the working copy. _(from Wonder, settled 2026-09-30; the dirty check's scope 2026-10-21, build choice)_
- **Bridge hash:** SHA-256 over each bridge Ruby file's name and hash in preload order, leaving out the generated `anil_version.rb`. Deploy writes it, with the build, into `anil_version.rb`, preloaded first, so the handshake reports the hash of the bridge the game actually loaded. `anil run` refuses when the stamp has no bridge or its hash differs from the repo's (install with `--harness` first), and kills the game and refuses when the handshake's differs from the stamp's. _(from Wonder, settled 2026-09-30)_
- **Base copy:** a base copy removes the working copy and copies the base afresh. A folder that exists, is not empty and has no stamp is refused and left alone, so a mistaken `ANIL_GAME_DIR` can never wipe someone's copy of the game. _(from Wonder, settled 2026-09-30)_
- **Install is refused while a game runs:** deploy reads the game lock first and refuses while `anil run`'s game is live, naming its session. _(from Wonder, settled 2026-09-30)_

### Game Modifications

- **Only preloaded Ruby, never an edited `Scripts.rxdata`:** every change is a Ruby file in `src/anil/mod/` or `src/anil/bridge/ruby/`, loaded by `mkxp.json`'s `preloadScript` before `Scripts.rxdata`, patching methods at runtime (the save folder, the clock, `Input`, payload wrappers). If a change ever can't be made at runtime, a patch file applied to the extracted scripts at deploy is added then, not before. Why: every change lives in the repo, and preload patches compose with the game without editing it. _(from Wonder, settled 2026-09-30)_
- **The bridge carries no updater or Discord hook of its own:** what [Randomlocke Design → Package Behaviour](randomlocke-design.md#package-behaviour) decides for every copy of the game holds under the harness too, because the mod is layered under the bridge. _(from Wonder, settled 2026-10-02)_

### Saves

- **In-game saves go straight to the data root:** the bridge overrides `System.data_directory` to return `saves/<name>/` through the `\\wsl.localhost\<distro>\...` path (with a trailing backslash, as the native value has), named by `anil run --save NAME`. Nothing is copied back and forth, and `%APPDATA%\Pokemon Anil\` is never written. Why: harness games don't clobber each other or a player's saves. `SaveData::FILE_PATH` (`S/029_SaveData.rb:8`) and Multi Save's `SaveData::SAVE_DIR` (`P/Multi Save/Multi Save.rb:54`) are constants built from `System.data_directory` while the scripts load, and every in-game save goes through Multi Save's `Game.save` into `SAVE_DIR`, so the override must be in place before `Scripts.rxdata` loads: the bridge installs it in `AnilBridge.start`, at the end of the preload, and only when the launch file names a save folder (otherwise saves are refused, next bullet). mkxp-z still creates an empty `%APPDATA%\Pokemon Anil\` at startup, before any preload runs, and nothing is written into it ([Runtime Reference → Bridge Start](../reference/runtime.md#bridge-start)). _(from Wonder, settled 2026-09-30, moved to `System.data_directory` 2026-10-02)_
- **A bridge game with no launch file refuses to save:** when the bridge is deployed but `anil_launch.json` is missing or names no save folder, as with the working copy started by hand from Windows after a harness install, an in-game save fails with "Esta copia de Añil solo guarda la partida bajo anil run. No se ha guardado nada." through `pbMessage`, answering false, so the save screen adds its own "El guardado ha fallado.", and `SaveData.save_to_file` raises `IOError`. Why: with no launch file the game has no path to save to, so refusing cannot write anywhere it shouldn't and shows the mistake at once. Code: `refuse_saves`, `refuse_save` and `install_save_refusal` in `anil_bridge.rb`; verified on Wonder's bridge in [Runtime Reference → Bridge Start](../reference/runtime.md#bridge-start). _(from Wonder, settled 2026-10-02; the message reworded for Añil 2026-10-21)_
- **A refused game's data directory is its own folder (forced by evidence):** with saves refused, `System.data_directory` is pinned to the game's folder (`Dir.pwd` with backslashes and a trailing one), so `SaveData::FILE_PATH` and Multi Save's `SAVE_DIR` are built from it. Why: refusing `Game.save` alone leaves the native `%APPDATA%\Pokemon Anil\` in place, and other code writes there outside a save: Multi Save's emergency backup, the load screen's conversion of an old save, the team photos plugin, the debug terminal, `errorlog.txt`, the F8 screenshot, the randomizer's `tm_compatibility*.dat` and Trade Expert's file, all through `RTP.getSaveFileName` or `System.data_directory`; the game would also list and load a player's saves from there. The working copy needs no path baked into it and holds no saves, so the load screen offers none. _(from Wonder, 2026-10-02, forced by evidence)_
- **A hand start never reads an old launch file:** `anil run` removes `anil_launch.json` from the working copy once the handshake is in, or once a failed launch has been cleaned up, so the working copy started by hand after a harness install finds none: it refuses saves, keeps its sound and is not held. Why: the bridge reads the file only at preload, and every launch is held until it is handed over ([Launch](#launch)), so a hand start that read the last run's file would stop at its first tick, listening for a driver; Wonder left the file in place, and a hand start then saved into that run's `saves/<name>/`. Verified by `anil run` leaving no `anil_launch.json` behind; the hand start itself was reasoned from `AnilBridge.start`, which raises before setting the hold when the file is missing. _(2026-10-21, build choice)_

### Clock

- **A pinned clock by default:** the bridge pins `pbGetTimeNow` (`S/247_Overworld_Time.rb:4`) to 2026-01-01 12:00; `--clock <time>` picks another pinned time and `--clock real` uses the wall clock. Why: encounters, day and night and some events read the clock, so seeded restores only reproduce with it pinned, and midday keeps games in daytime. _(from Wonder, settled 2026-09-30)_
- **CLI:** `--save NAME` takes letters, digits, `-` and `_`, and defaults to `main`; `anil run` creates `saves/<name>/` before launch. `--clock` takes `real` or a local time in any form `datetime.fromisoformat` reads, such as `2026-01-01T12:00`; a time zone is refused and fractions of a second are dropped. `--seed` takes 0 to 2³²−1; without it the harness picks one at random, so every session still has a recorded boot seed. _(from Wonder, settled 2026-09-30; the default save `main` 2026-10-21, build choice, so `anil run` needs no options)_
- **Launch file fields:** `save` (the name), `save_dir` (a `\\wsl.localhost` path), `clock` (`[year, month, day, hour, minute, second]` or `"real"`) and `seed`; the bridge logs them at start. _(from Wonder, settled 2026-09-30)_
- **Overrides of game methods are installed as hooks at preload:** the preload runs before `Scripts.rxdata`, whose definitions would replace an override made then, and the scripts read some of these values while they load. So `Object.method_added` redefines the top-level `pbGetTimeNow` the moment the game defines it, when the clock is pinned; a later redefinition is pinned again. `System.data_directory` is the engine's own method, so it is simply redefined at preload. `pbGetTimeNow` returns `Time.local` of the pinned fields on every call, so the game's time stands still. _(from Wonder, settled 2026-09-30)_
- **Seed:** the bridge calls `srand(seed)` at preload, before any game script runs, and wraps `Kernel#srand` and `Kernel.srand`: a call with a seed passes through, and a bare `srand` gets `(seed × 1000003 + tick) mod 2³²` instead, logged. The only bare `srand` in Añil is the lottery's (`S/338_Minigame_Lottery.rb:10`), whose date seed already follows the pinned clock. Snapshot restore sets the seed this rule uses. _(from Wonder, settled 2026-09-30)_
- **Other clock reads stay unpinned:** every other `Time.now` or `Time.new` in Añil's scripts and plugins measures wall-time intervals, names or stamps debug output and files, sets the Discord presence's start, or stores a time that is only shown or compared with other stored times; the list, with each place, is in Wonder's design (Wonder: `docs/subsystems/harness/explanation/runtime-design.md` → Clock). The Pokémon creation stamps are the one read that can reach game state, through Box Auto-Sort's catch-date sort, and get their own clock (next bullet). _(from Wonder, settled 2026-09-30, re-checked on Añil 2026-10-02)_
- **Creation stamps follow a tick clock:** `@timeReceived` and `@timeEggHatched` are stamped with 2026-01-01 12:00 UTC plus `Graphics.frame_count / Graphics.frame_rate` in whole seconds, so a session and its replay stamp the same times and the catch-date sort still orders Pokémon by when they were received. Once the game's scripts have loaded, the bridge wraps `Pokemon#initialize` to set `@timeReceived` after the original runs, and `Pokemon#timeEggHatched=` to store the stamp for any non-nil value. Code: `creation_stamp` and `install_stamp_hooks` in `anil_drive.rb`; verified in [Runtime Reference → Saves, Clock and Seed](../reference/runtime.md#saves-clock-and-seed). _(from Wonder, owner, settled 2026-10-02)_

### Launch

- **`anil run [--save NAME] [--build B] [--hidden] [--clock real|<time>] [--seed N] [--snapshot NAME]`** checks the deploy stamp, writes the launch parameters to `anil_launch.json` in the working copy, starts `Game.exe` without activating it and waits for the handshake. The handshake reports the game's Windows PID (Ruby's `Process.pid`), which the harness uses to kill the game with `taskkill`. Only one game runs at a time per data root, guarded by the data-root lock. _(from Wonder, settled 2026-09-30)_
- **Every launch is held until it is handed over:** a launch from the title holds at its first tick, as a boot into a snapshot already did ([Snapshots](#snapshots)): the game takes no logic tick until a driver attaches or `anil control take` hands it to the owner, and the bridge serves requests meanwhile, so `anil state`, `eval` and `snapshot` work on the held game. Why: the work queue's bridge entry asked for `anil run` to launch the game paused under the bridge and `anil control` to hand it over; holding from the first tick also keeps a session's first ticks the driver's, so a session started from the title replays from its first tick. Wonder let a title launch run free with the owner in control and held only snapshot boots. Code: `@boot_hold` set in `AnilBridge.start` when the launch file names no snapshot. _(2026-10-21, build choice)_
- **Readiness:** the harness retries connecting until the handshake timeout of 60 s, because the bridge only starts listening once the game's scripts load. A handshake whose bridge hash differs from the stamp is an error ([Deploy](#deploy)). _(from Wonder, settled 2026-09-30)_
- **Launch file:** `anil_launch.json` carries the session ID, port, the session and `bridge.log` paths as `\\wsl.localhost` paths, the snapshots folder and the boot snapshot; the same values, plus the build and stamp, go to `sessions/<id>/launch.json`, which outlives the working copy's file ([Saves](#saves)). The save, clock and seed fields are under [Clock](#clock). _(from Wonder, settled 2026-09-30)_
- **Session ID:** local time, `YYYYMMDD-HHMMSS`, with `-2`, `-3` on a collision. The handshake echoes it, so a game left holding the port from another session is detected rather than adopted. _(from Wonder, settled 2026-09-30)_
- **Lifetime:** `anil run` returns once the handshake succeeds and the game keeps running. `game.lock` records the session, the harness PID and, after the handshake, the game's Windows PID. It is live while that PID is a running `Game.exe` (`tasklist.exe`), or, before the handshake, while the harness process lives; otherwise it is stale and removed. `anil stop` kills the locked game with `taskkill.exe /F` and removes the lock. _(from Wonder, settled 2026-09-30)_
- **Failed launch kills by executable path:** when a launch fails or is interrupted before `anil run` returns, the harness lists every `Game.exe` with its executable path (`Get-CimInstance Win32_Process` through `powershell.exe`), kills each one running from the working copy with `taskkill.exe /F`, releases the lock, and reports which PIDs it killed. Matching the path as well as the image name means the owner's playable copy, Wonder's games and other `Game.exe` programs are never touched. _(from Wonder, settled 2026-09-30)_
- **Launching never takes focus and opens off the primary screen:** the harness starts `Game.exe` hidden with `CreateProcess` (C# through `Add-Type` in `powershell.exe`, `STARTF_USESHOWWINDOW` and `SW_HIDE`), then after the handshake moves the `SDL_app` window of the game's PID to the centre of the working area of the largest non-primary monitor with `SetWindowPos` and shows it with `SW_SHOWNA` unless `--hidden` was passed, handing the foreground back if the game took it. `anil run` prints where the window went. Why: the owner works on the Windows desktop while games run ([Runtime Reference → Focus and Placement](../reference/runtime.md#focus-and-placement)). _(from Wonder, owner, settled 2026-10-01)_

### Bridge Protocol

- **JSON lines over TCP on `127.0.0.1`,** port 24731 by default. The bridge is the server, using Ruby's own `TCPServer` with `accept_nonblock` and `read_nonblock`, polled in the wrapped `Graphics.update`; a reply is written with a blocking `write`. Each request carries an id and gets one reply, which also carries the [events](#events) after the request's `since` cursor. The bridge carries its own small JSON encoder and decoder, which decode every request as UTF-8 and encode every string as UTF-8, reinterpreting or converting a string in another encoding so one odd string never breaks a reply. The handshake gives the protocol version, bridge hash, build, PID and current tick. Several clients may connect: one holds the driver role (lockstep and input), the others read state and eval, and a client with the control role can change speed, pause, and take or release control. The wire format is in [Runtime Reference → Launch](../reference/runtime.md#launch). _(from Wonder, settled 2026-09-30, `TCPServer` 2026-10-02)_
- **Port outside the ephemeral range:** launch refuses a port inside `/proc/sys/net/ipv4/ip_local_port_range`. Forced by WSL mirrored networking, where Windows reserves WSL's ephemeral range ([Runtime Reference → Bridge Start](../reference/runtime.md#bridge-start)). _(from Wonder, settled 2026-09-30)_
- **Handshake and clients:** the first request on a connection must be `hello`; the bridge serves any number of clients, each non-blocking, polled once per `Graphics.update`. _(from Wonder, settled 2026-09-30)_

### State

- **Typed state built in Python from one generic bridge read:** the bridge's `read` takes a Ruby object path (such as `$player@party`) and returns that object's instance variables, plus any named zero-argument methods the request asks for, as plain JSON down to a depth limit. The harness's pydantic models turn the reply into trainer, party, bag, PC boxes, map, position, facing, moving, pending transfer, switches, variables and self-switches on request, the battle, and the event interpreter's current command. Species, moves, items, abilities, natures, types and statuses are v21 Symbols, each given with its name from the game's `GameData`. Why: keeping the shapes in Python means a layout fix needs no bridge redeploy or game restart, and the Ruby side stays small and stable; the randomizer makes live state the only reliable source for species, moves and abilities. _(from Wonder, owner, settled 2026-09-30)_
- **One request, many paths:** `read` takes a list of named paths and reads them all in one poll, so an `anil state` is one round trip at one tick. Methods to call are named per class and apply wherever an object of that class turns up, and a `stop` list of classes (the battle and its scene) cuts back-references. Depth is per request with a per-path override; `anil state` asks for 10. The wire format and path grammar are in [Runtime Reference → State Read](../reference/runtime.md#state-read). _(from Wonder, settled 2026-09-30)_
- **Calls run on a copy:** each method a `read` names is called on a fresh shallow copy of the object (`Kernel#clone`), not on the object itself, because Essentials fills several `Pokemon` fields lazily on first call and those land in the party digest, so a read would otherwise change what a replay sees. A method that changes an object it reaches, such as `form` when the game would recalculate it, can still change the game. _(from Wonder, settled 2026-10-02)_
- **Methods with literal arguments in a path (forced by evidence):** a path step may call a method with integer, string, `nil` or boolean arguments, since every name on Añil is reached as `GameData::X.get("KEY").name`. Paths are parsed, never passed to `eval`. _(from Wonder, settled 2026-09-30)_
- **Battle access:** a `pbStartBattle` hook installed once `$scene` is first set publishes the running battle as `AnilBridge.battle`, in `anil_read.rb` with the `read` command. Safari battles are not covered. _(from Wonder, settled 2026-09-30)_
- **Names:** read on the first `anil state` of a session in two reads (each `GameData::X.keys`, then every key's name, about 3,650 paths) and cached as `sessions/<id>/names.json`. Weather and terrain stay as their Symbols, and battle and field effects stay numeric arrays indexed by `PBEffects`. _(from Wonder, settled 2026-10-02)_
- **Interpreter command:** the harness reads the map interpreter's whole `@list` with `@index` and picks the command in Python, since a path cannot index by another value. _(from Wonder, settled 2026-09-30)_
- **Models:** `anil.harness.state` holds the models and `read_state(session, switches=, variables=, with_self_switches=)`; a layout that no longer matches raises `StateError` naming the tick. `anil state` prints a text view and takes `--switch N`, `--variable N` (both repeatable), `--self-switches`, `--events N` and `--json`. The state still carries Wonder's battle reveals and rules ledger, read from `$PokemonGlobal@anil_reveals` and `$PokemonGlobal@anil_rules`: the reveals are filled by the bridge's event hooks, and the ledger by its rules hooks ([Rules Engine Design → The Ledger](rules-engine-design.md#the-ledger)). _(from Wonder, settled 2026-09-30; the ledger's source 2026-10-21, build choice)_

### Context

- **Classified in Python from the Ruby call stack, with Ruby wrappers only for payloads:** every reply carries `caller` at the current poll, and a table in the harness maps frames to a context: `overworld`, `event`, `message`, `choice`, `number`, `menu` (with the screen named), `battle_command`, `battle_fight`, `battle_target`, `battle_switch`, `battle_bag`, `pokedex_entry`, `transition`, `special` or `unknown` (no table match; the stack is logged). Ruby wrappers capture only what the stack cannot carry: message text, choice options, the number range, the live cursors, the battle menus' indices and options, and the menu screens' prompts and live selections. The table and each wrapper are in [Runtime Reference → Context](../reference/runtime.md#context). Why: "what is the game waiting for" is not a variable in the game, and a newly found screen is a table line with no bridge redeploy or game restart. _(from Wonder, owner, settled 2026-09-30)_
- **Reply fields:** every reply carries `caller` (the game's frames at the poll that served it, without the bridge's own) and `payloads` (the active wrappers, outermost first), both taken once per tick. _(from Wonder, settled 2026-09-30)_
- **Table keys are section and method,** such as `093:Messages`, `block in pbMessageDisplay`, since a waiting loop calls `Graphics.update` from more than one line of the same method; a line may require an outer frame (`under`). The harness walks the stack from the top, skips lines marked `pass`, and the first other frame decides; it never looks further down. `overworld` becomes `event` while the map interpreter runs. _(from Wonder, settled 2026-09-30)_
- **`transition` covers busy frames:** fades, map transfers, the battle intro, battle animations and fixed waits. _(from Wonder, settled 2026-09-30)_
- **One generic wrapper (forced by evidence):** each wrapper aliases the final definition and replaces it with a `define_method` that takes any arguments and keeps the method private when the game's was, since Añil's plugins redefine the battle menus with signatures of their own. A payload field that raises is logged and left out, never raised into the game. _(from Wonder, settled 2026-10-02)_
- **Unknown log:** an unknown context is a warning with the stack on the console and one JSON line (`tick`, `frames`) in `sessions/<id>/unknown_contexts.jsonl`. _(from Wonder, settled 2026-09-30)_
- **Signature:** each tick the bridge computes `signature`, every game frame with its method name removed, joined with `|`, so an advance can stop when it changes. Code: the wrappers and the per-tick stack in `anil_context.rb`; the table and `classify` in `anil.harness.context`. _(from Wonder, settled 2026-09-30)_

### Events

- **An event stream explains why state changed:** hooks in the bridge give each event a sequence number and its tick, write it to the session record at once, and append it to a shared ring of the newest 1,000. The hooks are `Battle#pbDisplay`, `pbDisplayPaused` and `pbDisplayBrief` (`battle_text`, the battle text a player sees) and `PBDebug.log` (`debug_log`, the internal battle log); the `reveal` kind records an opposing Pokémon's shown move, ability or item. Each hook records the event and then calls the original. _(from Wonder, owner, settled 2026-09-30)_
- **Every client is treated the same:** a request may carry `since: <seq>` and its reply carries the ring's events with a higher number; without `since` it gets none. Nothing is cleared, each client keeps its own cursor, and when `since` is older than the ring's oldest event, the reply sets `events_gap` and the client reads what it missed from the record. The handshake reports `event_seq`. _(from Wonder, owner, settled 2026-10-01)_
- **Harness side:** `Session.follow_events` sets a cursor; every later request sends it, and the events returned go to the session's inbox, which `Session.take_events` empties. `anil.harness.drive` follows from attach and puts the inbox on each advance's answer; `read_state` puts it on the state. `anil state` follows from its handshake's number minus `--events` (10 by default). Code: `anil_events.rb`. _(from Wonder, settled 2026-10-01)_

### Input and Control

- **The driver owns input; the owner can take it:** the bridge wraps `Input`'s queries once the game's scripts have loaded. In a driven session each tick's input comes only from the driver, and real keys are ignored. "Take control" hands input to the owner's keyboard and pauses the driver; "release" hands it back. With no driver attached the owner controls, except during the boot hold ([Launch](#launch)). _(from Wonder, settled 2026-09-30)_
- **Roles:** `hello` takes an optional `role`. `driver` is refused while another client drives; `control` may be held by any number of clients; a client without a role reads and evals. _(from Wonder, settled 2026-10-01)_
- **Input per tick, latched in the poll:** each tick's input is `buttons`, `keys` and `text`, latched before the game's `Input.update`, so input is a function of the tick alone; from the second `Input.update` in a tick, `trigger?`, `repeat?` and `release?` answer false. The details are in [Runtime Reference → Input and Lockstep](../reference/runtime.md#input-and-lockstep). _(from Wonder, settled 2026-10-01)_
- **Take and release:** `anil control take` and `anil control release`. `control take` ends the driver's running advance at once with `stopped: control` and holds every later driver request until release. Wonder's reason for a take, and its record of takeovers, belong to its run records and are not copied ([Left Out](#left-out)). _(from Wonder, settled 2026-10-01; the reason dropped 2026-10-21)_
- **Helpers:** `anil.harness.drive` attaches as the driver and offers `advance`, `advance_driven`, `hold_until_moved`, `wait_until_still`, `walk`, `press_until_changed` and `type_text`; the helpers re-send their advance after a `control` stop, and the driver's connection has no reply timeout. _(from Wonder, settled 2026-10-01)_

### Speed

- **The bridge owns speed, the game's clock and `Graphics.frame_count`:** presets are 1×, 2× and max. The bridge replaces `System.uptime` with a virtual clock that advances once per logic tick, and the step per tick is the preset's scale (1, 2 or 8) over the game's `Graphics.frame_rate`, never more than 0.2 s, under `Game_Character#update`'s 0.25 s skip. At max a tick renders only when about 1/30 s of wall time has passed. `Graphics.delta` and `Graphics.average_frame_rate` follow the clock, and turbo's stages are pinned to ×1. The facts are in [Runtime Reference → Speed](../reference/runtime.md#speed). _(from Wonder, owner, settled 2026-09-30 and 2026-10-02)_
- **Presets and who sets them:** `anil speed [1x|2x|max]` from a `control` client; without a preset any client reads the speed and the frames rendered. The session starts at 1×, or at the snapshot's preset when it boots into one. Whenever it becomes driven the bridge switches to `max` until a control client picks another preset; whenever it stops being driven it switches to 1×. Code: `anil_speed.rb`. _(from Wonder, settled 2026-10-01)_

### Lockstep

- **Every driven session is lockstep:** the game advances only on a driver command, N ticks or until a condition (`signature`, `payloads`, `position`, `moving`), with the input to apply on each tick; the reply is deferred to the poll where a condition changed or the limit was reached. While no advance is pending the game waits inside the wrapped `Graphics.update`, pumping the window and socket without advancing game logic. Why: the game draws `rand` on every tick on the map, so wall-clock input is unreproducible ([Runtime Reference → Investigation Commands](../reference/runtime.md#investigation-commands)). _(from Wonder, settled 2026-09-30)_
- **`frame_count` follows the tick plus an offset (forced by evidence):** the bridge wraps `Graphics.frame_count=`, and when the game assigns it the offset becomes the assigned value minus the tick; every poll sets `frame_count` to the tick plus that offset. Code: `anil_drive.rb`. _(from Wonder, settled 2026-10-01)_

### Snapshots

- **A snapshot is restored in place the moment it is taken:** it is the game's save hash (`SaveData.compile_save_hash`) as Marshal plus a seed, the pinned clock, the tick, the virtual uptime and the speed preset. The bridge writes it to `snapshots/<name>/` with a newly picked seed, then immediately restores from that file, so the live session continues from a restore and every later restore starts from identical state. Restore switches `$scene` to a one-shot restore scene that seeds `srand` and loads the hash through `Game.load`. Taking a snapshot is refused outside idle overworld, and a name is never overwritten. Why: `Game.load` builds a new `Scene_Map` whose sprites are made for the loaded objects, and plugin save values come back without a hand-kept list ([Runtime Reference → Snapshots](../reference/runtime.md#snapshots)). _(from Wonder, owner, settled 2026-09-30 and 2026-10-02)_
- **Files:** `snapshots/<name>/` holds `save.dat` and `snapshot.json`: name, seed, tick, virtual uptime, speed preset, RNG call count, clock, the hash (CRC-32 of `save.dat`), size, position, session, build, bridge hash and when it was taken. Wonder's `run` field is not written, and a snapshot copied from Wonder's data root that carries one is read with it ignored. A restore whose `save.dat` no longer matches the hash is refused; the bridge hash is informational. _(from Wonder, settled 2026-10-01; `run` dropped 2026-10-21)_
- **Request:** `snapshot` with `action` `save` or `restore`, `name` and an optional `seed`, from a `driver` or `control` client (`anil snapshot` attaches as `control`); `anil snapshot list` reads the folders. Save and restore are refused unless the game is idle on the map, while an advance or another restore runs, while paused, and on the real clock. _(from Wonder, settled 2026-10-01)_
- **The restore** sets the tick, virtual uptime and RNG call count to the snapshot's, sets the pinned clock, seeds `srand` before the load, clears the driver's input, loads every save value with `SaveData.load_values`, resets TM items' moves to `items.dat`, calls `Game.load`, puts back the snapshot's TM-compatibility table, and runs what the skipped title and load screens would have done (Challenge Modes' `begin_challenge`, and on a boot the Discord presence). Each step is forced by evidence on Añil; the reasons are in Wonder's design (Wonder: `docs/subsystems/harness/explanation/runtime-design.md` → Snapshots). A restore never forks a run, since `anil` keeps none. _(from Wonder, settled 2026-10-01 to 2026-10-03)_
- **Boot into a snapshot:** `anil run --snapshot NAME` reads `snapshot.json`, refuses a changed hash, and launches with the snapshot's clock (`--clock` is refused with it) and seed (or `--seed`). The bridge wraps `pbCallTitle`, so the first scene is the restore scene, opens its listener only after the restore, and starts at the snapshot's speed preset. After it the game holds until a driver attaches or the owner takes control, as every launch does ([Launch](#launch)). _(from Wonder, settled 2026-10-01)_

### Session Records and Replay

- **Every session is recorded and replays exactly:** `sessions/<id>/` holds the launch parameters, the deploy stamp, the starting save, and `record.jsonl`, which the bridge writes: every lockstep command with its ticks and input, owner input per tick while the owner held control, every eval with its tick, every event, snapshot saves and restores, speed and control changes, and a state digest (`party`, `position`, `rng`) in each reply. `anil replay <id>` relaunches with the same parameters, feeds the log, and reports the first advance whose digest differs, with its tick range. Another build is refused, another bridge hash warns and replays anyway, and a missing or changed snapshot is refused. Code: `anil_record.rb`, `anil.harness.replay`. _(from Wonder, owner, settled 2026-09-30)_
- **Entries:** `advance`, `input`, `eval`, `control`, `speed`, `snapshot`, `restore` and `event`, written by the bridge; any other lowercase kind is written by a harness client through `note`. Replay skips `control` and `event`, the kinds navigation, dialog and the menu layer write through `note` (`nav`, `dialog`, `menu`, with the game database check's `check`), and the kinds later tooling writes (`battle` and `rules` through `note`, and `rules_bought`, `rules_shiny` and `rules_sleep`, which the rules hooks write from the bridge); any other kind is refused, so a new record kind needs replay support first. Wonder's `save`, `reload_refused`, `run_lost`, `run_fork`, `takeover`, `agent` and `tool` kinds are not written. _(from Wonder, settled 2026-10-01; the kinds trimmed 2026-10-21)_
- **Starting save kept (forced by evidence):** `anil run` copies `saves/<name>/` into `sessions/<id>/save/` before launch, and replay boots from a fresh copy of it in `saves/replay-<id>/`, never the live save folder. _(from Wonder, settled 2026-10-01)_
- **Replay is a driver:** it launches with the session's build, clock, seed and snapshot and attaches as the driver `anil replay` straight after the handshake, sending plain advances of the recorded number of ticks and comparing the digest at each one's end; recorded evals are re-run at their ticks, snapshot saves become restores of the saved snapshot, and a second client, `anil replay speed`, replays the speed changes. A session on the real clock, or one needing input from before the replay driver attaches, is refused. After the last recorded tick replay stops the game unless `--keep` is passed. The limits are in [Runtime Reference → Replay](../reference/runtime.md#replay). _(from Wonder, settled 2026-10-01 and 2026-10-02)_

### Investigation Commands

- **Eval, stack, screenshot and RNG counter in every session:** `anil eval`, `anil stack`, `anil shot` and `anil rng` attach to the live session as extra clients, each reading the live lock, connecting, saying `hello` under its own client name, refusing a bridge whose session differs from the lock's, and disconnecting after one request. Every eval is logged with its source and result and recorded at its tick, so replay runs it again at the same point. _(from Wonder, settled 2026-09-30)_
- **Every attached command logs to the session's `harness.log`:** `attach` adds the session's log handler (`anil.harness.session_log`) to the `harness` logger before it connects, as `anil run` and `anil stop` do, so what an attached command logs (a guard, a freeze, an unknown context) lands in `sessions/<id>/harness.log` beside the launch's lines, as well as on the console. _(build choice, 2026-10-21)_
- **Eval:** the source runs with `eval(source, TOPLEVEL_BINDING, "anil_eval", 1)`; the reply carries the result's class and `inspect`, and an exception becomes an error reply. Wonder's refusal of eval in a real run has no counterpart, since `anil` has no real runs. _(from Wonder, settled 2026-09-30)_
- **Stack:** `caller` inside the request, without the bridge's own frames. **Screenshot:** the bridge writes `shot-<tick>.bmp` in the session directory, and the harness converts it to PNG with Pillow and deletes the BMP. **RNG counter:** the bridge wraps `Kernel#rand` and `Kernel.rand` at preload, and `rng` returns the calls counted since boot. _(from Wonder, settled 2026-09-30)_
- **Showdown export:** `anil showdown` evaluates the mod's `RandomlockeShowdown.export` and prints the party in Showdown's format ([Randomlocke Design → Showdown Export](randomlocke-design.md#showdown-export)). _(from Wonder, settled 2026-10-02)_

### Sound

- **Harness games are muted:** the bridge mutes as soon as it reads `anil_launch.json`, at preload, so every game `anil run` or `anil replay` starts is silent from its first frame; a hand start without a launch file keeps its sound. Muting sets the global BGM volume to 0 and plays BGS, ME and SE at volume 0; a `sound` request with `muted` from a `control` client switches it, and is not recorded. No `anil` command sends it yet. Code: `anil_audio.rb`; verified in [Runtime Reference → Sound](../reference/runtime.md#sound). _(from Wonder, owner, settled 2026-10-02)_

### Left Out

- **What stays in Wonder:** its run records (`wonder_run.rb`, `harness.runs`: run IDs, save counters, reload refusal, forks, lost runs), the real run and its Fair Play refusals (`run --real`, eval and restore refused, takeovers with a reason), the control panel (`harness.panel`; the bridge's `pause` and `status` requests stay, unused by any `anil` command), and the agent and its settings. The rules hooks (`wonder_rules.rb`) come with the rules guard, as `anil_rules.rb` ([Rules Engine Design](rules-engine-design.md)). Why: the owner, "nothing for wonder (where wonder is the actually agent that runs it) should be kept"; the panel only made sense for watching the agent. _(owner, 2026-10-21)_
