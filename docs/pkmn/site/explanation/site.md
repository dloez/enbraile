# The pkmn Site

The group's Pokémon web app, `pkmn/site/`, served at `pkmn.enbraile.vip`. Players sign in with Discord and see it once an admin has allowed them: they land on the running series' page, `/series/<n>`, with every series listed at `/series` ([Series](#series)), and [Open Sheet](open-sheet.md) at `/open-sheet` and [Team Analysis](team-analysis.md) at `/team-analysis` stay behind the PC and Teams tabs until the pages replacing them are built. Its API runs on Vercel Functions, admins sign in at `/admin`, keep the allowlist at `/admin/players`, keep the games and their files at `/admin/games`, and make and run the series at `/admin/series`. Running and deploying it is in [How to Run and Deploy the Site](../how-to/run-and-deploy-the-site.md). It was scoped with the owner on 2026-10-15.

## Stack

npm; Vite 8, React 19, TypeScript 7, Tailwind 4 and shadcn/ui; TanStack Router; zod 4; Dexie over IndexedDB; `@pkmn/dex` and `@pkmn/img` for Showdown's data and sprites; `react-markdown` and `remark-gfm` for a series' rules. Every package is pinned exactly, at its latest stable version when it went in (the scaffold, 2026-10-16: vite 8.3.4, react 19.3.1, typescript 7.0.2, tailwindcss 4.3.3, shadcn 4.21.5, @tanstack/react-router 1.170.44, @pkmn/dex 0.10.11, @pkmn/img 0.3.4). The gate is `npm run gate`: `tsc -b`.

Routes are declared in code in `src/router.tsx`, not with TanStack Router's file-based plugin: a handful of routes needs no generated route tree for `tsc` to check before a build. A page gets its route there; the home, `/`, has no page of its own and sends a signed-in reader on to the running series ([Series](#series)).

The server side is TypeScript too: a Hono app (`api/_lib/app.ts`) under `/api`, Better Auth for sign-in (`api/_lib/auth.ts`), and Postgres through Drizzle over `pg` (`api/_lib/db.ts`, schema in `api/_lib/schema.ts`), with `drizzle-kit` writing the migrations into `drizzle/` (scaffolded 2026-10-22: hono 4.13.13, better-auth 1.7.12, drizzle-orm 0.45.4, drizzle-kit 0.31.11, pg 8.23.1, @hono/node-server 2.1.5, tsx 4.23.15; @aws-sdk/client-s3 and @aws-sdk/s3-request-presigner 3.1156.0 on 2026-10-22). `api/index.ts` is the only Vercel Function: Vercel makes a function of every file in `api/` except those under a `_` folder, so the app lives in `api/_lib/`, and `vercel.json` sends every `/api/` path to it. Locally, `scripts/dev-api.ts` serves the same app on Node at `API_PORT` (8787), started and stopped by a small Vite plugin in `vite.config.ts` so that one `npm run dev` runs both, and Vite proxies `/api` to it. The browser talks to it through Better Auth's client (`src/lib/auth-client.ts`) and, for the site's own routes, `src/lib/api.ts`, which parses each answer with a zod schema from `shared/`, the folder both the browser and the API compile, so the two agree on every request and answer. `tsconfig.api.json` puts `api/`, `scripts/` and `shared/` under the gate, and their relative imports end in `.js` so that both `tsx` and Vercel's compiled output resolve them.

## Accounts

A player signs in with Discord, through Better Auth's Discord provider, registered only when `DISCORD_CLIENT_ID` and `DISCORD_CLIENT_SECRET` are set. Their first sign-in makes a `user` row named after their Discord display name, with a `discord` account, and `allowed` false. `SiteShell` (`src/components/site-shell.tsx`), the root route's component, guards every page but `/admin` and its pages: signed out, it shows the sign-in page (`src/pages/sign-in.tsx`); signed in but not allowed, the waiting page (`src/pages/waiting.tsx`), with the player's badge and name and its own sign-out; otherwise the header and the page. Neither page has the header. Every API route but `/api/auth/*` answers only a session that is allowed or an admin's (`api/_lib/access.ts`): 401 without a session, 403 "Waiting for an admin" for a player not allowed. The flag is read on every request, so allowing or removing a player takes effect on their next reload. An admin keeps the allowlist at `/admin/players` (`src/pages/admin-players.tsx`), which lists every player who has signed in, waiting first, and allows or removes each one through `GET /api/players` and `POST /api/players/<id>/allowed` (`api/_lib/players.ts`, schemas in `shared/players.ts`), both for admins only. Admins never touch Discord: account linking is off, so a Discord sign-in can never join an existing account, and a database hook refuses any account other than a password for an admin's user.

An admin is a separate username-and-password account, not a player: a `user` row with `admin` set and a `credential` account holding the password hash. `npm run admin:create <name>` (`scripts/admin-create.ts`) is the only way to make one outside the local stack, whose seed makes its own: it asks for the password twice without echoing it, never takes it as an argument, and writes both rows in one transaction, with the username lower-cased and a placeholder `<name>@admin.invalid` email, since Better Auth requires an email. Better Auth's sign-up is off (`disableSignUp`), so no route makes an account, and `admin` cannot be set through its API (`input: false`). Locally, `DEV_SIGN_IN=1` adds a test sign-in (`api/_lib/dev-sign-in.ts`), a Better Auth plugin whose `GET /api/auth/dev/sign-in?username=<name>` starts a session for a player who is not an admin and redirects home; unset, the plugin is not registered and the route does not exist. `npm run seed` (`scripts/seed.ts`) makes the local admin, the test players (Red and Blue allowed, Leaf waiting), a game with a stand-in zip and series 1 running on it ([How to Run and Deploy the Site](../how-to/run-and-deploy-the-site.md) has the details), and only against a database and a file store on `localhost` or `127.0.0.1`. `/admin` (`src/pages/admin.tsx`) shows a sign-in form, and an admin's session gets the admin home with sign-out. The admin home lists the admin pages as links, and the header's sign-out signs an admin out. The admin pages have no design of their own; they are built from the look's shared pieces (`Panel`, `fieldClass`, the quiet button, the lifting card). Every `/api/games` route answers only an admin's session (`api/_lib/admin.ts`): 401 without one, 403 for a player.

The [Site v2 Screens](https://claude.ai/artifact/JZpaCYGx2NQtPpcvAWYXrZ) design in Claude Design sets the look the whole site moves to. The owner signed off its series list, series page and site header on 2026-10-22; its sign-in and waiting pages on 2026-10-23; and, later that day, the snapshot upload flow, the series page's revision and the two player pages (profile, and a player in a series). Its other screens are still being designed on the same canvas. It replaces the look the [Open Sheet Screens](https://claude.ai/artifact/SfpFcW5UoLVLeLAmdJZMG1) design set on 2026-10-16 (charcoal, a slate-blue PC, orange for actions) everywhere, the PC and team views included, as each screen is designed and built. Frozen copies of the signed-off boards are in `pkmn/site/design/` (`series-list.dc.html`, `series.dc.html`, `sign-in.dc.html`, `sign-in-phone.dc.html`, `waiting.dc.html`, `waiting-phone.dc.html`, `upload-*.dc.html`, `player-profile.dc.html`, `player-series.dc.html`, `header-phone*.dc.html`): builders read them for exact colours, sizes and spacing, and they never change; a later revision is signed off on the canvas and copied in again. Their trainer numbers and names are sample data, and their Google Fonts link stands for the bundled fonts.

The look is a Gen 4–5 game screen, kept readable:

- **One dark theme,** a deep navy ground with a faint dot grid, navy panels with 3px slate borders and rounded corners. No light theme.
- **Two typefaces:** Jersey 10, a pixel face, for headings, labels, tabs, buttons and numbers; Nunito for running text.
- **Pixel art drawn in code** as crisp-edged SVG: the Poké Ball home mark, the icons (flag, monitor, people, download arrow, cartridge) and the series scenes.
- **A scene per series.** Each series has a background scene from a fixed set (so far a night sky and a daytime route), picked by the admin in the series form. Every scene moves a little in stepped, game-like animation: the night sky's stars, sparkles and lit windows blink; the route's clouds drift and its flowers blink. Under `prefers-reduced-motion` they stand still.
- **Sign-in and waiting are a Poké Ball:** the top half red with the site's name, a black band with a large Poké Ball on the seam, and the dark half below holding the Discord button or, for a player not yet allowed, their badge, the waiting message and sign-out. No header, no Pokémon, no animation. Discord's blurple is the one colour outside the look, on the Discord button alone.
- **The header:** the Poké Ball links home; tabs Series · PC · Teams (· Admin for admins) sit on the header's red bottom line, the open one filled red and joined to it; at the right, your badge and name, opening your profile, then sign-out. On a phone the bar shrinks to the Poké Ball, the open section's name and a three-line menu button whose dropdown lists the tabs, your profile and sign-out.
- **Players are boxed, never round:** a rounded-square badge with the player's initial, a dark border and a ring in the player's own colour.
- **Quiet controls:** buttons are translucent, in the pixel face, with a dark bottom edge; whatever is clickable as a whole (a series banner, a trainer's PC or Teams tile) lifts and takes a cyan border on hover. Red marks where you are, cyan what you can act on, yellow you and winners, amber a soft warning that never blocks (an old export's missing fields, a snapshot about to be replaced).
- No helper text explaining the UI. The UI is in English, since Showdown's names are. Desktop-first, with every view usable on a phone.

The site's design system is kept in the repository: the code (`src/index.css`'s tokens, the shell, the shared components) is its source of truth, and the [Site Design System](../reference/design-system.md) describes it, changing in the same commit as the code does. A new page follows [How to Add a Page to the Site](../how-to/add-a-page-to-the-site.md).

shadcn was initialised with its Nova preset on Radix, its palette replaced by the design's colours as the only theme, and its vendored components in `src/components/ui/` follow the same token rule. The design's fonts are bundled from Fontsource rather than loaded from Google Fonts, and the type icons come from duiker101's [Pokémon Type SVG Icons](https://github.com/duiker101/pokemon-type-svg-icons), free for any use, bundled in `src/lib/type-icons.ts`, so the only outside calls the site makes at runtime are for Showdown's sprites; everything else it fetches is its own `/api`.

The tab icon is a spiral notepad with a red and white Poké Ball drawn on it and a pencil writing on it: `public/favicon.svg`, plus `favicon-32.png` and `apple-touch-icon.png` rendered from it for browsers that take no SVG icon.

## Games

A game is a name and one zip of its files (`game` in `api/_lib/schema.ts`, with the file's key, name, size and upload time). At `/admin/games` (`src/pages/admin-games.tsx`) an admin creates a game by name, which must be unique, and uploads its zip; the page lists every game with its file's name, size and upload date, and downloads it. The file never passes through the API, since a Vercel Function's body is capped at a few MB and a game is about 600 MB:

1. `POST /api/games/<id>/upload` with the file's name and size aborts any multipart upload the game left open, starts a multipart upload for a new key, `games/<id>/<uuid>.zip`, and answers the key, the upload's id and the part size (`partSizeFor` in `shared/upload.ts`).
2. The browser splits the file into parts of that size and sends four at a time (`uploadParts` in `shared/upload.ts`). For each part it asks `POST /api/games/<id>/upload/part` for a presigned `PUT` of that part, valid for an hour and signed for its exact size, and `PUT`s the part straight to the bucket, keeping the `ETag` the bucket answers (exposed by its CORS rule). One percentage shows the bytes sent across all parts.
3. A part that fails, or goes 30 seconds without sending a byte or getting its answer, is retried on its own with a freshly signed URL, up to six tries in all, after 1, 2, 4, 8 and 16 seconds. When a part runs out of tries, the other parts are cancelled and `DELETE /api/games/<id>/upload` aborts the multipart upload, tried three times; the page shows why the upload failed, and says so if the abort could not reach the bucket either, in which case the game's next upload aborts it in step 1. Aborting an upload the bucket no longer knows, because step 4 completed or aborted it, counts as done.
4. `POST /api/games/<id>/file` with the key, the upload's id and every part's number and `ETag` checks that the key belongs to the game and completes the multipart upload, aborting it if the bucket refuses. It then reads the object's real size from the bucket, records it and deletes the game's previous object.

Until step 4 completes, the bucket holds no object for the upload, only its parts, so a half-finished replacement leaves the old file in place and leaves no stray file behind. `npm run seed` puts its stand-in zip in the bucket through the same multipart calls and `uploadParts`, signing the parts in the script rather than through the API. The API's calls to the bucket give up after 5 seconds without a connection or 20 seconds without an answer, tried twice, so a bucket that cannot be reached fails a request rather than hanging it. A download is `GET /api/games/<id>/download`, a presigned `GET` valid for five minutes that saves under the uploaded file's name. Every games route is admin-only; a series' players download its game through the series page ([Series](#series)). The bucket is private: nothing in it has a public URL.

## Series

A series (`series` in `api/_lib/schema.ts`) has a unique number, a name, its game, its background scene (`night` or `route`), its ingestion mode (`manual`, players upload their saves, or `automatic`, the game sends them), its rules as Markdown, and a state: `draft`, `running` or `finished`. Its players are rows of `series_player`, and its milestones rows of `milestone`, in order (`position`), each named and marked `none`, `round` (a league round is played at it) or `tournament`. A partial unique index on `state` lets one series run at a time. The shapes the browser and the API share, and `startChecklist`, are in `shared/series.ts`.

**Admins** keep the series at `/admin/series` (`src/pages/admin-series-list.tsx`), which lists every series, newest first, and creates a draft from a number and a name, then opens its form at `/admin/series/<id>` (`src/pages/admin-series.tsx`): number, name, game (from `/admin/games`, marked when it has no file), ingestion, the scene with a preview of it under the series' name, the players (checkboxes over the allowlist), the milestones (named, marked, reordered, removed, added) and the rules, a Markdown text area that "Copy from" fills with another series' rules. The checklist under it shows what starting still needs: rules written, a game with its file, at least two players, at least one milestone, and, while another series runs, that series finished. It is worked out from the form as it is being filled, by the same `startChecklist` the API runs, and Start, which saves the form first, enables once every item is done. Save keeps a draft without starting it, and a draft can be deleted. Once a series runs only its rules change, through Save rules, and Finish, confirmed by a second press, ends it; a finished series stays finished. The routes are `GET` and `POST /api/admin/series`, `GET`, `PUT` and `DELETE /api/admin/series/<id>`, `PUT /api/admin/series/<id>/rules`, and `POST /api/admin/series/<id>/start` and `/finish` (`api/_lib/admin-series.ts`), every one admin-only; start refuses a draft whose checklist is not done, and the index refuses a second running series even if two starts race.

**Players** reach the running series from `/`, which sends a signed-in reader to its page, or to `/series` while none runs (`src/pages/home.tsx`). `/series` (`src/pages/series-list.tsx`, after `series-list.dc.html`) shows one banner per series that is running or finished, newest first, on its scene, with its name, its game and "Playing now" or "Finished"; the whole banner is a lifting link. `/series/<n>` (`src/pages/series.tsx`, after `series.dc.html`) is a header drawn on the series' scene with its name and its game in a box, with Download for the series' players and admins; the League as a work-in-progress placeholder; the Trainers, one row per player with their badge, their name, "You" on the reader's own row, and the milestones as a track, the rounds tinted and numbered and the tournament a cup, each row opening into PC, Teams and Snapshots tiles, which read "—" until snapshots and teams exist; and the rules, rendered from Markdown by `react-markdown` with GitHub tables (`remark-gfm`) and raw HTML skipped, in two columns on wide screens. A draft's page answers 404 to players and opens for admins. The routes are `GET /api/series`, `GET /api/series/<n>` and `GET /api/series/<n>/download` (`api/_lib/series.ts`), the last a five-minute presigned link to the game's zip for the series' players and admins, 403 for anyone else.

The scenes are `SceneArt` (`src/components/scene.tsx`): the boards' night sky and daytime route, drawn in code as crisp SVG rectangles on a pixel grid (360 by 65 for a page's header, 338 wide for a banner) and scaled to cover their box from the bottom. Their stars, sparkles and windows blink and their clouds drift in stepped CSS animations (`scene-twinkle`, `scene-sparkle`, `scene-glow`, `scene-drift` in `src/index.css`), which stand still under `prefers-reduced-motion`. `SCENE_LOOK` beside it holds each scene's ground, title shadow and the colours of the chips and the game's box drawn over it.

## Data and Storage

Accounts and their sessions live in Postgres: Neon (Vercel Marketplace, free tier, resource `pkmn-site`, region `aws-eu-central-1`, Frankfurt) in production, with a `dev` branch for previews, and locally the Postgres of `compose.yaml`, which also runs MinIO as the local stand-in for the file store, with a `pkmn-site` bucket. Files live in private Backblaze B2 buckets, `pkmn-site-enbraile` for production and `pkmn-site-preview-enbraile` for previews, reached through their S3-compatible API with the AWS S3 SDK (`api/_lib/files.ts`), the same code that talks to MinIO locally. The schema holds Better Auth's `user` (with the site's `admin` and `allowed` flags), `session`, `account` and `verification` tables, the `game` table, and the `series`, `series_player` and `milestone` tables, and changes only by forward migrations generated into `drizzle/` (`npm run db:generate`) and applied with `npm run db:migrate`; there are no down migrations, and data is restored with Neon's point-in-time restore. Secrets (`DATABASE_URL`, `BETTER_AUTH_SECRET`, the Discord application's `DISCORD_CLIENT_SECRET`, the buckets' `S3_*` keys) live in Vercel's environment and in an untracked `.env.local`, never in the repository; `.env.example` names every variable.

Open Sheet's tabs and teams still stay in the reader's browser, in IndexedDB, and Team Analysis's drafts in `localStorage`, per browser and device, until the team builder moves them into accounts. Game data (names, descriptions, base stats, the type chart) is bundled from `@pkmn/dex` rather than fetched. Sprites load from Showdown's sprite server, `play.pokemonshowdown.com`, through `@pkmn/img`'s URLs.

## Hosting and Deploys

Vercel serves the site from the owner's Hobby account: the Vite build's static `dist/` and the API as a Vercel Function (`api/index.ts`) in the same project. `pkmn/site/vercel.json` runs the function in Frankfurt (`fra1`), beside the Neon database (`aws-eu-central-1`), sends `/api/` paths to the function and rewrites every other path to `/index.html` so deep links load the single-page app. `pkmn.enbraile.vip` is a DNS-only (grey-cloud) `CNAME` to the Vercel target in the `enbraile.vip` zone, which stays on the owner's Cloudflare account. If the record were proxied, traffic would go through Cloudflare's IPs again, which Spanish ISPs block during LaLiga matches.

Vercel's Git integration, connected to the GitHub repository in the Vercel dashboard with root directory `pkmn/site`, builds and deploys each push to `main` that touches `pkmn/site/`. Pushes that touch nothing there are skipped, and each branch push gets a public preview URL (Vercel Authentication is off for previews). A preview or `vercel.app` URL is a different origin from `pkmn.enbraile.vip`, so its IndexedDB and `localStorage` start empty. The project's environment variables are set per Vercel environment: `DATABASE_URL` (the Neon production branch for Production, the `dev` branch for Preview), `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL` (`https://pkmn.enbraile.vip` for Production), and the B2 file store's `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY`, whose bucket and key differ for Preview, so a preview never reaches the production files, and, for Production only, the Discord application's `DISCORD_CLIENT_ID` and `DISCORD_CLIENT_SECRET`. Previews leave `BETTER_AUTH_URL` unset, so Better Auth takes each request's own URL as its base. There are no secrets in the repository. A schema change is migrated by hand (`npm run db:migrate` against the branch) before the code needing it is deployed. A bad deploy is undone with Vercel's Instant Rollback to the previous production deployment, or by reverting the commit, which redeploys.

The site writes no logs of its own: Vercel's build and deployment logs cover the deploy, the API's uncaught errors land in Vercel's function logs, there is no Web Analytics, and import and upload errors are shown to the reader.

## Decisions

- **The allowlist's build choices:** an `allowed` column on Better Auth's `user`, beside `admin`, set by no Better Auth route (`input: false`); one middleware on the whole API that lets `/api/auth/*` through and refuses everything else to a session neither allowed nor an admin's, so a route added later is closed to waiting players without opting in; admins pass it as if allowed, and see the site's pages with the header's sign-out and their name but no badge, since they are not players; `/admin` and its pages stay outside `SiteShell`'s sign-in and waiting pages, so an admin can always reach the password form; account linking off, and a `databaseHooks.account.create.before` hook refusing a non-password account for an admin; Discord registered only when both of its variables are set, so previews and the local stack run without it; a failed Discord sign-in, or one Better Auth sends back with `?error=`, reads "Sign-in failed" under the button; `/admin/players` as an admin page linked from the admin home, its players in a Waiting and an Allowed panel, Remove in the destructive button; a player's badge colour picked from their id until players get a colour of their own (`playerColour` in `src/components/player-badge.tsx`); the home's tool list left for allowed players until the series page replaced it and deleted it with the home's cards (the series build choices, 2026-10-23); the header's name hidden below `sm` and its gaps narrowed, so the badge and sign-out fit a 360px screen beside both tabs, until the signed-off phone menu (`header-phone*.dc.html`) was built and the whole account, badge, name and sign-out, moved into it below `sm` (the phone header's build choices, 2026-10-23); Discord's blurple as the `discord`, `discord-edge` and `discord-hi` tokens and the sign-in pages' pale pink as `blush`. **Why:** delegated build choices in an unattended run. _(settled 2026-10-23)_
- **The phone header's build choices:** one `SiteHeader` holding both widths, the desktop tabs and account shown from `sm` and the compact bar and its menu below it, so the menu never reaches desktop; the Admin tab, which no queued entry added, built with the menu's key and shown to admins at both widths, opening `/admin` and open on every admin page; the menu's name row not a link until the player's profile exists, as the desktop name is not one, and an admin's row their name alone, without a badge; a `PlayerBadge` size `xs` (32px) for that row, after the boards; the bar's middle left empty where no tab is open, as on the home; the scrim rendered beside the header rather than in it, so it dims the page without dimming the bar; the menu closed by choosing a tab, the scrim, Escape or any route change. **Why:** delegated build choices in an unattended run. _(settled 2026-10-23)_
