# The pkmn Site

The group's Pokémon web app, `pkmn/site/`, served at `pkmn.enbraile.vip`. Players sign in with Discord and see it once an admin has allowed them: they land on the running series' page, `/series/<n>`, with every series listed at `/series` ([Series](#series)), upload their save zip there as a snapshot, follow any player's journey and fallen through the series at `/players/<player>/series/<n>` and their career and each series' league record on their profile at `/players/<player>`, and open any player's PC at any snapshot the save rule lets them see at `/players/<player>/series/<n>/pc` ([Snapshots](#snapshots)), search a series' abilities for every trainer's Pokémon that can have one at `/series/<n>/abilities` ([Abilities](#abilities)), and build their teams, stored in their account, at `/teams` ([Team Builder](team-builder.md)), behind the Teams tab, where they also compare teams side by side. Its API runs on Vercel Functions, admins sign in at `/admin`, keep the allowlist at `/admin/players`, keep the games and their files at `/admin/games`, and make and run the series at `/admin/series`. Running and deploying it is in [How to Run and Deploy the Site](../how-to/run-and-deploy-the-site.md). It was scoped with the owner on 2026-10-15.

## Stack

npm; Vite 8, React 19, TypeScript 7, Tailwind 4 and shadcn/ui; TanStack Router; zod 4; `@pkmn/dex` and `@pkmn/img` for Showdown's data and sprites; `react-markdown` and `remark-gfm` for a series' rules. Every package is pinned exactly, at its latest stable version when it went in (the scaffold, 2026-10-16: vite 8.3.4, react 19.3.1, typescript 7.0.2, tailwindcss 4.3.3, shadcn 4.21.5, @tanstack/react-router 1.170.44, @pkmn/dex 0.10.11, @pkmn/img 0.3.4). The gate is `npm run gate`: `tsc -b`.

Routes are declared in code in `src/router.tsx`, not with TanStack Router's file-based plugin: a handful of routes needs no generated route tree for `tsc` to check before a build. A page gets its route there; the home, `/`, has no page of its own and sends a signed-in reader on to the running series ([Series](#series)).

The server side is TypeScript too: a Hono app (`api/_lib/app.ts`) under `/api`, Better Auth for sign-in (`api/_lib/auth.ts`), and Postgres through Drizzle over `pg` (`api/_lib/db.ts`, schema in `api/_lib/schema.ts`), with `drizzle-kit` writing the migrations into `drizzle/` (scaffolded 2026-10-22: hono 4.13.13, better-auth 1.7.12, drizzle-orm 0.45.4, drizzle-kit 0.31.11, pg 8.23.1, @hono/node-server 2.1.5, tsx 4.23.15; @aws-sdk/client-s3 and @aws-sdk/s3-request-presigner 3.1156.0 on 2026-10-22). `api/index.ts` is the only Vercel Function: Vercel makes a function of every file in `api/` except those under a `_` folder, so the app lives in `api/_lib/`, and `vercel.json` sends every `/api/` path to it. Locally, `scripts/dev-api.ts` serves the same app on Node at `API_PORT` (8787), started and stopped by a small Vite plugin in `vite.config.ts` so that one `npm run dev` runs both, and Vite proxies `/api` to it. The browser talks to it through Better Auth's client (`src/lib/auth-client.ts`) and, for the site's own routes, `src/lib/api.ts`, which parses each answer with a zod schema from `shared/`, the folder both the browser and the API compile, so the two agree on every request and answer. `tsconfig.api.json` puts `api/`, `scripts/` and `shared/` under the gate, and their relative imports end in `.js` so that both `tsx` and Vercel's compiled output resolve them. The save export is the site's own TypeScript (`api/_lib/export/`), with no package of its own: a port of the retired Python export's Ruby Marshal reader and export ([Save Export](save-export.md)), a zip reader over `node:zlib`, and the export's game data as `data.json`, imported with `with { type: "json" }` (`resolveJsonModule` in `tsconfig.api.json`).

## Accounts

A player signs in with Discord, through Better Auth's Discord provider, registered only when `DISCORD_CLIENT_ID` and `DISCORD_CLIENT_SECRET` are set. Their first sign-in makes a `user` row named after their Discord display name, with a `discord` account, and `allowed` false, unless an admin invited them: an invite, made at `/admin/players` from a Discord user ID and a name (`POST /api/players`), is a `user` row, allowed, with the placeholder email `<discord id>@discord.invalid`, and a `discord` account whose `account_id` is that ID and which holds no token. Better Auth signs a Discord sign-in into the user that owns the account with its ID, so the invited player's first sign-in lands in that row, already allowed and already in any series an admin put them in. Every Discord sign-in sets the user's name, avatar and email from Discord (`overrideUserInfoOnSignIn`), so an invite's name and placeholder email last only until then. `SiteShell` (`src/components/site-shell.tsx`), the root route's component, guards every page but `/admin` and its pages: signed out, it shows the sign-in page (`src/pages/sign-in.tsx`), its Discord button over a link to the admin sign-in, "Admin? Sign in here" (`/admin`), mirroring the admin sign-in's link back; signed in but not allowed, the waiting page (`src/pages/waiting.tsx`), with the player's badge and name and its own sign-out; allowed but owing a save to a running series they were added to mid-way, the same page as "Upload your save" ([Series → Joining mid-series](#series)); otherwise the header and the page. Neither page has the header. Every API route but `/api/auth/*` answers only a session that is allowed or an admin's (`api/_lib/access.ts`): 401 without a session, 403 "Waiting for an admin" for a player not allowed. The flag is read on every request, so allowing or removing a player takes effect on their next reload, or sooner when their tab regains focus, which refetches the session. An admin keeps the allowlist at `/admin/players` (`src/pages/admin-players.tsx`), which lists every player who has signed in or been invited, waiting first, an invite whose account holds no token yet marked "Invited", and allows or removes each one through `GET /api/players` and `POST /api/players/<id>/allowed`; any player is deleted with `DELETE /api/players/<id>`, an unused invite at one press and anyone else at a second ("Confirm delete"), which deletes their user row and with it their sessions, accounts, series places, saves and snapshots, then every object under their `saves/<series id>/<player id>/` in each series they were in, open uploads included; a delete refused because a hand-set change on another player's snapshot names them answers 409. Deleted, a Discord user who signs in again starts over as someone new, waiting (`api/_lib/players.ts`, schemas in `shared/players.ts`), both for admins only. Admins never touch Discord: account linking is off, so a Discord sign-in can never join an existing account, and a database hook refuses any account other than a password for an admin's user.

An admin is a separate username-and-password account, not a player: a `user` row with `admin` set and a `credential` account holding the password hash. `npm run admin:create <name>` (`scripts/admin-create.ts`) is the only way to make one outside the local stack, whose seed makes its own: it asks for the password twice without echoing it, never takes it as an argument, and writes both rows in one transaction, with the username lower-cased and a placeholder `<name>@admin.invalid` email, since Better Auth requires an email. Better Auth's sign-up is off (`disableSignUp`), so no route makes an account, and `admin` cannot be set through its API (`input: false`). Locally, `DEV_SIGN_IN=1` adds a test sign-in (`api/_lib/dev-sign-in.ts`), a Better Auth plugin whose `GET /api/auth/dev/sign-in?username=<name>` starts a session for a player who is not an admin and redirects home; unset, the plugin is not registered and the route does not exist. `npm run seed` (`scripts/seed.ts`) makes the local admin, the test players (Red and Blue allowed, Leaf waiting), a game with a stand-in zip, series 1 running on it and, since the profile, a finished series 2 ([How to Run and Deploy the Site](../how-to/run-and-deploy-the-site.md) has the details), and only against a database and a file store on `localhost` or `127.0.0.1`. `/admin` (`src/pages/admin.tsx`) shows a sign-in form, and an admin's session gets the admin home with sign-out. The admin home lists the admin pages as links, and the header's sign-out signs an admin out. The admin pages follow the canvas's admin boards, frozen as `admin-sign-in.dc.html`, `admin-overview.dc.html`, `admin-series-list.dc.html`, `admin-series.dc.html`, `admin-players.dc.html`, `admin-games.dc.html` and the phone boards `admin-overview-phone.dc.html`, `admin-players-phone.dc.html` and `admin-series-phone.dc.html` ([Admin pages](#admin-pages)).

**Admin pages.** Signed out, or signed in as a player, every `/admin` page is the admin sign-in (`AdminSignInPage`, `src/pages/admin-sign-in.tsx`), drawn by `SiteShell` without the header: the sign-in page's ball split in reverse, an `ink` top with the pixel key and "Admin" in `yellow` over the site's name and a red band, and under it a card with the username, the password and Sign in, "Wrong username or password" under a refused one, and a link home, "Not an admin? Players sign in with Discord". Signed in, each admin page opens with the admin tabs (`AdminNav`), Overview, Series, Players and Games, Players carrying a `yellow` count of the players waiting; the page's own title is for screen readers only. **Overview** (`/admin`, `src/pages/admin.tsx`): the running series as its scene banner, with its game and its players, milestones and snapshots, linking to its form, or a dashed card when none runs; the series, newest three, a draft dashed with how much of its checklist is done ("Draft · 3/4"); the players waiting, each with Let in (`POST /api/players/<id>/allowed`); and the games with their zip's size and how many series use each, or "No zip yet" in `warning`. **Series** (`/admin/series`): a one-line New series form, the number fixed at the next free one, and one scene banner per series, a draft faded and dashed, each with its state and its players, milestones and either its snapshots or, for a draft, its checklist ("3/4 ready to start"). **Players** (`/admin/players`): Waiting, outlined in `yellow` while anyone waits, above Allowed, each row a player's badge and name linking to their profile, "Invited" on an invite, when they signed in or joined, Delete (a second press, "Confirm delete", warns that it deletes their saves and snapshots; an unused invite goes at one press) and Let in or Remove; the invite form beside them. **Games** (`/admin/games`): a one-line New game form and one card per game, its cartridge, its zip's name, size, upload date and the series that use it, Upload zip (`go`) or Replace zip with Download, the upload's progress bar in `primary`, and "No zip yet. A series can't start on this game until it has one." for a game without one. Every `/api/games` route answers only an admin's session (`api/_lib/admin.ts`): 401 without one, 403 for a player.

## Games

A game is a name and one zip of its files (`game` in `api/_lib/schema.ts`, with the file's key, name, size and upload time). At `/admin/games` (`src/pages/admin-games.tsx`) an admin creates a game by name, which must be unique, and uploads its zip; the page lists every game with its file's name, size and upload date, and downloads it. The file never passes through the API, since a Vercel Function's body is capped at a few MB and a game is about 600 MB:

1. `POST /api/games/<id>/upload` with the file's name and size aborts any multipart upload the game left open, starts a multipart upload for a new key, `games/<id>/<uuid>.zip`, and answers the key, the upload's id and the part size (`partSizeFor` in `shared/upload.ts`).
2. The browser splits the file into parts of that size and sends four at a time (`uploadParts` in `shared/upload.ts`, driven by `sendFile` in `src/lib/upload.ts`, which the save upload shares). For each part it asks `POST /api/games/<id>/upload/part` for a presigned `PUT` of that part, valid for an hour and signed for its exact size, and `PUT`s the part straight to the bucket, keeping the `ETag` the bucket answers (exposed by its CORS rule). One percentage shows the bytes sent across all parts.
3. A part that fails, or goes 30 seconds without sending a byte or getting its answer, is retried on its own with a freshly signed URL, up to six tries in all, after 1, 2, 4, 8 and 16 seconds. When a part runs out of tries, the other parts are cancelled and `DELETE /api/games/<id>/upload` aborts the multipart upload, tried three times; the page shows why the upload failed, and says so if the abort could not reach the bucket either, in which case the game's next upload aborts it in step 1. Aborting an upload the bucket no longer knows, because step 4 completed or aborted it, counts as done.
4. `POST /api/games/<id>/file` with the key, the upload's id and every part's number and `ETag` checks that the key belongs to the game and completes the multipart upload, aborting it if the bucket refuses. It then reads the object's real size from the bucket, records it and deletes the game's previous object.

Until step 4 completes, the bucket holds no object for the upload, only its parts, so a half-finished replacement leaves the old file in place and leaves no stray file behind. `npm run seed` puts its stand-in zip in the bucket through the same multipart calls and `uploadParts`, signing the parts in the script rather than through the API. The API's calls to the bucket give up after 5 seconds without a connection or 20 seconds without an answer, tried twice, so a bucket that cannot be reached fails a request rather than hanging it. A download is `GET /api/games/<id>/download`, a presigned `GET` valid for five minutes that saves under the uploaded file's name. Every games route is admin-only; a series' players download its game through the series page ([Series](#series)). The bucket is private: nothing in it has a public URL.

**Item icons.** The item sprites the PC's bag and the team builder draw come from the game itself, so an item Showdown has no icon for has one too. When step 4 records a game's zip, the API reads the zip's `Graphics/Items/*.png` (any folder above `Graphics`, none below `Items`) out of the bucket with ranged reads, never the whole 600 MB: the zip's tail for its directory, the directory, then the icons' bytes in runs that skip gaps over 1 MB (`api/_lib/item-icons.ts`, over `zipDirectory`, `directoryEntries` and `readEntry` in `api/_lib/export/zip.ts`). It packs them into one PNG sheet, a 32-column grid of cells as big as the largest icon (`pngjs`), puts it at `games/<id>/item-icons-<uuid>.png`, and keeps the sheet's index in `game.item_icons` (`itemIcons` in `shared/items.ts`, migration `drizzle/0015_item_icons_and_world.sql`): the uuid, the sheet's size, each icon's rectangle by its file name (the item's game ID, or `machine_<TYPE>` for a TM), and the Showdown ID of each icon that has one, from the export's data. It deletes the sheet the game had before. A zip without the folder leaves `item_icons` null, and a failure to read it leaves the game's old icons, without failing the upload; the game's card shows the count as "Item icons". `GET /api/item-icons/<game>` answers the index and `GET /api/item-icons/<game>/<uuid>.png` the sheet, cached by the browser for a year since a new zip makes a new uuid. `npm run item-icons` (`scripts/item-icons.ts`) rebuilds every game's sheet from the zip it holds. Añil's zip holds 893 icons, mostly 48 px art drawn at 24 px doubled, packed into a 1920×1680 sheet of 578 KB.

**Team builder costs.** A game also keeps what the [team builder](team-builder.md#the-team-page) charges a snapshot's Pokémon for what the player would buy in game: `ability_setas`, the Mini Setas per ability change, and `mint_price`, the money per mint bought for a nature change (`game` in `api/_lib/schema.ts`, migration `drizzle/0012_game_costs.sql`, `gameCosts` in `shared/games.ts`). They default to Añil's, 1 Mini Seta and $30,000 ([World → Marts](../../games/anil/reference/world.md)). Each game card at `/admin/games` has a "Team builder costs" form, 0 to 99 Mini Setas and 0 to 9,999,999 money, saved with `PUT /api/games/<id>/costs`; a team's source takes its series' game's costs, and the defaults when its series has no game.

## Series

A series (`series` in `api/_lib/schema.ts`) has a unique number, a name, its game, its background scene (`night` or `route`), its ingestion mode (`manual`, players upload their saves, or `automatic`, the game sends them), its rules as Markdown, once in Spanish (`rules_es`) and once in English (`rules`), the default pool a new team built from its snapshots starts with (`pool`, jsonb, `teamPool` in `shared/pool.ts`; series 1's, `DEFAULT_POOL`, is every series' until changed: [Team Builder → The Pool](team-builder.md#the-pool)), and a state: `draft`, `running` or `finished`. Its players are rows of `series_player`, and its milestones rows of `milestone`, in order (`position`), each named and marked `none`, `round` (a league round is played at it) or `tournament`. A partial unique index on `state` lets one series run at a time. The shapes the browser and the API share, and `startChecklist`, are in `shared/series.ts`.

**Admins** keep the series at `/admin/series` (`src/pages/admin-series-list.tsx`), which lists every series, newest first, and creates a draft from a name, its number the next free one, then opens its form at `/admin/series/<id>` (`src/pages/admin-series.tsx`): under a preview of the series page's header, drawn live from the form's name, scene and game, the number (fixed), name, game (from `/admin/games`, marked when it has no zip), ingestion, the scene picked from its two scenes drawn small, the players (toggle tiles over the allowlist), the milestones (a preview of the track, then each named, marked Checkpoint, Round or Tournament, reordered, removed, added), the default pool (the team builder's pool bar and the Moves rule under it, editable while a draft) and the rules, a Markdown text area under an Español · English switch, Spanish first, holding each language's text, that "Copy from" fills with another series' rules in both. Beside them, sticky from `lg` and first below it, the checklist shows what starting still needs: rules written in either language, a game with its file, at least one milestone, and, while another series runs, that series finished. It is worked out from the form as it is being filled, by the same `startChecklist` the API runs, and Start, which saves the form first, enables once every item is done. Save keeps a draft without starting it, and a draft can be deleted, at a second press; below `lg` Save and Start sit in a bar along the screen's bottom. Once a series runs only its rules, its players and its milestones change, through Save (`PUT /api/admin/series/<id>/rules`, then `/players`, then `/milestones`), which adds any allowed player, marking their place in a manual series as owing a save (below), and refuses to drop one with a snapshot in it, and edits the milestones in place, by id, so a snapshot stays on its milestone through a rename, a new mark or a new order: a milestone is added, renamed, re-marked and moved freely, except that one with a league round at it stays marked Round, and removed only when no snapshot is at it ("Move or delete the snapshots at <milestone> first") and no league round is played at it ("League rounds are played at <milestone>"); a finished series changes only its rules, through Save rules, and Finish, confirmed by a second press, ends it; a finished series stays finished. The routes are `GET` and `POST /api/admin/series`, `GET`, `PUT` and `DELETE /api/admin/series/<id>`, `PUT /api/admin/series/<id>/rules`, and `POST /api/admin/series/<id>/start` and `/finish` (`api/_lib/admin-series.ts`), every one admin-only; start refuses a draft whose checklist is not done, and the index refuses a second running series even if two starts race.

**Joining mid-series.** A player of a running manual series uploads their save before they reach the site. Adding them to the running series sets `needs_save` on their `series_player` row, and so does starting a manual series for every player its draft holds (`POST /api/admin/series/<id>/start`, in the same transaction); a player of an automatic series gets no mark. `GET /api/series/owed` (`api/_lib/series.ts`) answers the running manual series whose mark the reader still holds, each with its number, name and milestones (`owedSeries` in `shared/series.ts`), and `src/main.tsx` asks for it beside the session as the page loads, and `SiteShell` takes that answer for an allowed player, holding the loading bar until it is in, and asks again whenever the session becomes another player or one newly allowed, as when a waiting player is let in and their tab regains focus, which refetches the session; a player already in the site who is added to a series is held from their next reload, and an answer that fails for any reason but a refused session counts as owing nothing, so a failing read never locks a player out. While it lists any, the shell shows the waiting page as "Upload your save": "<series> is under way. Upload your save to join it." and Upload save, or, when several are owed, one "Upload to <series>" button each. Each opens the series page's upload dialog for the player's own row, loaded only then, with the series' milestones and the save's suggestion preselected; its done step keeps the rolled zip's Download, and Close or Open PC asks for the list again, so the site opens once it is empty. The first snapshot in the series clears the mark, whoever uploads it, so an admin can upload an old export for the player instead. The hold is the shell's: the API answers a held player as any allowed one. An admin onboards a new player by letting them in and adding them to the running series; one added by mistake is dropped from the series form while they have no snapshot, which lifts the hold.

**Players** reach the running series from `/`, which sends a signed-in reader to its page, or to `/series` while none runs (`src/pages/home.tsx`). `/series` (`src/pages/series-list.tsx`, after `series-list.dc.html`) shows one banner per series that is running or finished, newest first, on its scene, with its name, its game and "Playing now" or "Finished"; the whole banner is a lifting link. `/series/<n>` (`src/pages/series.tsx`, after `series.dc.html`) is a header drawn on the series' scene with its name and its game in a box, with Download for the series' players and admins; the League summary ([League](#league)); the Trainers, one row per player with their badge and their name (a link to their profile, [Snapshots → The player's profile](#snapshots)), "You" on the reader's own row, and the milestones as a track, the rounds tinted and numbered and the tournament a cup. A draft's page answers 404 to players and opens for admins. The routes are `GET /api/series`, `GET /api/series/<n>` and `GET /api/series/<n>/download` (`api/_lib/series.ts`), the last a five-minute presigned link to the game's zip for the series' players and admins, 403 for anyone else.

## Snapshots

A player has one save per series (`save` in `api/_lib/schema.ts`, unique per series and player), and a save holds snapshots (`snapshot`), at most one per milestone, each the export of one `Partida N.rxdata` slot of a save zip, or else an old export's JSON read as far as it goes: the file's key, name and size in the bucket, the slot's entry in the zip (null for an export), the export as `data` (jsonb, the [Snapshot Format](../reference/snapshot.md)), the rest of the save as `world` (jsonb, read by no page and sent by no route; [Snapshot Format → World](../reference/snapshot.md#world), null for an export), an old export's missing-field report (`missing`, null for a zip; [Snapshot Format → Old Exports](../reference/snapshot.md#old-exports)), the slot's TM rolls (`tm_rolls`) and the key of its rolled zip (`rolled_key`), its Pokémon and fainted counts, who uploaded it (null when no one did, as for the seed) and when it was taken, and the admin overrides below. Every way a save comes in goes through one pipeline, `ingest` in `api/_lib/ingest.ts`: given a file already in the bucket, a slot and a milestone, it reads the file back; a zip's slot it exports and puts the rolled zip in the bucket, and an export (a `.json` key, no slot) it reads with `readExport`, with no TM rolls and no rolled zip; then it writes the snapshot, replacing the one at that milestone and deleting the replaced zip and rolled zip once no snapshot holds them, and clears the player's `needs_save` mark in that series in the same transaction ([Series → Joining mid-series](#series)); the manual upload below and `npm run seed` are its two sources so far, and nothing in it knows which one called it.

The export (`api/_lib/export/`, [Save Export](save-export.md)) is the retired Python export ported to TypeScript, with moves always exported: `marshal.ts` the save's Ruby Marshal reader and the side file's writer, `export.ts` the Pokémon, items, TMs and moves as the Python wrote them, TM compatibility rolled for what the slot's rolls lack (below), plus what the Python left out (the fallen, every item, all eight pockets, the trainer, play time, the Pokédex, the battle counts, the Hall of Fame, the used first encounters), `zip.ts` a zip reader and writer, and `save-zip.ts` the slots a zip holds (`Partida N.rxdata` in any folder, ordered by folder then number, with each one's saved time from the zip and its badges and Hall of Fame) and the export of one with its rolled zip. `generate_export_data.py` writes `data.json` beside them ([Save Export → Data Shipped With the Export](save-export.md#data-shipped-with-the-export)). On MIRAMEEE's save (a 15 MB `Partida 1.rxdata`, 2.1 MB zipped) the slots are listed in about 0.2 s and the export takes about 0.2 s.

**TM rolls.** A roll counts only once the game loads it and the player saves ([Save Export → Rolling TMs](save-export.md#rolling-tms)), so the site keeps what it rolled. The export starts from the slot's existing rolls, rolls each bag TM still missing for a Pokémon it exports, and `ingest` stores the result in the snapshot's `tm_rolls`, as `[species, [[move, compatible], …]]` pairs in the side file's order (jsonb would reorder an object's keys). Where the existing rolls come from depends on the zip: a zip the site already exported for that slot, the same key in the bucket, starts from the rolls a snapshot of it keeps, so exporting it again rolls nothing and its TM moves stay as they were; any other zip, a new upload, starts from its own `tm_compatibility_<slot>.dat`, else the save's copy, as the game loads them. The site never compares one zip's rolls with another's. The rolled zip is the player's zip entry for entry, as stored with each entry's name, DOS time and external attributes (extra fields dropped), the slot's side file replaced, or added beside the save when the zip has none, holding every roll in the Marshal bytes Ruby writes (the writer rewrites MIRAMEEE's 44,179-byte side file byte for byte). It goes in the bucket beside the zip, at `saves/<series id>/<player id>/<uuid>-rolled.zip`, and downloads under the uploaded zip's name through `GET /api/series/<n>/trainers/<player>/snapshots/<milestone>/zip`, which answers a link (`downloadUrl`) to the player and to admins and 403 to anyone else. The player extracts it into the save folder with the game closed, loads and saves, and their next upload holds the rolls: on MIRAMEEE's zip the export rolls 3,047 pairs, and the rolled zip exported again rolls none and gives the same TM moves.

**Uploading.** On the series page the Snapshots tile's Upload button opens the upload dialog (`UploadDialog`, `src/components/upload-dialog.tsx`, after the `upload-*.dc.html` boards): on a player's own row in a running manual series, on every row for an admin in any series that is not a draft, and nowhere else (`mayUpload` in `api/_lib/series-data.ts`, which the routes check too). The dialog takes a zip or an old export's `.json`, by drop or file pick ("Drop a save zip or an export"), and uploads it at once, through the same multipart calls as a game's zip ([Games](#games)) under `/api/series/<n>/trainers/<player>/`: `upload`, `upload/part`, `DELETE upload` and `file`, the zip at `saves/<series id>/<player id>/<uuid>.zip`, at most 100 MB, an export at `<uuid>.json`, at most 10 MB. While it goes up the milestone can be picked. `file` completes the upload, reads the zip back and answers its slots, each with the milestone it suggests (`suggestMilestone` in `shared/save-upload.ts`: a save in the Hall of Fame suggests the first milestone with "League" in its name, else N badges suggest "Gym N"), or refuses a zip with no slot ("No Partida save in this zip") and deletes it; for an export it answers its Pokémon count and missing-field report instead, or refuses one the site cannot read ("This file is not JSON", [Snapshot Format → Old Exports](../reference/snapshot.md#old-exports)) and deletes it. The dialog then shows the slots to pick from when there are several, the first picked, preselects the picked slot's suggestion unless a milestone was already chosen by hand, marks it "From the save · 8 badges" or "From the save · Hall of Fame", marks the milestones that have a snapshot, and warns in amber when the pick replaces one ("Replaces Post-League · 79 Pokémon"). Save (or "Replace <milestone>") calls `POST /api/series/<n>/trainers/<player>/snapshots`, which runs `ingest` and answers the milestone, the counts and whether it replaced one; an export that fails shows its reason in the dialog, which stays open on the pick. The done step shows "<milestone> saved" or "replaced", the Pokémon count, and for a zip a row with how many TM pairs the export rolled, the side file's name and "Download zip", for an export (`upload-done-json.dc.html`) an amber chip naming what it lacks ("Missing: IVs, EVs, stats · moves") and a grey one with how many entries were skipped, and "Open PC", which opens the player's PC at that snapshot, and the page reloads the series. On the series page, from `sm`, each snapshot chip of a player's own row, or of every row for an admin, carries a download button for its rolled zip. Below `sm` the dialog is a bottom sheet. An admin's dialog is titled "Upload for <player>" with their badge. Starting an upload aborts the player's open multipart uploads and deletes their files more than an hour old that no snapshot holds, as its zip or its rolled zip.

**Admin overrides.** An admin can set by hand the values a save gives (a player's progress in a series, a snapshot's fainted count, a snapshot's milestone) and delete any snapshot, in running and finished series; each value set by hand keeps who set it and when, and wins over the save's until an admin clears it. Progress is the save's (`progress_id`, `progress_set_by`, `progress_set_at` on `save`, the row made if the player has no snapshot yet): unset, it is the milestone of the latest snapshot; set, the track, the phone row's milestone and the profile's Reached show it, whatever later uploads bring. The fainted count is the snapshot's (`fainted_set`, `fainted_set_by`, `fainted_set_at`): set, it stands in for the export's count on the row's Fainted tile, in the Journey and in the profile's Fallen, while the Fallen list stays the export's; `ingest` replacing that snapshot keeps it. Moving a snapshot changes its milestone and records `moved_by` and `moved_at`, which a later upload replacing it clears, since its uploader then picked that milestone; a milestone that already holds one of the player's snapshots refuses it (409, "delete it first"). A move also starts over each round or cup team resting on the snapshot whose match has no result, and a delete each such team whatever its milestone, the copy's members from the deleted snapshot turned into free members ([League](#league), "Round teams"). Both are refused (409, "A league team built on this snapshot is on a match with a game, a ban or a six in") while a round or cup team built on the snapshot is on a match without a result that has a game recorded or a ban or a six in, and a delete is refused too (409, "A league team built on this snapshot is on a match with a result") under a team whose match has a result, so no league team its games stand on ever changes under them. Deleting a snapshot deletes its zip and rolled zip once no other snapshot holds them, as replacing one does, so the seed's Gym 8 copy, which shares its zips with Post-League and Series 2's Tournament, deletes no file while those stand. A player's hatched eggs in a series are the save's too (`hatched_set`, `hatched_set_by`, `hatched_set_at`, the row made if needed): set, they stand in for the latest snapshot's count on the league's standings, whatever later uploads bring; the league page sets them ([League](#league)). Series 1's import writes the Trainer League app's counts there too, with `hatched_imported` true and no `hatched_set_by`; such a count gives way by itself once the snapshot the standings read, the player's latest milestone's, was uploaded (`taken_at`) after it, and an admin setting or clearing the count turns it into their own or empties it. Check constraints on both tables refuse a value set by hand without who and when, and a hatched count with both or neither of an admin and the import's mark. The routes are `PUT` and `DELETE /api/series/<n>/trainers/<player>/progress` (`{ milestone }`), `PUT` and `DELETE …/hatched` (`{ count }`, 0 to 999), `PUT` and `DELETE …/snapshots/<milestone>/fainted` (`{ count }`, 0 to 999), `POST …/snapshots/<milestone>/move` (`{ milestone }`) and `DELETE …/snapshots/<milestone>` (`api/_lib/overrides.ts`), each behind `requireAdmin`, answering 403 to players. On the series page an admin's open row ends in a dashed amber Admin panel (`TrainerAdmin`, `src/components/trainer-admin.tsx`): Progress, a select of the milestones with "From the save (<milestone>)" first; the shown snapshot's fainted count with Set and, when set by hand, Clear; and the shown snapshot's milestone with a select of the milestones without a snapshot, Move, and Delete, confirmed by a second press. Under Progress and the fainted count, "From the save", or "Set by hand by <admin> · <date> · save: <the save's value>" in amber; under the milestone, "Moved by <admin> · <date>" once it was moved, else nothing. `GET /api/series/<n>` answers each trainer's `progress`, and to admins alone each one's `sources` and each snapshot's, the save's value beside who set what and when (`shared/series.ts`).

**Whose saves a reader sees.** A player sees another player's snapshot only from their own round or older; someone outside the series only once every player of the series has reached its round; admins, and a snapshot's own player, always ([discovery → Team Locking](../../../work-in-progress/league/discovery.md#team-locking)). A player's round is the round of their latest snapshot, at whatever milestone it sits, so a Tournament save alone reaches every round (owner, 2026-10-29); a snapshot's round is the latest round milestone at or before its milestone, so series 1's Gym 4 is round 3 and anything before Gym 1 round 0, which everyone sees. A series without round milestones has every snapshot at round 0 and hides nothing. That much holds in open and closed rounds alike. A closed round hides more while a match of it has no result: each of its two players' snapshot at the round's milestone is seen only by that player and admins, hidden from the other player and everyone else alike, and each one's snapshots at any later milestone are hidden from the other, so moving on does not give the box away. So that the saves never give away what the round's pairs keep back ([League](#league), "A closed round hides its pairs"), the one who rests has their snapshot at the round's milestone hidden from a reader while the round hides who rests from them, and a player whose own pair is still hidden from them, who has not locked their round team, misses the later saves of every other player of the round too, not only their opponent's. Once every match of the round has its result, the round hides nothing more. The rule moves as snapshots come in, are moved or are deleted and as results are recorded, since it is worked out on every read: `savesSeen` in `shared/league.ts` holds the rule, and `savesSeenBy` in `api/_lib/series-data.ts` reads a series' milestones, players, snapshots and round matches for it, answering every snapshot seen to an admin. Every route that hands out a snapshot or what it holds checks it on the server, a hidden snapshot answering as one that does not exist: the PC, the series page's trainer rows (their snapshots, and their progress when no admin set it by hand, the latest snapshot the reader may see), the player's series page (its Journey and Fallen), the profile's series banners and Career, and the [Abilities](#abilities) search; a team refuses a hidden snapshot as a source as one that does not exist, and a team page answers one it already rests on cut to the team's own Pokémon ([Team Builder → Stored Teams](team-builder.md#stored-teams)). The league page's eggs, worked out from snapshots, and a match page's members are the league's, not a save's, and do not follow it. A Pokémon League try's members and team follow it as a snapshot past the series' last round milestone does ([League](#league), "Pokémon League tries").

**The PC.** `/players/<player>/series/<n>/pc?snapshot=<milestone>` (`src/pages/pc.tsx`, after `pc.dc.html`), with `<player>` the player's user id, shows one player's PC at one snapshot of a series, read-only, to every signed-in reader who may see that snapshot (Whose saves a reader sees, above). Above it, a breadcrumb of two links, the player's name opening the player's series page and "Series <n>" opening the series page, the player's badge and "<player>'s PC", "You" on the reader's own, and, centred against the title, a picker over the series' milestones (named "Snapshot" to screen readers, with no visible label), those without a snapshot disabled, picking one changing `?snapshot=`; without it the page shows the latest snapshot, and "No snapshot yet" when there is none; what an old export lacks is warned of where it shows, in the summary's Stats and Moves and in the bag ([Snapshot Format → Old Exports](../reference/snapshot.md#old-exports)). Below, the PC box with its search, type filter and Bag button, the summary beside it from `lg`, the two filling the rest of the screen's height (no less than 36rem of page, so a 720px-tall screen does not scroll), or in a bottom sheet below, and the bag dialog with nothing to give, its head showing the snapshot's Mini Setas and money beside the title rather than the Mini Setas as an item, its items the fight items ([Snapshot Format → `items[]`](../reference/snapshot.md#items)) and its icons the game's own sprites ([Games → Item icons](#games)), a TM's the game's disc of its type, each falling back to Showdown's icon while the sheet loads or when the game has none: `SnapshotPc` in `src/components/pc/pc-box.tsx`, over the pieces the team builder's add dialog is built from too ([Design System → Shared](../reference/design-system.md#shared)). The box shows the living Pokémon; when the snapshot has fainted ones, a **Fainted · <n>** toggle beside Bag, off on every visit, adds them after the living, each cell greyed with a red cross and its summary's types followed by a "Fainted" chip (`FaintedToggle` and `FaintedMark` in `src/components/pc/pc-box.tsx`); a fainted Pokémon with no Showdown species is not shown. On the signed-in player's own snapshot a living Pokémon's summary ends in "Add to team" ([Team Builder → Adding From the PC](team-builder.md#adding-from-the-pc)); a fainted one's has none, since it cannot be fielded. The page reads `GET /api/series/<n>/trainers/<player>/pc?snapshot=<milestone>` (`api/_lib/series.ts`), which answers the player, the series, its milestones with whether each has a snapshot, the milestone shown, the snapshot's Pokémon, its fainted ones after them marked `fainted` and numbered on from the living, items and TMs already described (names, types, abilities, stats, type defenses, sprite and icon URLs, moves; each move once, the Pokémon naming theirs by ID) by `describePc` in `shared/describe.ts`, which the route imports only when it runs, and the snapshot's missing-field report, parsed in the browser by `pcPage` in `shared/pc.ts`, over `pcView` in `shared/mon.ts`, so the page loads no game data; it answers 404 for a series a reader may not see, a player not in the series, or a milestone without a snapshot the reader may see, and its milestones mark only those as having one. Its Pokémon's IVs, EVs and stats reach only the player and admins: to anyone else the route describes the snapshot without them, each Pokémon marked `spreadHidden`, and the summary's Stats says only its trainer and admins see them ([Team Builder → Stored Teams](team-builder.md#stored-teams)). The header's PC tab opens the signed-in player's own PC in the running series, or `/series` while none runs, and is open on every PC page. `?mon=<index>` opens the PC with that living Pokémon picked, its cell scrolled into view and, below `lg`, its summary's sheet open, as the [Abilities](#abilities) page's links do; picking another snapshot drops it. Wherever a summary knows its series (the PC page, and in the team builder a snapshot member's summary and the add dialog's), each ability's description ends in "Who shares <ability>", opening that series' Abilities page on it; a free member's summary has none.

## Abilities

`/series/<n>/abilities?ability=<id>` (`src/pages/abilities.tsx`, after `abilities.dc.html` and `abilities-phone.dc.html`) is one PC box holding every trainer's Pokémon in a series, so the PC's own filters answer "who can have this ability" across the series, to every signed-in reader. Since the Randomlocke rolls each run's ability table ([Save Export → What Goes Out](save-export.md#what-goes-out)), the answer is per Pokémon, never per species: the box holds the living Pokémon of every trainer's latest snapshot in the series that the reader may see ([Snapshots](#snapshots), "Whose saves a reader sees"), the one at their latest such milestone, as the PC shows it without `?snapshot=`, the reader's first, and each Pokémon's possible abilities as its snapshot lists them, base, hidden and its current one. The fainted are left out, since they cannot be fielded.

Under a breadcrumb back to "Series <n>" and the title "Abilities", it is the PC page's layout: `PcBox` with its search, type and Ability filters and the In use toggle (below), plus a Trainer select ("All trainers"), each cell marked with its trainer's badge at its bottom left (`PlayerBadge` size `cell`); the Ability filter is `?ability=`, so a link can open the box on one ability. A link "Abilities" beside the series page's Trainers heading opens it, and each summary's "Who shares <ability>" opens it on that ability ([Snapshots → The PC](#snapshots)).

**Filtering by ability anywhere a box shows.** Every PC box, the PC page's, this page's and the team builder's add dialog's, has an Ability filter beside Type: a searchable dropdown (`ComboField`) of every ability its Pokémon can have, each with how many of them can, "All abilities" first; picking one keeps the Pokémon that can have it, and an **In use** toggle then keeps only those using it. The filter is the box's own, reset with it.

It answers 404 for a series the reader may not see.

## League

A series' league is its rounds and their matches, built on its milestones: round N is played at the series' Nth milestone marked `round`, so series 1's five rounds are at Gyms 1, 2, 3, 5 and 7. A round (`league_round` in `api/_lib/schema.ts`) names its milestone, one round per milestone, its mode (`mode`, `open` or `closed`, the `league_mode` enum, the options named by `LEAGUE_MODES` in `shared/league.ts`; series 1's imported rounds and the seed's are open) and the player resting on it, if any (`bye_id`); a match (`league_match`) names its round, or for a cup match its cup and its place in the bracket ([The cup](#league) below), its order in it (`position`), its two players (`player_a`, `player_b`), the Bo3's games each side won (`games_a`, `games_b`: both empty while it is unplayed, otherwise 2–0 or 2–1 either way, held by a check), the Pokémon each side lost (`fainted_a`, `fainted_b`) and when it was made (`created_at`). A game (`league_game`) names its match, its place in the Bo3 (`number`, 1 to 3, one game per place), its winner (`winner_id`), the Pokémon each side lost in it (`fainted_a`, `fainted_b`, 0 to 6 each, held by a check), its Showdown replay link (`replay`, or none) and who recorded it and when (`recorded_by`, `recorded_at`). A cup game's side (`league_game_side`, one per match, game number and player, made by the side's first ban or pick, before the game has a row of its own) holds that player's ban, the place in the other's team of eight of the Pokémon they banned (`ban`, 0 to 7, held by a check), and their six (`picks`, the places in their own team), each with when it went in (`banned_at`, `picked_at`). A Pokémon League try (`league_try`) names its series, its player, the team it was played with (`team_id`, emptied if that team is deleted), the combats won (`combats_won`, 0 to 5, held by a check), its members as they were when it was logged (`members`, one to six `{ species, fell }`, `fell` the combat the member fainted in or none) and who logged and last edited it and when (`logged_by`, `logged_at`, `edited_by`, `edited_at`). A series' cup (`league_cup`, one per series) names its mode (`mode`, `open` or `closed`, as a round's), who started it and when (`started_by`, `started_at`), and its entrants (`league_cup_entrant`) each player's seed, 1 to the number entered. Deleting a player deletes their matches with their games, their tries and their place in a cup, as it deletes the rest of what they have; a milestone with a round at it cannot be removed ([Series](#series)).

The league's rules are named values in `shared/league.ts`, the only place they live ([Series 1 Rules → The League](../../series/1/reference/rules.md#the-league)): a point per Bo3 win (`POINTS_PER_WIN`) and one per combat won in the player's best Pokémon League try (`POINTS_PER_COMBAT`), five combats in the Pokémon League (`LEAGUE_COMBATS`), at most six Pokémon brought to it (`PARTY_SIZE`), a Bo3 of three games won at two (`MATCH_GAMES`, `GAMES_TO_WIN`), at most six Pokémon lost by a side in a game (`FAINTED_PER_GAME`), a round team of six (`ROUND_TEAM_SIZE`), the rulebook's matchday team, a cup team of eight (`CUP_TEAM_SIZE`) of which a cup game brings six (`CUP_BROUGHT`), bans only in an open cup (`cupBans`), the Showdown format and clauses every match is played under (`SHOWDOWN_FORMAT`, `SHOWDOWN_CLAUSES`), the ban a player may not repeat, their ban of the game before when they won it (`barredBan`), a pick of six distinct places of the team, none of them banned (`pickProblem`), and `standings`, which ranks the league's players by points and breaks a tie by the rulebook: two tied players by their direct result, three or more by their wins in the matches among them, and those still level, or a pair that has not met, by a stable random draw, a hash of the series and the player (`drawOrder`). Games won and Pokémon fainted show beside the points and never break a tie. Each row carries, for a tied player, whom among the tied they beat and lost to, the combats won in their best try (`best`, none without a try), and the eggs won: one per league win (`EGGS_PER_WIN`) and one per combat won in the best try (`EGGS_PER_COMBAT`), none for a cup win (`eggsWon`). A player's best try is their try with the most combats won, the earliest of those tied (`bestTries`); a member can only have fallen in a combat the try reached, the one after the last won, or the fifth once all five are won (`fellProblem`).

**Opening and drawing a round.** An admin opens the league's next round, the first round milestone with no round yet, in the mode they pick; opening draws its pairs at once (`drawRound` in `shared/league.ts`): at random among the league's players, never two who have met in another round, and with an odd count one player resting, never one who has rested before. The draw looks ahead: it picks a round only if the rounds still to open can follow it without a repeat, as many of them as can, so a six-player league's five rounds meet every pair once, and so do a five-player league's five, each player resting once; with no such round left it refuses. **The cup.** An admin starts a series' cup once, picks who enters and its mode; its bracket follows from how many enter, two, four or six, the sizes the rulebook draws (`CUP_MIN` and `CUP_MAX`, `cupProblem`, `cupSlots` and `cupDraw` in `shared/league.ts`), seeded by the league's standings at the start, entrant 1 the highest placed. The first round pairs seed k with seed n + 1 − k. Two or four entrants play a plain knockout, the first round's matches placed so that seeds 1 and 2 can only meet in the final (`seedOrder`). Six play the rulebook's pattern ([Series 1 Rules → Final Tournament](../../series/1/reference/rules.md#final-tournament)): the first round's losers play a round robin, the losers' group, whose best goes through to fill the bracket to four beside the first round's three winners; the group ranks by wins, then head-to-head (wins over the others on as many wins), then game difference, then the opponents' Pokémon fainted minus their own, then the higher seed (`groupTable`), and sends no one through until every group match has a result. The bracket pairs the winner of seed 2's first-round match with the group's best and the other two winners against each other, so six entrants give series 1's cup: 1–6, 2–5 and 3–4, the losers' triangular, and the semifinals 1–6's winner against 3–4's and 2–5's against the triangular's. A cup match is a `league_match` with its cup and its place (`slot`: `f<k>` the first round's match of seed k, `g<i>-<j>` a group match between the losers of `f<i>` and `f<j>`, `b<r>-<m>` the bracket's round r) in place of a round, made once both its players are known; it is played and fixed through the match module as a league match is ([The match page](#league)), and after each of its moves the module works the bracket out again from the cup's results in the same transaction (`settleCup` in `api/_lib/cup.ts`), making the matches whose players are now known, and changing or removing those whose players changed while they have no game, a changed match losing its bans and picks; a fix that would change a match with a game is refused with 409 ("A later cup match already has a game; fix that one first"). Each cup match gives each of its players a team of eight to build, once the match exists and so does the player's snapshot at the series' tournament milestone, the latest milestone marked `tournament`: one pass over the cup (`giveCupTeams` in `api/_lib/cup.ts`) makes the teams still missing, runs in `settleCup`'s transaction, after every snapshot upload (`ingest`) and after an admin moves or deletes a snapshot, and deletes the team of a player who is no longer in a match; the team itself and its lock are the team builder's ([Team Builder → Stored Teams](team-builder.md#stored-teams)). Who sees a cup team before its reveal is its owner and admins alone: in an open cup it shows once every cup player has locked, that is once every cup match made no later than its own and still without a result has both its teams locked, so a first round's teams show all at once and a later match's once its two players lock; in a closed cup once its match has its result. A round match's teams follow their round's mode alike, once both players have locked in an open round and once the match has its result in a closed one, and any match's teams show once it has its result (`teamsSeenBy` in `api/_lib/series-data.ts`, [Team Builder → Stored Teams](team-builder.md#stored-teams)). Cup matches belong to no round, so the standings, the eggs, the head-to-head and the reader's rounds never count them. `POST /api/series/<n>/league/cup` with `{ players, mode }` starts it (`startCup`), 403 to anyone but an admin, 400 for a mode other than open or closed, a player who is not one of the league's, one named twice, or an odd number, fewer than two or more than six ("The cup needs an even number of players, from 2 to 6"), 409 once the cup has started, and answers with the league page; the league read carries the cup (`cup`, `null` before it starts): its mode, the seeds in order, every place in the bracket with its match, players and result as far as known and the games each side has won so far (`wonA`, `wonB`), the group's table with who went through (`through`) and the champion.

The page reads `GET /api/series/<n>/league/matches/<id>`, open to every signed-in reader of the series, its `teams` giving each side's team as `shown` (its members described for the column), `hidden` (with whether it is locked and when it shows, `reveal`: `all`, `both` or `result`) to a reader who may not see it, `waiting` (with the milestone's name: the tournament milestone's for a cup player without one, the round's for a round player without one on a match still to play), or `none`, and the admin's editor calls `POST /api/series/<n>/league/matches/<id>/games` and `PUT /api/series/<n>/league/matches/<id>/games/<number>`, which answer 403 to anyone but an admin; each answers with the match page as it now stands, so the score and the players' places and points move at once.

**Bans and picks.** A cup game opens once the game before it has its result, the first once both its teams are locked and, in an open cup, shown (the open cup's reveal, `revealed` in `api/_lib/series-data.ts`), and stays open until its result is recorded. In an open cup each player then bans one of the other's eight on the page: the other team's cards turn to buttons, the one picked tagged "Ban" in red and named in the panel's dashed "Your ban" box over "Ban <name>"; the winner of the game before finds the Pokémon they banned in it dimmed and tagged "Your game <n> ban", while the loser may ban theirs again. The panel, "Game <n> · Bans", shows each player "Choosing", with a blinking hourglass, or "Banned"; whoever bans first sees their ban tagged "Your ban" and the button reads "Waiting for <player>", and nobody else, the other player and admins included, learns which Pokémon it is until both are in. Then each banned Pokémon shows greyed and tagged "Banned" on both pages, and each player picks six of the seven left, ticking their own cards ("<n> of 6 in", the first six ticked to begin with, the seventh off once six are ticked) and pressing Confirm these 6; a closed cup has no bans and goes straight to the pick of six of the eight. The panel reads "Game <n> · Your 6" to a player still to pick and "Game <n> · Picking 6" otherwise, each player "Banned" with the sprite of their ban until they pick, "Choosing" in a closed cup, and "6 in" after; a six shows only to its player until both are in, and then on each team the player may see, the Pokémon left out dimmed and tagged "Not brought", the six outlined in green. With both in, "Game <n> · Play" names the Showdown format and clauses ("[Gen 9] Custom Game", "Species · Sleep · OHKO · Evasion Moves · team preview") and gives each player **Copy my 6 for Showdown**, the team page's Showdown text of their six alone, read from their team's page (`GET /api/teams/<id>`); the game's card reads "Bans", "Picking 6" or "Playing" in place of "To play". On a phone the team being banned from, or picked from, moves above the panel. While a game is open the page reads itself again every five seconds (`REFRESH_MS` in `src/pages/league-match.tsx`, skipped while the tab is hidden), so each side sees the other's ban, six and the admin's result land without a reload, since Vercel holds no websockets; a choice not yet sent survives the refresh.

Each step is a move of the match module, under a lock on the match's row: `banIn` writes a player's ban and `pickSix` their six (`api/_lib/match.ts`), each taking the player and who makes it, so the rules hold whoever calls them. `POST /api/series/<n>/league/matches/<id>/games/<number>/ban` with `{ player, slot }` and `POST …/games/<number>/pick` with `{ player, slots }` answer 401 signed out, 404 for no such series, match or game number, 400 for a body that does not read (`slot` 0 to 7, `slots` six of them), 403 when the reader is not that player, an admin included, 409 for a round match ("Only a cup match's games have bans and picks"), a ban in a closed cup, a game not open (decided, not the next, or its teams not locked and shown), a second ban or six, a pick before both bans are in, or a winner's repeated ban, and 400 for a ban of no Pokémon of the other's or a pick with a repeat or a banned Pokémon; each answers with the match page as it now stands. The read route gives a cup match's game in play, or its last game once none is left to play, as `draft`: its number, whether it has bans (`bans`) and is open (`open`), and for each side whether they have banned and picked, their ban and six where the reader may see them, and to the player alone the Pokémon they may not ban (`barred`); a round match's `draft` is `null`. A result recorded before both bans or both sixes are in is taken as any result, and closes that game's bans and picks. An admin cannot unlock a team of the match while a game of it without a result has a ban or a six in ([Team Builder → Stored Teams](team-builder.md#stored-teams)).

An imported match whose games do not account for its whole score, since some of its games had no replay, keeps the app's score and fainted: a move still rewrites its games but leaves its result, and refuses a winner that would give a side more games than the score, and the page shows a dashed "No replay" card, with who won, for each game it is missing, and its recorded games without numbers, since the dump does not say where the missing ones fell.

**Importing series 1 from the Trainer League app.** `npm run league-import` (`scripts/league-import.ts`) reads the app's dump from the gitignored `pkmn/site/saves/league-export/`, finding its `data/league.json` at any depth, and writes series 1's league from it: each matchday a round at the round milestone of its number, each league match a match with the app's id, order, players, score and fainted, written through the match module's `importMatch`, a match the app holds as unplayed or still pending confirmation left unplayed. Each replay with its Showdown log in the dump (`data/replays/<id>.log`) becomes a game of its match, in the order the battles started (the log's first `|t:|`): its winner from `|win|`, each side's fainted by counting `|faint|` lines, its link as the game's replay; the log's two Showdown names are matched to the match's players through the Showdown names in the script, from the dump's `INTEGRATION.md`, ignoring case. A match whose replays cover all its games takes its fainted from them, the app's otherwise. The import reports and leaves out a replay whose players are not its match's or that has more than six fainted on a side, and the games of a match whose replays' wins disagree with the app's score; it also reports each match whose fainted from the replays differ from the app's, which is round 3's Elfo v Dloez alone, 17–11 from its replays against the app's 0–0. It maps the app's players to site accounts through the user map in the script (Vicky, Dloez, Javi, Inop, Tole and Elfo to the usernames `vicky`, `dloez`, `javi`, `inop`, `tole` and `elfo`), making each missing account as an allowed test player of that name and adding the six to series 1's players. It gives each side of each match one team, an Any Pokémon round team of its player's on the match, keyed `<match id>-team-a` or `-team-b`, named "<milestone> team" as the round's other teams are, and locked, with no admin, at its first battle's start: built from the match's replays together, in its first replay's `|poke|` order (species and level), each member holding the first item, the first ability and up to four moves, in the order they appear, that any of the replays shows that Pokémon with (`|move|`, `-ability`, `-item`, `-enditem`, an `ability:` or `item:` effect such as `-start`'s Flash Fire, the move Forewarn reveals, and any `[from] ability:` or `[from] item:`, an `[of]` Pokémon taking it when one is named, but for a `-heal`, Frisk aside, whose own Pokémon holds it), leaving out a move another move or an ability called, Struggle, the moves and abilities a Pokémon shows while transformed, the abilities it shows after its ability changed (Trace's own ability kept, the traced one given to the Pokémon it came from; Skill Swap and the like), and the items it shows after it took another's (Trick and the like); each member's set is written as a Showdown set and read by `readShowdownTeam`, so it takes the paste-in's nature (Serious), EVs (none) and IVs (all 31), which a replay never shows, and keeps no ability when the replays show none. A side whose match has no replay of its player takes their matchday paste from the dump (`teams[].text`, hidden ones included), read the same way and locked at the paste's last edit: round 5's Dloez v Vicky on both sides and Javi's side of the unplayed Elfo v Javi, whose Elfo has none and gets his round team once his Gym 7 snapshot exists. The import reports a Pokémon a later replay brings that the first does not, one showing two items or abilities across the replays, one showing more than four moves, and anything the paste-in leaves out; the dump's replays report none, all 29 teams coming across, 26 from replays and 3 from pastes. Once it has written the rounds it runs the round teams' pass. It brings each of the dump's Pokémon League tries (`pokemon_league.tries`) as a try keyed by the app's id, stamped with its time, its combats won and where each member fell, and its `team_text` read by the same `readShowdownTeam` into an Any Pokémon team of its player's, keyed `<try id>-team`, named "Pokémon League try <n>" and locked at the try's time; each member keeps the ability and moves its paste gives, series 1's randomized ones, since an Any Pokémon member may hold any ability and any move ([Team Builder → The Team Page](team-builder.md#the-team-page)), and anything the paste leaves out is reported; a try whose paste does not read as its members is reported and left out. It writes each player's hatched count as the app holds it (`players[].eggs.hatched`: Vicky 9, Javi 9, Dloez 8, Elfo 2, Inop 0 and Tole 0) as an imported override on their series 1 save, stamped with the import's time, replacing an earlier import's count or none, but leaving alone a count an admin set ([Snapshots → Admin overrides](#snapshots)); a snapshot the player uploads after it takes over. It replaces series 1's rounds and tries, with the matches' and the tries' teams, each time, so a rerun writes the same rows, its games keyed `<match id>-g<n>` and stamped with their battle's start, and prints the rounds, matches, games, match teams and tries it wrote, the hatched counts it wrote and the players whose admin-set count it kept, the standings, and any player whose points, wins, losses or games differ from the app's: none, with the tries' points in. Like `npm run seed`, it refuses a database or store off the local stack unless `LEAGUE_TARGET` is `preview` and the bucket is the preview's (`scripts/target.ts`, which both share).

## Languages

The site reads in English or Spanish (Spain). The reader picks one from the flag in the header (`LanguageSwitch`, `src/components/language-switch.tsx`), left of their name, which sets a `lang` cookie for a year and reloads the page; without the cookie, a browser whose language starts with `es` reads in Spanish and any other in English (`preferredLang` in `shared/i18n.ts`). The language is fixed for a page load, so `lang` is a module constant read once at start, and switching reloads rather than re-renders.

**The interface's text** sits beside its code: each file holds one `const t = messages({ en, es })` table (`shared/i18n.ts`), its values strings or functions for counts, plurals and sentences around a link, and `messages` returns the reader's language. Both halves must hold the same keys and types, so `npm run gate` fails on a missing Spanish line. Dates and numbers format with `locale` (`en-GB` or `es-ES`). The API answers its errors in the reader's language too: `says` (`api/_lib/i18n.ts`) picks the table per request from the same cookie, or the request's `Accept-Language`, since one function serves both. What the group writes (series and milestone names, player names and nicknames) and Pokémon species names, the same in both languages, are never translated. A series' rules are the exception: each series holds them in both languages, written by an admin, and a reader gets theirs, or the other while theirs are empty. Showdown's text format, copied and pasted on a team page, stays English, so a paste works in Showdown whatever the site's language (`src/teams/showdown.ts` names everything from `@pkmn/dex` directly).

**Pokémon data** (move, ability, item, nature and type names, move categories, and the move, ability and item descriptions) is English in `@pkmn/dex` and Spanish in `src/i18n/es/`: `names.json`, the official Spanish names from PokeAPI's data plus the hand-kept `names.extra.json` for those PokeAPI lacks, and `descs.json`, Showdown's own short descriptions translated by us, keeping every mechanic (Curse's Ghost and non-Ghost effects, not the games' "works differently for Ghost types"), with `descs.lock.json` holding a hash of the English each was translated from. Both are keyed by Showdown ID and load, as their own chunk, before the app starts and only for a Spanish reader (`loadDexText`, `src/i18n/dex.ts`, from `src/main.tsx`, which then imports `src/boot.tsx`), so an English reader downloads none of it. `shared/dex-text.ts` answers `dexName`, `dexDesc`, `typeLabel` and `categoryLabel`, falling back to the English for anything missing; `shared/describe.ts` names everything through them. Types, categories and IDs stay English as keys and data, and are translated only where they are shown. The server knows no Spanish game data, so it describes a PC or a series' ability holders in English and the page renames them by ID once they arrive (`localizePc`, `localizeHolders`). Refreshing the Spanish data after an `@pkmn/dex` upgrade is in [How to Run and Deploy the Site → Refresh the Spanish game text](../how-to/run-and-deploy-the-site.md#refresh-the-spanish-game-text).

## Data and Storage

Accounts and their sessions live in Postgres: Neon (Vercel Marketplace, free tier, resource `pkmn-site`, region `aws-eu-central-1`, Frankfurt) in production, with a `dev` branch for previews, and locally the Postgres of `compose.yaml`, which also runs MinIO as the local stand-in for the file store, with a `pkmn-site` bucket. Files (game zips under `games/`, save zips under `saves/`) live in private Backblaze B2 buckets, `pkmn-site-enbraile` for production and `pkmn-site-preview-enbraile` for previews, reached through their S3-compatible API with the AWS S3 SDK (`api/_lib/files.ts`), the same code that talks to MinIO locally. Once a day a Vercel Cron Job (`crons` in `vercel.json`, scheduled for 04:00 UTC and started within that hour on Hobby) calls `GET /api/cron/sweep-files` (`api/_lib/sweep.ts`), which deletes every object in the bucket more than a day old that no row names: not a game's `file_key` or its item icon sheet, nor a snapshot's `file_key` or `rolled_key`. It catches what the uploads' own clean-up misses, such as a game's zip whose recording failed, or a player's last unused upload. The route skips the sign-in check and answers only Vercel's `Authorization: Bearer <CRON_SECRET>`, and refuses everything while `CRON_SECRET` is unset; it answers the keys it deleted and how many it kept. The schema holds Better Auth's `user` (with the site's `admin` and `allowed` flags), `session`, `account` and `verification` tables, the `game` table, the `series`, `series_player` and `milestone` tables, and the `save` and `snapshot` tables, and the `team` and `team_source` tables, and changes only by forward migrations generated into `drizzle/` (`npm run db:generate`) and applied with `npm run db:migrate`; there are no down migrations, and data is restored with Neon's point-in-time restore. Secrets (`DATABASE_URL`, `BETTER_AUTH_SECRET`, the Discord application's `DISCORD_CLIENT_SECRET`, the buckets' `S3_*` keys, `CRON_SECRET`) live in Vercel's environment and in an untracked `.env.local`, never in the repository; `.env.example` names every variable.

Teams live in Postgres too, in the `team` and `team_source` tables ([Team Builder → Stored Teams](team-builder.md#stored-teams)); each reader's Analyse switch and pick of six on a team of seven or eight stay in their browser, in `localStorage` ([Team Builder → The Team Page](team-builder.md#the-team-page)). Game data (names, descriptions, base stats, the type chart) is bundled from `@pkmn/dex` rather than fetched, and its Spanish names and descriptions are bundled from `src/i18n/es/` ([Languages](#languages)), never stored in the database. Sprites load from Showdown's sprite server, `play.pokemonshowdown.com`, through `@pkmn/img`'s URLs.

## Hosting and Deploys

Vercel serves the site from the owner's Hobby account: the Vite build's static `dist/` and the API as a Vercel Function (`api/index.ts`) in the same project. `pkmn/site/vercel.json` runs the function in Frankfurt (`fra1`), beside the Neon database (`aws-eu-central-1`), sends `/api/` paths to the function and rewrites every other path but `/assets/` to `/index.html` so deep links load the single-page app. Each deploy names its chunks anew and serves only its own, so a tab opened before a deploy asks for chunks that are gone: their `/assets/` paths answer 404, Vite fires `vite:preloadError` on the failed import, and the page reloads once onto the new deploy (`reloadForNewDeploy` in `src/boot.tsx`), not again within ten seconds, so a chunk that keeps failing does not loop. `pkmn.enbraile.vip` is a DNS-only (grey-cloud) `CNAME` to the Vercel target in the `enbraile.vip` zone, which stays on the owner's Cloudflare account. If the record were proxied, traffic would go through Cloudflare's IPs again, which Spanish ISPs block during LaLiga matches.

Vercel's Git integration, connected to the GitHub repository in the Vercel dashboard with root directory `pkmn/site`, builds and deploys each push to `main` that touches `pkmn/site/`. Pushes that touch nothing there are skipped, and each branch push gets a preview URL, behind Vercel Authentication, which covers every deployment but the custom domain. A preview or `vercel.app` URL is a different origin from `pkmn.enbraile.vip`, so its `localStorage` starts empty. The project's environment variables are set per Vercel environment: `DATABASE_URL` (the Neon production branch for Production, the `dev` branch for Preview), `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL` (`https://pkmn.enbraile.vip` for Production), and the B2 file store's `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY`, whose bucket and key differ for Preview, so a preview never reaches the production files, the Discord application's `DISCORD_CLIENT_ID` and `DISCORD_CLIENT_SECRET`, for Production only `CRON_SECRET`, since Vercel runs cron jobs on the production deployment alone, and, for Preview only, `DEV_SIGN_IN` and `SEED_ADMIN_PASSWORD`. Previews leave `BETTER_AUTH_URL` unset, so Better Auth takes each request's own URL as its base. There are no secrets in the repository. Each deploy's build migrates its own environment's branch (`npm run db:migrate` after `npm run build`, `buildCommand` in `vercel.json`) before that deploy goes live, and a preview's build then seeds the `dev` branch and the preview bucket (`npm run seed` with `SEED_TARGET=preview`). A bad deploy is undone with Vercel's Instant Rollback to the previous production deployment, or by reverting the commit, which redeploys.

The site writes no logs of its own: Vercel's build and deployment logs cover the deploy, the API's uncaught errors land in Vercel's function logs, there is no Web Analytics, and import and upload errors are shown to the reader.

## Performance

The site is measured on the local stack, in four passes that each fix the biggest measured cost that changes nothing a reader sees or can do (owner, 2026-10-25). A pass measures a production build (`npm run build`) served gzip-compressed with the API behind it, as Vercel serves it, seeded by `npm run seed` with MIRAMEEE's save, signed in as Red, driven through the Playwright browser with Chrome DevTools Protocol throttling. It loads each page cold three times and keeps the median: the series page, Red's series page, Red's PC, the team list and the Seed team, at desktop width (1366×768, 10 Mbps, 40 ms round trip, no CPU slowdown) and at phone width (390×844, 1.6 Mbps, 150 ms, the CPU four times slower). "Ready" runs from navigation until the page's own content shows (the Trainers heading, the Fallen heading, the first Pokémon in the box, a team's name); JS is the compressed bytes of the scripts loaded, as the browser's resource timing reports them (a little under `npm run build`'s gzip estimates). The API is timed over 50 requests in a row per read route, with its queries counted from Postgres' statement log.

**Pass one (2026-10-25).** The biggest cost was `@pkmn/dex`'s chunk (1.8 MB, 347 kB compressed) and the summary's chunk, holding `@pkmn/img` (180 kB, 56 kB compressed), loaded by two pages that only name and draw Pokémon: the player's series page, for its fallen cards' names and sprites, and the team list, for its rows' sprites and for Compare, whose analysis chunk (514 kB, 163 kB compressed) it imported up front. Interactions were not either: picking a Pokémon in the PC took at most 64 ms on the phone profile and 16 ms on desktop, before and after. The fix: the journey route names the fallen and gives their sprite URLs, the team list draws its sprites with `@pkmn/img` alone and loads Compare's code when Compare is first pressed, and `MonSprite` has a file of its own ([Decisions](#decisions)).

## Decisions

- **The site reads in English and Spanish, picked from a flag in the header left of the reader's name, and the whole site is translated: the interface, the API's errors and Showdown's game text.** **Why:** the group is Spanish and plays a Spanish game; the owner asked for the full site in Spanish with a flag in the header to switch. _(owner, 2026-10-28)_
- **Showdown's move, ability and item descriptions are translated by us, not taken from PokeAPI.** PokeAPI has the official Spanish names but, in Spanish, only the games' own flavour text, which is vague (Curse: "Un movimiento que tiene efectos distintos si el usuario es de tipo Fantasma o no") and missing for many Gen 9 entries; its precise effect text exists in English, French and German only, and Showdown ships no Spanish game data. So names come from PokeAPI and descriptions are Showdown's, translated once with an LLM and checked in, with a hash of each English source so a dex upgrade shows what to redo. **Why:** the owner wanted Showdown's detail in Spanish, not the games' summaries. _(owner, 2026-10-28)_
- **The Spanish game text lives in the repository and is bundled, never in the database.** It is about 220 KB of JSON, 50 KB compressed, loaded only by a Spanish reader, and changes only with `@pkmn/dex`, like the English it sits beside. **Why:** the owner worried about Neon's free tier; static data needs no table, query or migration. _(settled 2026-10-28)_
- **A series' rules are kept in both languages, Spanish the source and English translated from it, each its own Markdown on the series, edited under one switch in the admin form.** The group will write the rules in Spanish and have the English translated from them on request. **Why:** the owner's answer when asked how the rules should be translated (2026-10-28); a reader's language falling back to the other keeps a series readable while only one is written. _(owner, 2026-10-28)_
- **i18n's build choices:** no i18n library, each file's own `messages({ en, es })` table typed so the gate catches a missing line; the language fixed per page load, switching by reload, so module-level text and lists stay simple; a cookie rather than `localStorage`, so the API reads the same choice; the browser's language as the default; Spain's flag and the United Kingdom's, as pixel-art SVGs in `public/flags/` to match the site's pixel icons (the owner asked for them more pixelated), since Windows draws flag emoji as letters; the Showdown export in English. _(settled 2026-10-28)_
- **A player's colour is picked from a hash of their name, among twelve `player-N` tokens rather than six, and is not stored.** Six colours gave six players about a 98% chance that two share one; twelve make a repeat less likely, and a colour stays the same across every deploy and database while the name does. The new six were picked from a set of light colours to keep the closest pair of the twelve no closer in OKLab than the existing yellow and orange, each at least 8.7:1 against the `ink` initial. A rename changes a player's colour, and two players can still share one. A colour hashed to any hue was turned down, since the site's colours come only from tokens; a stored colour per player was turned down by the owner. **Why:** the owner asked for the name as the seed and for more colours; the palette size and the token route are delegated choices. _(owner, 2026-10-28)_
- **Site v2's scoping decisions, with the owner's reasons,** kept when its work in progress closed; what each became is in the sections above. _(owner, 2026-10-22 to 2026-10-25)_
  - Players sign in with Discord: one click, no passwords, and the Discord name is how the group knows each other.
  - Anyone signed in sees nothing until an admin lets them in: the PCs are the group's own, with no invite links to manage.
  - An admin is a separate local account, not a player, and the owner plays under their own Discord account like everyone else: a player building a team should not carry admin powers. Admins work in an admin UI rather than in code.
  - A game is made once and reused by many series.
  - The pieces are game → series → save → snapshot, and "Box" keeps the game's meaning, a page of the PC: the owner's pick.
  - Every PC at every snapshot and every team was open to every player, for now ("I would not worry about this now"); showing only what a series' rules allow was left for later. Teams have since become private by default ([Team Builder → Decisions](team-builder.md#decisions), 2026-10-28), and snapshots follow the series' save rule (the save rule's build choices, 2026-10-29).
  - Saves arrive by each series' ingestion mode, manual first: the end goal is games that report by themselves, but Añil will not be modded again for it, so the model assumes neither.
  - Manual ingestion trusts the players: no snapshot's TMs are checked against another's, and rolled TMs belong in the snapshot.
  - Old exports are read as far as they go and never refused: series 1's MIRAMEEE and Vicky exports cannot be made again, and the site never stops working for a gap.
  - Uploaded save zips are kept, so snapshots can be exported again when the export improves.
  - No "tools" anywhere: the owner dislikes them as a concept, since they read as standalone.
  - A player's profile gathers all their data across series, and their page in a series shows how they stood at each milestone, with no party ("it does not make much sense") and no PC tab, which would read badly.
  - The series page ranks no one: the league owns rankings.
  - One backend language, TypeScript, for Better Auth and types shared with the browser, all free at the group's size; Supabase was turned down because a free project pauses after a week idle.
  - Files live in Backblaze B2: Vercel Blob's free allowance covers about one round of game downloads a month, and Cloudflare R2's URLs sit on the IPs Spanish ISPs block during LaLiga matches.
  - Players' real saves for local checks stay in the gitignored `pkmn/site/saves/` and never enter the public repo.
- **A page whose chunk a deploy removed reloads onto the new deploy, and `/assets/` paths are never rewritten to the page.** A tab opened before a deploy asked for its old chunk, the rewrite answered `index.html`, and the browser refused it ("disallowed MIME type (text/html)"), leaving the page on its frame until a manual reload; reported by the owner on 2026-10-28 and reproduced on a local production build. Vercel's Skew Protection, which keeps old deploys' assets, is not on the Hobby plan. The reload is guarded for ten seconds in `sessionStorage`. **Why:** forced by the deploy model; a 404 is the true answer for a missing asset. _(settled 2026-10-28)_
- **Files the bucket holds that no row names are swept by a scheduled job.** **Why:** the owner, asked whether the clean-up is a script run by hand or scheduled. _(owner, 2026-10-28)_
- **The sweep's build choices:** a Vercel Cron Job calling a route of the one API function, once a day since the Hobby account runs cron jobs at most daily; the route behind `CRON_SECRET`, as Vercel sends it, rather than an admin session, since the job signs in as no one; objects named by no row and at least a day old, longer than the save upload's hour since a daily sweep loses nothing by waiting, so an object written just before its row (a rolled zip, an icon sheet, a game zip being recorded, even one whose upload started long before) is not caught; the bucket listed before the rows are read, and the rows read again just before each delete, so a row recorded during the sweep keeps its object, except in the moment between that last read and the delete, which a save zip only reaches when its player has left the upload dialog on its pick step for over a day and saves just then; abandoned multipart uploads left to the next upload under their prefix, as before, since they are parts, not objects. **Why:** delegated build choices. _(settled 2026-10-28)_
- **A player added to a running manual series uploads their save before they reach the site.** Adding them marks their place (`series_player.needs_save`); while any running series holds their mark, the site shows the waiting page with an upload for that series, picked from a list when several do, and the save's suggested milestone preselected as on the series page; their first snapshot in it, whoever uploads it, clears the mark. Letting a player in and adding them to a series stay two admin steps. Automatic series are left out for now. **Why:** the owner wants every player who joins mid-series to arrive onboarded. _(owner, 2026-10-27; replaces joining with nothing and uploading later from the series page)_
- **Starting a manual series marks every player its draft holds `needs_save`,** as adding them to it running would. **Why:** the owner called leaving them unmarked a bug: Series 1 was started on the site with its run already under way in the game, and its players reached the site without uploading. A series started with fresh games holds its players until they upload a first save too. _(owner, 2026-10-27; replaces holding only players added to a running series)_
- **The hold is the site shell's, not the API's:** a held player is let in and in the series, so the API answers them as any player, and only `GET /api/series/owed` tells the shell what they still owe. **Why:** the hold keeps the player on the upload rather than guarding data they may already read, and checking it in `requireAllowed` would add a query to every API call. _(settled 2026-10-27)_
- **The Site v2 Screens canvas is split into one page per site area, however many boards it holds** ([Look → Canvas pages](#look)). **Why:** at 52 boards on one page the canvas had grown slow to use; an area on one page reads better than one split across several. _(owner, 2026-10-27; the page list set by the design session at the owner's request; the 10-board cap dropped by the owner, 2026-10-28, folding Team builder · phone into Team builder and the league's three pages into League)_
- **A running series' milestones are edited in place:** renamed, re-marked, reordered and added, and removed only when no snapshot is at one. **Why:** the owner wants to change a started series' milestones and their order; saving a draft replaces every milestone, which on a running series would delete their snapshots with them (`snapshot.milestone_id` cascades), so a running series' save keeps each milestone's id. Reordering moves a player's progress with it, since progress is their latest milestone with a snapshot. _(owner, 2026-10-24; replaces a running series changing only its rules and players)_
- **The admin pages have no Admin button beside their title;** the header's Admin tab leads back to the admin home. _(owner, 2026-10-24)_
- **Deleting a player deletes everything they have,** their snapshots in every series and their save zips in the bucket included, after a second press; Remove only takes them off the allowlist. **Why:** the owner chose it over refusing to delete a player who has played, accepting that finished series lose that player's history. _(owner, 2026-10-24)_
- **The waiting page says only "Waiting for an admin",** without the line under it that `waiting.dc.html` and `waiting-phone.dc.html` draw ("An admin has to let you in before you can see the series."); the frozen boards keep it. _(owner, 2026-10-24)_
- **An admin invites a player by their Discord user ID, and a series starts with any number of players, taking more while it runs.** An invite is a real player, allowed, with their Discord account made ahead of their first sign-in; a running series' players change, but one with a snapshot in it stays. **Why:** the owner wants everything ready for a player before they sign in, and to start a series before every player has joined. The invite owning the Discord account, rather than a list of pending IDs read at sign-in, lets an invited player be put in a series before they sign in, and needs no migration. _(owner, 2026-10-24; replaces "at least two players" on the start checklist and a running series changing only its rules)_
- **Production and preview migrate in the Vercel build, after the site builds, with the environment's pooled `DATABASE_URL`.** **Why:** the owner keeps no database credentials on their machine; a migration and its code then land in the same push. While the build migrates, the previous deployment still serves on the new schema, so a migration that drops or renames something it reads ships a deploy after the code that stops reading it; additive ones, like `0002`–`0007`, need nothing.
