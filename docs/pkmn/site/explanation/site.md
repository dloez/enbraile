# The pkmn Site

The group's Pokémon web app, `pkmn/site/`, served at `pkmn.enbraile.vip`. It holds a home page listing the tools, [Open Sheet](open-sheet.md) at `/open-sheet` and [Team Analysis](team-analysis.md) at `/team-analysis`. Its API runs on Vercel Functions, admins sign in at `/admin`, and they keep the games and their files at `/admin/games`. Running and deploying it is in [How to Run and Deploy the Site](../how-to/run-and-deploy-the-site.md). It was scoped with the owner on 2026-10-15.

## Stack

npm; Vite 8, React 19, TypeScript 7, Tailwind 4 and shadcn/ui; TanStack Router; zod 4; Dexie over IndexedDB; `@pkmn/dex` and `@pkmn/img` for Showdown's data and sprites. Every package is pinned exactly, at its latest stable version when it went in (the scaffold, 2026-10-16: vite 8.3.4, react 19.3.1, typescript 7.0.2, tailwindcss 4.3.3, shadcn 4.21.5, @tanstack/react-router 1.170.44, @pkmn/dex 0.10.11, @pkmn/img 0.3.4). The gate is `npm run gate`: `tsc -b`.

Routes are declared in code in `src/router.tsx`, not with TanStack Router's file-based plugin: a handful of routes needs no generated route tree for `tsc` to check before a build. A tool gets its route there and its home-page card from `src/tools.ts`.

The server side is TypeScript too: a Hono app (`api/_lib/app.ts`) under `/api`, Better Auth for sign-in (`api/_lib/auth.ts`), and Postgres through Drizzle over `pg` (`api/_lib/db.ts`, schema in `api/_lib/schema.ts`), with `drizzle-kit` writing the migrations into `drizzle/` (scaffolded 2026-10-22: hono 4.13.13, better-auth 1.7.12, drizzle-orm 0.45.4, drizzle-kit 0.31.11, pg 8.23.1, @hono/node-server 2.1.5, tsx 4.23.15; @aws-sdk/client-s3 and @aws-sdk/s3-request-presigner 3.1156.0 on 2026-10-22). `api/index.ts` is the only Vercel Function: Vercel makes a function of every file in `api/` except those under a `_` folder, so the app lives in `api/_lib/`, and `vercel.json` sends every `/api/` path to it. Locally, `scripts/dev-api.ts` serves the same app on Node at `API_PORT` (8787), started and stopped by a small Vite plugin in `vite.config.ts` so that one `npm run dev` runs both, and Vite proxies `/api` to it. The browser talks to it through Better Auth's client (`src/lib/auth-client.ts`) and, for the site's own routes, `src/lib/api.ts`, which parses each answer with a zod schema from `shared/`, the folder both the browser and the API compile, so the two agree on every request and answer. `tsconfig.api.json` puts `api/`, `scripts/` and `shared/` under the gate, and their relative imports end in `.js` so that both `tsx` and Vercel's compiled output resolve them.

## Accounts

An admin is a separate username-and-password account, not a player: a `user` row with `admin` set and a `credential` account holding the password hash. `npm run admin:create <name>` (`scripts/admin-create.ts`) is the only way to make one outside the local stack, whose seed makes its own: it asks for the password twice without echoing it, never takes it as an argument, and writes both rows in one transaction, with the username lower-cased and a placeholder `<name>@admin.invalid` email, since Better Auth requires an email. Better Auth's sign-up is off (`disableSignUp`), so no route makes an account, and `admin` cannot be set through its API (`input: false`). Locally, `DEV_SIGN_IN=1` adds a test sign-in (`api/_lib/dev-sign-in.ts`), a Better Auth plugin whose `GET /api/auth/dev/sign-in?username=<name>` starts a session for a player who is not an admin and redirects home; unset, the plugin is not registered and the route does not exist. `npm run seed` (`scripts/seed.ts`) makes the local admin, test players and a game with a stand-in zip, and only against a database and a file store on `localhost` or `127.0.0.1`. `/admin` (`src/pages/admin.tsx`) shows a sign-in form, and an admin's session gets the admin home with sign-out. The admin home links to the admin pages. The admin pages have no design of their own; they are built from the look's shared pieces (`Panel`, `fieldClass`, the quiet button, the lifting card). Every `/api/games` route answers only an admin's session (`api/_lib/admin.ts`): 401 without one, 403 for a player.

## Look

The [Site v2 Screens](https://claude.ai/artifact/JZpaCYGx2NQtPpcvAWYXrZ) design in Claude Design sets the look the whole site moves to. The owner signed off its series list, series page and site header on 2026-10-22; its other screens are still being designed on the same canvas. It replaces the look the [Open Sheet Screens](https://claude.ai/artifact/SfpFcW5UoLVLeLAmdJZMG1) design set on 2026-10-16 (charcoal, a slate-blue PC, orange for actions) everywhere, the PC and team views included, as each screen is designed and built. Frozen copies of the signed-off boards are in `pkmn/site/design/` (`series-list.dc.html`, `series.dc.html`): builders read them for exact colours, sizes and spacing, and they never change; a later revision is signed off on the canvas and copied in again. Their trainer numbers and names are sample data, and their Google Fonts link stands for the bundled fonts.

The look is a Gen 4–5 game screen, kept readable:

- **One dark theme,** a deep navy ground with a faint dot grid, navy panels with 3px slate borders and rounded corners. No light theme.
- **Two typefaces:** Jersey 10, a pixel face, for headings, labels, tabs, buttons and numbers; Nunito for running text.
- **Pixel art drawn in code** as crisp-edged SVG: the Poké Ball home mark, the icons (flag, monitor, people, download arrow, cartridge) and the series scenes.
- **A scene per series.** Each series has a background scene from a fixed set (so far a night sky and a daytime route), picked by the admin in the series form. Every scene moves a little in stepped, game-like animation: the night sky's stars, sparkles and lit windows blink; the route's clouds drift and its flowers blink. Under `prefers-reduced-motion` they stand still.
- **The header:** the Poké Ball links home; tabs Series · PC · Teams (· Admin for admins) sit on the header's red bottom line, the open one filled red and joined to it; sign-out at the right, and no profile.
- **Players are boxed, never round:** a rounded-square badge with the player's initial, a dark border and a ring in the player's own colour.
- **Quiet controls:** buttons are translucent, in the pixel face, with a dark bottom edge; whatever is clickable as a whole (a series banner, a trainer's PC or Teams tile) lifts and takes a cyan border on hover. Red marks where you are, cyan what you can act on, yellow you and winners.
- No helper text explaining the UI. The UI is in English, since Showdown's names are. Desktop-first, with every view usable on a phone.

The site's design system is kept in the repository: the code (`src/index.css`'s tokens, the shell, the shared components) is its source of truth, and the [Site Design System](../reference/design-system.md) describes it, changing in the same commit as the code does. A new page follows [How to Add a Page to the Site](../how-to/add-a-page-to-the-site.md).

shadcn was initialised with its Nova preset on Radix, its palette replaced by the design's colours as the only theme, and its vendored components in `src/components/ui/` follow the same token rule. The design's fonts are bundled from Fontsource rather than loaded from Google Fonts, and the type icons come from duiker101's [Pokémon Type SVG Icons](https://github.com/duiker101/pokemon-type-svg-icons), free for any use, bundled in `src/lib/type-icons.ts`, so the only outside calls the site makes at runtime are for Showdown's sprites; everything else it fetches is its own `/api`.

The tab icon is a spiral notepad with a red and white Poké Ball drawn on it and a pencil writing on it: `public/favicon.svg`, plus `favicon-32.png` and `apple-touch-icon.png` rendered from it for browsers that take no SVG icon.

## Games

A game is a name and one zip of its files (`game` in `api/_lib/schema.ts`, with the file's key, name, size and upload time). At `/admin/games` (`src/pages/admin-games.tsx`) an admin creates a game by name, which must be unique, and uploads its zip; the page lists every game with its file's name, size and upload date, and downloads it. The file never passes through the API, since a Vercel Function's body is capped at a few MB and a game is about 600 MB:

1. `POST /api/games/<id>/upload` with the file's name and size answers a presigned `PUT` URL for a new key, `games/<id>/<uuid>.zip`, valid for an hour and signed for that exact size.
2. The browser `PUT`s the file straight to the bucket, showing its progress.
3. `POST /api/games/<id>/file` with the key checks that it belongs to the game and reads the object's real size from the bucket, then records it and deletes the game's previous object.

Replacing a game's file is the same new upload under a new key, so a half-finished replacement leaves the old file in place. A download is `GET /api/games/<id>/download`, a presigned `GET` valid for five minutes that saves under the uploaded file's name. Every games route is admin-only for now; players of a linked series will download through the series page. The bucket is private: nothing in it has a public URL.

## Data and Storage

Accounts and their sessions live in Postgres: Neon (Vercel Marketplace, free tier, resource `pkmn-site`, region `aws-eu-central-1`, Frankfurt) in production, with a `dev` branch for previews, and locally the Postgres of `compose.yaml`, which also runs MinIO as the local stand-in for the file store, with a `pkmn-site` bucket. Files live in a private Backblaze B2 bucket in production, reached through its S3-compatible API with the AWS S3 SDK (`api/_lib/files.ts`), the same code that talks to MinIO locally. The schema holds Better Auth's `user`, `session`, `account` and `verification` tables and the `game` table, and changes only by forward migrations generated into `drizzle/` (`npm run db:generate`) and applied with `npm run db:migrate`; there are no down migrations, and data is restored with Neon's point-in-time restore. Secrets (`DATABASE_URL`, `BETTER_AUTH_SECRET`, the bucket's `S3_*` key) live in Vercel's environment and in an untracked `.env.local`, never in the repository; `.env.example` names every variable.

Open Sheet's tabs and teams still stay in the reader's browser, in IndexedDB, and Team Analysis's drafts in `localStorage`, per browser and device, until the team builder moves them into accounts. Game data (names, descriptions, base stats, the type chart) is bundled from `@pkmn/dex` rather than fetched. Sprites load from Showdown's sprite server, `play.pokemonshowdown.com`, through `@pkmn/img`'s URLs.

## Hosting and Deploys

Vercel serves the site from the owner's Hobby account: the Vite build's static `dist/` and the API as a Vercel Function (`api/index.ts`) in the same project. `pkmn/site/vercel.json` runs the function in Frankfurt (`fra1`), beside the Neon database (`aws-eu-central-1`), sends `/api/` paths to the function and rewrites every other path to `/index.html` so deep links load the single-page app. `pkmn.enbraile.vip` is a DNS-only (grey-cloud) `CNAME` to the Vercel target in the `enbraile.vip` zone, which stays on the owner's Cloudflare account. If the record were proxied, traffic would go through Cloudflare's IPs again, which Spanish ISPs block during LaLiga matches.

Vercel's Git integration, connected to the GitHub repository in the Vercel dashboard with root directory `pkmn/site`, builds and deploys each push to `main` that touches `pkmn/site/`. Pushes that touch nothing there are skipped, and each branch push gets a public preview URL (Vercel Authentication is off for previews). A preview or `vercel.app` URL is a different origin from `pkmn.enbraile.vip`, so its IndexedDB and `localStorage` start empty. The project's environment variables are set per Vercel environment: `DATABASE_URL` (the Neon production branch for Production, the `dev` branch for Preview), `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL` (`https://pkmn.enbraile.vip` for Production), and the B2 bucket's `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY`. Previews leave `BETTER_AUTH_URL` unset, so Better Auth takes each request's own URL as its base. There are no secrets in the repository. A schema change is migrated by hand (`npm run db:migrate` against the branch) before the code needing it is deployed. A bad deploy is undone with Vercel's Instant Rollback to the previous production deployment, or by reverting the commit, which redeploys.

The site writes no logs of its own: Vercel's build and deployment logs cover the deploy, the API's uncaught errors land in Vercel's function logs, there is no Web Analytics, and import and upload errors are shown to the reader.
