# The pkmn Site

The group's Pokémon web app, `pkmn/site/`, served at `pkmn.enbraile.vip`. Players sign in with Discord and see it once an admin has allowed them: they land on the running series' page, `/series/<n>`, with every series listed at `/series` ([Series](#series)), upload their save zip there as a snapshot, follow any player's journey and fallen through the series at `/players/<player>/series/<n>`, and open any player's PC at any snapshot at `/players/<player>/series/<n>/pc` ([Snapshots](#snapshots)); [Team Analysis](team-analysis.md) at `/team-analysis` stays behind the Teams tab, and [Open Sheet](open-sheet.md) at `/open-sheet` is reached only by its address, until the team pages replacing them are built. Its API runs on Vercel Functions, admins sign in at `/admin`, keep the allowlist at `/admin/players`, keep the games and their files at `/admin/games`, and make and run the series at `/admin/series`. Running and deploying it is in [How to Run and Deploy the Site](../how-to/run-and-deploy-the-site.md). It was scoped with the owner on 2026-10-15.

## Stack

npm; Vite 8, React 19, TypeScript 7, Tailwind 4 and shadcn/ui; TanStack Router; zod 4; Dexie over IndexedDB; `@pkmn/dex` and `@pkmn/img` for Showdown's data and sprites; `react-markdown` and `remark-gfm` for a series' rules. Every package is pinned exactly, at its latest stable version when it went in (the scaffold, 2026-10-16: vite 8.3.4, react 19.3.1, typescript 7.0.2, tailwindcss 4.3.3, shadcn 4.21.5, @tanstack/react-router 1.170.44, @pkmn/dex 0.10.11, @pkmn/img 0.3.4). The gate is `npm run gate`: `tsc -b`.

Routes are declared in code in `src/router.tsx`, not with TanStack Router's file-based plugin: a handful of routes needs no generated route tree for `tsc` to check before a build. A page gets its route there; the home, `/`, has no page of its own and sends a signed-in reader on to the running series ([Series](#series)).

The server side is TypeScript too: a Hono app (`api/_lib/app.ts`) under `/api`, Better Auth for sign-in (`api/_lib/auth.ts`), and Postgres through Drizzle over `pg` (`api/_lib/db.ts`, schema in `api/_lib/schema.ts`), with `drizzle-kit` writing the migrations into `drizzle/` (scaffolded 2026-10-22: hono 4.13.13, better-auth 1.7.12, drizzle-orm 0.45.4, drizzle-kit 0.31.11, pg 8.23.1, @hono/node-server 2.1.5, tsx 4.23.15; @aws-sdk/client-s3 and @aws-sdk/s3-request-presigner 3.1156.0 on 2026-10-22). `api/index.ts` is the only Vercel Function: Vercel makes a function of every file in `api/` except those under a `_` folder, so the app lives in `api/_lib/`, and `vercel.json` sends every `/api/` path to it. Locally, `scripts/dev-api.ts` serves the same app on Node at `API_PORT` (8787), started and stopped by a small Vite plugin in `vite.config.ts` so that one `npm run dev` runs both, and Vite proxies `/api` to it. The browser talks to it through Better Auth's client (`src/lib/auth-client.ts`) and, for the site's own routes, `src/lib/api.ts`, which parses each answer with a zod schema from `shared/`, the folder both the browser and the API compile, so the two agree on every request and answer. `tsconfig.api.json` puts `api/`, `scripts/` and `shared/` under the gate, and their relative imports end in `.js` so that both `tsx` and Vercel's compiled output resolve them. The save export is the site's own TypeScript (`api/_lib/export/`), with no package of its own: a port of the retired Python export's Ruby Marshal reader and export ([Save Export](save-export.md)), a zip reader over `node:zlib`, and the export's game data as `data.json`, imported with `with { type: "json" }` (`resolveJsonModule` in `tsconfig.api.json`).

## Accounts

A player signs in with Discord, through Better Auth's Discord provider, registered only when `DISCORD_CLIENT_ID` and `DISCORD_CLIENT_SECRET` are set. Their first sign-in makes a `user` row named after their Discord display name, with a `discord` account, and `allowed` false. `SiteShell` (`src/components/site-shell.tsx`), the root route's component, guards every page but `/admin` and its pages: signed out, it shows the sign-in page (`src/pages/sign-in.tsx`); signed in but not allowed, the waiting page (`src/pages/waiting.tsx`), with the player's badge and name and its own sign-out; otherwise the header and the page. Neither page has the header. Every API route but `/api/auth/*` answers only a session that is allowed or an admin's (`api/_lib/access.ts`): 401 without a session, 403 "Waiting for an admin" for a player not allowed. The flag is read on every request, so allowing or removing a player takes effect on their next reload. An admin keeps the allowlist at `/admin/players` (`src/pages/admin-players.tsx`), which lists every player who has signed in, waiting first, and allows or removes each one through `GET /api/players` and `POST /api/players/<id>/allowed` (`api/_lib/players.ts`, schemas in `shared/players.ts`), both for admins only. Admins never touch Discord: account linking is off, so a Discord sign-in can never join an existing account, and a database hook refuses any account other than a password for an admin's user.

An admin is a separate username-and-password account, not a player: a `user` row with `admin` set and a `credential` account holding the password hash. `npm run admin:create <name>` (`scripts/admin-create.ts`) is the only way to make one outside the local stack, whose seed makes its own: it asks for the password twice without echoing it, never takes it as an argument, and writes both rows in one transaction, with the username lower-cased and a placeholder `<name>@admin.invalid` email, since Better Auth requires an email. Better Auth's sign-up is off (`disableSignUp`), so no route makes an account, and `admin` cannot be set through its API (`input: false`). Locally, `DEV_SIGN_IN=1` adds a test sign-in (`api/_lib/dev-sign-in.ts`), a Better Auth plugin whose `GET /api/auth/dev/sign-in?username=<name>` starts a session for a player who is not an admin and redirects home; unset, the plugin is not registered and the route does not exist. `npm run seed` (`scripts/seed.ts`) makes the local admin, the test players (Red and Blue allowed, Leaf waiting), a game with a stand-in zip and series 1 running on it ([How to Run and Deploy the Site](../how-to/run-and-deploy-the-site.md) has the details), and only against a database and a file store on `localhost` or `127.0.0.1`. `/admin` (`src/pages/admin.tsx`) shows a sign-in form, and an admin's session gets the admin home with sign-out. The admin home lists the admin pages as links, and the header's sign-out signs an admin out. The admin pages have no design of their own; they are built from the look's shared pieces (`Panel`, `fieldClass`, the quiet button, the lifting card). Every `/api/games` route answers only an admin's session (`api/_lib/admin.ts`): 401 without one, 403 for a player.

- **A scene per series.** Each series has a background scene from a fixed set (so far a night sky and a daytime route), picked by the admin in the series form. Every scene moves a little in stepped, game-like animation: the night sky's stars, sparkles and lit windows blink; the route's clouds drift and its flowers blink. - **Sign-in and waiting are a Poké Ball:** the top half red with the site's name, a black band with a large Poké Ball on the seam, and the dark half below holding the Discord button or, for a player not yet allowed, their badge, the waiting message and sign-out. - **The header:** the Poké Ball links home; tabs Series · PC · Teams (· Admin for admins) sit on the header's red bottom line, the open one filled red and joined to it; at the right, your badge and name, opening your profile, then sign-out. On a phone the bar shrinks to the Poké Ball, the open section's name and a three-line menu button whose dropdown lists the tabs, your profile and sign-out.

Red marks where you are, cyan what you can act on, yellow you and winners, amber a soft warning that never blocks (an old export's missing fields, a snapshot about to be replaced).

The site's design system is kept in the repository: the code (`src/index.css`'s tokens, the shell, the shared components) is its source of truth, and the [Site Design System](../reference/design-system.md) describes it, changing in the same commit as the code does. A new page follows [How to Add a Page to the Site](../how-to/add-a-page-to-the-site.md).

The tab icon is a spiral notepad with a red and white Poké Ball drawn on it and a pencil writing on it: `public/favicon.svg`, plus `favicon-32.png` and `apple-touch-icon.png` rendered from it for browsers that take no SVG icon.

## Games

A game is a name and one zip of its files (`game` in `api/_lib/schema.ts`, with the file's key, name, size and upload time). At `/admin/games` (`src/pages/admin-games.tsx`) an admin creates a game by name, which must be unique, and uploads its zip; the page lists every game with its file's name, size and upload date, and downloads it. The file never passes through the API, since a Vercel Function's body is capped at a few MB and a game is about 600 MB:

1. `POST /api/games/<id>/upload` with the file's name and size aborts any multipart upload the game left open, starts a multipart upload for a new key, `games/<id>/<uuid>.zip`, and answers the key, the upload's id and the part size (`partSizeFor` in `shared/upload.ts`).
2. The browser splits the file into parts of that size and sends four at a time (`uploadParts` in `shared/upload.ts`, driven by `sendFile` in `src/lib/upload.ts`, which the save upload shares). For each part it asks `POST /api/games/<id>/upload/part` for a presigned `PUT` of that part, valid for an hour and signed for its exact size, and `PUT`s the part straight to the bucket, keeping the `ETag` the bucket answers (exposed by its CORS rule). One percentage shows the bytes sent across all parts.
3. A part that fails, or goes 30 seconds without sending a byte or getting its answer, is retried on its own with a freshly signed URL, up to six tries in all, after 1, 2, 4, 8 and 16 seconds. When a part runs out of tries, the other parts are cancelled and `DELETE /api/games/<id>/upload` aborts the multipart upload, tried three times; the page shows why the upload failed, and says so if the abort could not reach the bucket either, in which case the game's next upload aborts it in step 1. Aborting an upload the bucket no longer knows, because step 4 completed or aborted it, counts as done.
4. `POST /api/games/<id>/file` with the key, the upload's id and every part's number and `ETag` checks that the key belongs to the game and completes the multipart upload, aborting it if the bucket refuses. It then reads the object's real size from the bucket, records it and deletes the game's previous object.

Until step 4 completes, the bucket holds no object for the upload, only its parts, so a half-finished replacement leaves the old file in place and leaves no stray file behind. `npm run seed` puts its stand-in zip in the bucket through the same multipart calls and `uploadParts`, signing the parts in the script rather than through the API. The API's calls to the bucket give up after 5 seconds without a connection or 20 seconds without an answer, tried twice, so a bucket that cannot be reached fails a request rather than hanging it. A download is `GET /api/games/<id>/download`, a presigned `GET` valid for five minutes that saves under the uploaded file's name. Every games route is admin-only; a series' players download its game through the series page ([Series](#series)). The bucket is private: nothing in it has a public URL.

## Series

A series (`series` in `api/_lib/schema.ts`) has a unique number, a name, its game, its background scene (`night` or `route`), its ingestion mode (`manual`, players upload their saves, or `automatic`, the game sends them), its rules as Markdown, and a state: `draft`, `running` or `finished`. Its players are rows of `series_player`, and its milestones rows of `milestone`, in order (`position`), each named and marked `none`, `round` (a league round is played at it) or `tournament`. A partial unique index on `state` lets one series run at a time. The shapes the browser and the API share, and `startChecklist`, are in `shared/series.ts`.

**Admins** keep the series at `/admin/series` (`src/pages/admin-series-list.tsx`), which lists every series, newest first, and creates a draft from a number and a name, then opens its form at `/admin/series/<id>` (`src/pages/admin-series.tsx`): number, name, game (from `/admin/games`, marked when it has no file), ingestion, the scene with a preview of it under the series' name, the players (checkboxes over the allowlist), the milestones (named, marked, reordered, removed, added) and the rules, a Markdown text area that "Copy from" fills with another series' rules. The checklist under it shows what starting still needs: rules written, a game with its file, at least two players, at least one milestone, and, while another series runs, that series finished. It is worked out from the form as it is being filled, by the same `startChecklist` the API runs, and Start, which saves the form first, enables once every item is done. Save keeps a draft without starting it, and a draft can be deleted. Once a series runs only its rules change, through Save rules, and Finish, confirmed by a second press, ends it; a finished series stays finished. The routes are `GET` and `POST /api/admin/series`, `GET`, `PUT` and `DELETE /api/admin/series/<id>`, `PUT /api/admin/series/<id>/rules`, and `POST /api/admin/series/<id>/start` and `/finish` (`api/_lib/admin-series.ts`), every one admin-only; start refuses a draft whose checklist is not done, and the index refuses a second running series even if two starts race.

**Players** reach the running series from `/`, which sends a signed-in reader to its page, or to `/series` while none runs (`src/pages/home.tsx`). `/series` (`src/pages/series-list.tsx`, after `series-list.dc.html`) shows one banner per series that is running or finished, newest first, on its scene, with its name, its game and "Playing now" or "Finished"; the whole banner is a lifting link. `/series/<n>` (`src/pages/series.tsx`, after `series.dc.html`) is a header drawn on the series' scene with its name and its game in a box, with Download for the series' players and admins; the League as a work-in-progress placeholder; the Trainers, one row per player with their badge, their name, "You" on the reader's own row, and the milestones as a track, the rounds tinted and numbered and the tournament a cup, each row opening into PC, Teams, Fainted, Journey and Snapshots tiles: under "At <milestone>", the PC tile counts the exported living Pokémon, the Fainted tile the permafainted ones (in red above 0) and the Journey tile the play time ("37 h 19") of the trainer's latest snapshot, the one at the latest milestone, the Snapshots tile lists their snapshots' milestones with the latest outlined, and an Upload button where the reader may upload for that trainer ([Snapshots](#snapshots)); Teams reads "—", as do PC, Fainted and Journey for a trainer without a snapshot; the Fainted and Journey tiles link to the trainer's series page at `#fallen` and `#journey` ([Snapshots → The player's series page](#snapshots)); the PC tile, when there is a snapshot, links to the trainer's PC and each snapshot's milestone in the Snapshots tile to their PC at that snapshot ([Snapshots → The PC](#snapshots)), the tile lifting with a `primary` border on hover and the chip turning `primary`; and the rules, rendered from Markdown by `react-markdown` with GitHub tables (`remark-gfm`) and raw HTML skipped, in two columns on wide screens. A draft's page answers 404 to players and opens for admins. The routes are `GET /api/series`, `GET /api/series/<n>` and `GET /api/series/<n>/download` (`api/_lib/series.ts`), the last a five-minute presigned link to the game's zip for the series' players and admins, 403 for anyone else.

The scenes are `SceneArt` (`src/components/scene.tsx`): the boards' night sky and daytime route, drawn in code as crisp SVG rectangles on a pixel grid (360 by 65 for a page's header, 338 wide for a banner; on a phone a smaller crop, 98 by 55 and 88 wide) and scaled to cover their box from the bottom. Their stars, sparkles and windows blink and their clouds drift in stepped CSS animations (`scene-twinkle`, `scene-sparkle`, `scene-glow`, `scene-drift` in `src/index.css`), which stand still under `prefers-reduced-motion`. `SCENE_LOOK` beside it holds each scene's ground, title shadow and the colours of the chips and the game's box drawn over it.

## Snapshots

A player has one save per series (`save` in `api/_lib/schema.ts`, unique per series and player), and a save holds snapshots (`snapshot`), at most one per milestone, each the export of one `Partida N.rxdata` slot of a save zip: the zip's key, name and size in the bucket, the slot's entry in the zip, the export as `data` (jsonb, the [Snapshot Format](../reference/snapshot.md)), the slot's TM rolls (`tm_rolls`) and the key of its rolled zip (`rolled_key`), its Pokémon and fainted counts, who uploaded it (null when no one did, as for the seed) and when it was taken. Every way a save comes in goes through one pipeline, `ingest` in `api/_lib/ingest.ts`: given a zip already in the bucket, a slot and a milestone, it reads the zip back, exports the slot, puts the rolled zip in the bucket, and writes the snapshot, replacing the one at that milestone and deleting the replaced zip and rolled zip once no snapshot holds them; the manual upload below and `npm run seed` are its two sources so far, and nothing in it knows which one called it.

The export (`api/_lib/export/`, [Save Export](save-export.md)) is the retired Python export ported to TypeScript, with moves always exported: `marshal.ts` the save's Ruby Marshal reader and the side file's writer, `export.ts` the Pokémon, items, TMs and moves as the Python wrote them, TM compatibility rolled for what the slot's rolls lack (below), plus what the Python left out (the fallen, the party, all eight pockets, the trainer, play time, the Pokédex, the battle counts, the Hall of Fame, the used first encounters), `zip.ts` a zip reader and writer, and `save-zip.ts` the slots a zip holds (`Partida N.rxdata` in any folder, ordered by folder then number, with each one's saved time from the zip and its badges and Hall of Fame) and the export of one with its rolled zip. `generate_export_data.py` writes `data.json` beside them ([Save Export → Data Shipped With the Export](save-export.md#data-shipped-with-the-export)). On MIRAMEEE's save (a 15 MB `Partida 1.rxdata`, 2.1 MB zipped) the slots are listed in about 0.2 s and the export takes about 0.2 s.

**TM rolls.** A roll counts only once the game loads it and the player saves ([Save Export → Rolling TMs](save-export.md#rolling-tms)), so the site keeps what it rolled. The export starts from the slot's existing rolls, rolls each bag TM still missing for a Pokémon it exports, and `ingest` stores the result in the snapshot's `tm_rolls`, as `[species, [[move, compatible], …]]` pairs in the side file's order (jsonb would reorder an object's keys). Where the existing rolls come from depends on the zip: a zip the site already exported for that slot, the same key in the bucket, starts from the rolls a snapshot of it keeps, so exporting it again rolls nothing and its TM moves stay as they were; any other zip, a new upload, starts from its own `tm_compatibility_<slot>.dat`, else the save's copy, as the game loads them. The site never compares one zip's rolls with another's. The rolled zip is the player's zip entry for entry, as stored with each entry's name, DOS time and external attributes (extra fields dropped), the slot's side file replaced, or added beside the save when the zip has none, holding every roll in the Marshal bytes Ruby writes (the writer rewrites MIRAMEEE's 44,179-byte side file byte for byte). It goes in the bucket beside the zip, at `saves/<series id>/<player id>/<uuid>-rolled.zip`, and downloads under the uploaded zip's name through `GET /api/series/<n>/trainers/<player>/snapshots/<milestone>/zip`, which answers a link (`downloadUrl`) to the player and to admins and 403 to anyone else. The player extracts it into the save folder with the game closed, loads and saves, and their next upload holds the rolls: on MIRAMEEE's zip the export rolls 3,047 pairs, and the rolled zip exported again rolls none and gives the same TM moves.

**Uploading.** On the series page the Snapshots tile's Upload button opens the upload dialog (`UploadDialog`, `src/components/upload-dialog.tsx`, after the `upload-*.dc.html` boards): on a player's own row in a running manual series, on every row for an admin in any series that is not a draft, and nowhere else (`mayUpload` in `api/_lib/series-data.ts`, which the routes check too). The dialog takes a zip, by drop or file pick, and uploads it at once, through the same multipart calls as a game's zip ([Games](#games)) under `/api/series/<n>/trainers/<player>/`: `upload`, `upload/part`, `DELETE upload` and `file`, the zip at `saves/<series id>/<player id>/<uuid>.zip`, at most 100 MB. While it goes up the milestone can be picked. `file` completes the upload, reads the zip back and answers its slots, each with the milestone it suggests (`suggestMilestone` in `shared/save-upload.ts`: a save in the Hall of Fame suggests the first milestone with "League" in its name, else N badges suggest "Gym N"), or refuses a zip with no slot ("No Partida save in this zip") and deletes it. The dialog then shows the slots to pick from when there are several, the first picked, preselects the picked slot's suggestion unless a milestone was already chosen by hand, marks it "From the save · 8 badges" or "From the save · Hall of Fame", marks the milestones that have a snapshot, and warns in amber when the pick replaces one ("Replaces Post-League · 79 Pokémon"). Save (or "Replace <milestone>") calls `POST /api/series/<n>/trainers/<player>/snapshots`, which runs `ingest` and answers the milestone, the counts and whether it replaced one; an export that fails shows its reason in the dialog, which stays open on the pick. The done step shows "<milestone> saved" or "replaced", the Pokémon count, and a row with how many TM pairs the export rolled, the side file's name and "Download zip", and "Open PC", which opens the player's PC at that snapshot, and the page reloads the series. On the series page each snapshot chip of a player's own row, or of every row for an admin, carries a download button for its rolled zip. Below `sm` the dialog is a bottom sheet. An admin's dialog is titled "Upload for <player>" with their badge. Starting an upload aborts the player's open multipart uploads and deletes their zips more than an hour old that no snapshot holds, as its zip or its rolled zip.

**The PC.** `/players/<player>/series/<n>/pc?snapshot=<milestone>` (`src/pages/pc.tsx`, after `pc.dc.html`), with `<player>` the player's user id, shows one player's PC at one snapshot of a series, read-only, to every signed-in reader. Above it, a breadcrumb link reading "◀ <player> · Series <n>", opening the player's series page, the player's badge and "<player>'s PC", "You" on the reader's own, and a Snapshot picker over the series' milestones, those without a snapshot disabled, picking one changing `?snapshot=`; without it the page shows the latest snapshot, and "No snapshot yet" when there is none. Below, the PC box with its search, type filter and Bag button, the summary beside it from `lg` or in a bottom sheet below, and the bag dialog with nothing to give: `SnapshotPc` in `src/components/pc/pc-box.tsx`, over the pieces Open Sheet's own PC is built from too ([Design System → Shared](../reference/design-system.md#shared), [Open Sheet → The PC](open-sheet.md#the-pc)). The page reads `GET /api/series/<n>/trainers/<player>/pc?snapshot=<milestone>` (`api/_lib/series.ts`), which answers the player, the series, its milestones with whether each has a snapshot, the milestone shown and the snapshot's export, parsed in the browser by the export's schema (`pcPage` in `shared/pc.ts`, over `snapshotSchema`); it answers 404 for a series a reader may not see, a player not in the series, or a milestone without a snapshot. The header's PC tab opens the signed-in player's own PC in the running series, or `/series` while none runs, and is open on every PC page.

**The player's series page.** `/players/<player>/series/<n>` (`src/pages/player-series.tsx`, after `player-series.dc.html` and `player-series-phone.dc.html`), with `<player>` the user id, shows one player's way through one series to every signed-in reader, as two sections. Above them, a breadcrumb of the player's name, plain until the profile exists, and "Series <n>", a link to the series page; the badge and "<player> in Series <n>", "You" on the reader's own; and the button to the player's PC naming its target, "<milestone> · latest", which opens the latest snapshot (full width under the title on a phone). **Journey** (`#journey`) is a table with a column per milestone of the series and a row per record: play time, badges ("8 / 8"), money, the Pokédex (owned, with seen under it), trainer battles (won – lost), blackouts, and the fainted count in red with how many fell since the previous snapshot ("+1"); a milestone with a snapshot heads its column with a link to the PC at that snapshot, one without reads "—" all down. On a phone the table scrolls sideways under its label column, which stays stuck to the left. **Fallen** (`#fallen`) counts the permafainted and shows each one's sprite, greyed, its nickname, species and level, and the span in which it fell: matched by `personalId` across the player's snapshots in milestone order, a Pokémon first permafainted in a snapshot fell between the snapshot before it and that one ("Gym 8 → Post-League"), and one already fainted in the player's first snapshot, or one without a `personalId`, reads "by <milestone>" (`fallenAcross` in `shared/journey.ts`); cards run in a grid on wide screens and one per row on a phone. A link with `#journey` or `#fallen` scrolls to that section once the page has loaded. The page reads `GET /api/series/<n>/trainers/<player>/journey` (`api/_lib/series.ts`, `journeyPage` in `shared/journey.ts`), which answers the player, the series, each milestone's records or null, the latest milestone and the fallen, reading only those keys of each snapshot's export out of Postgres; it answers 404 for a series a reader may not see or a player not in the series. The page shows no PC or party.

## Data and Storage

Accounts and their sessions live in Postgres: Neon (Vercel Marketplace, free tier, resource `pkmn-site`, region `aws-eu-central-1`, Frankfurt) in production, with a `dev` branch for previews, and locally the Postgres of `compose.yaml`, which also runs MinIO as the local stand-in for the file store, with a `pkmn-site` bucket. Files (game zips under `games/`, save zips under `saves/`) live in private Backblaze B2 buckets, `pkmn-site-enbraile` for production and `pkmn-site-preview-enbraile` for previews, reached through their S3-compatible API with the AWS S3 SDK (`api/_lib/files.ts`), the same code that talks to MinIO locally. The schema holds Better Auth's `user` (with the site's `admin` and `allowed` flags), `session`, `account` and `verification` tables, the `game` table, the `series`, `series_player` and `milestone` tables, and the `save` and `snapshot` tables, and changes only by forward migrations generated into `drizzle/` (`npm run db:generate`) and applied with `npm run db:migrate`; there are no down migrations, and data is restored with Neon's point-in-time restore. Secrets (`DATABASE_URL`, `BETTER_AUTH_SECRET`, the Discord application's `DISCORD_CLIENT_SECRET`, the buckets' `S3_*` keys) live in Vercel's environment and in an untracked `.env.local`, never in the repository; `.env.example` names every variable.

Open Sheet's tabs and teams still stay in the reader's browser, in IndexedDB, and Team Analysis's drafts in `localStorage`, per browser and device, until the team builder moves them into accounts. Game data (names, descriptions, base stats, the type chart) is bundled from `@pkmn/dex` rather than fetched. Sprites load from Showdown's sprite server, `play.pokemonshowdown.com`, through `@pkmn/img`'s URLs.

## Hosting and Deploys

Vercel serves the site from the owner's Hobby account: the Vite build's static `dist/` and the API as a Vercel Function (`api/index.ts`) in the same project. `pkmn/site/vercel.json` runs the function in Frankfurt (`fra1`), beside the Neon database (`aws-eu-central-1`), sends `/api/` paths to the function and rewrites every other path to `/index.html` so deep links load the single-page app. `pkmn.enbraile.vip` is a DNS-only (grey-cloud) `CNAME` to the Vercel target in the `enbraile.vip` zone, which stays on the owner's Cloudflare account. If the record were proxied, traffic would go through Cloudflare's IPs again, which Spanish ISPs block during LaLiga matches.

Vercel's Git integration, connected to the GitHub repository in the Vercel dashboard with root directory `pkmn/site`, builds and deploys each push to `main` that touches `pkmn/site/`. Pushes that touch nothing there are skipped, and each branch push gets a public preview URL (Vercel Authentication is off for previews). A preview or `vercel.app` URL is a different origin from `pkmn.enbraile.vip`, so its IndexedDB and `localStorage` start empty. The project's environment variables are set per Vercel environment: `DATABASE_URL` (the Neon production branch for Production, the `dev` branch for Preview), `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL` (`https://pkmn.enbraile.vip` for Production), and the B2 file store's `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY`, whose bucket and key differ for Preview, so a preview never reaches the production files, and, for Production only, the Discord application's `DISCORD_CLIENT_ID` and `DISCORD_CLIENT_SECRET`. Previews leave `BETTER_AUTH_URL` unset, so Better Auth takes each request's own URL as its base. There are no secrets in the repository. A schema change is migrated by hand (`npm run db:migrate` against the branch) before the code needing it is deployed. A bad deploy is undone with Vercel's Instant Rollback to the previous production deployment, or by reverting the commit, which redeploys.

The site writes no logs of its own: Vercel's build and deployment logs cover the deploy, the API's uncaught errors land in Vercel's function logs, there is no Web Analytics, and import and upload errors are shown to the reader.
