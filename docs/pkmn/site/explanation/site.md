# The pkmn Site

The group's Pokémon web app, `pkmn/site/`, served at `pkmn.enbraile.vip`. Players sign in with Discord and see it once an admin has allowed them: they land on the running series' page, `/series/<n>`, with every series listed at `/series` ([Series](#series)), upload their save zip there as a snapshot, follow any player's journey and fallen through the series at `/players/<player>/series/<n>` and their career across every series on their profile at `/players/<player>`, and open any player's PC at any snapshot at `/players/<player>/series/<n>/pc` ([Snapshots](#snapshots)); [Team Analysis](team-analysis.md) at `/team-analysis` stays behind the Teams tab, and [Open Sheet](open-sheet.md) at `/open-sheet` is reached only by its address, until the team pages replacing them are built. Its API runs on Vercel Functions, admins sign in at `/admin`, keep the allowlist at `/admin/players`, keep the games and their files at `/admin/games`, and make and run the series at `/admin/series`. Running and deploying it is in [How to Run and Deploy the Site](../how-to/run-and-deploy-the-site.md). It was scoped with the owner on 2026-10-15.

## Stack

npm; Vite 8, React 19, TypeScript 7, Tailwind 4 and shadcn/ui; TanStack Router; zod 4; Dexie over IndexedDB; `@pkmn/dex` and `@pkmn/img` for Showdown's data and sprites; `react-markdown` and `remark-gfm` for a series' rules. Every package is pinned exactly, at its latest stable version when it went in (the scaffold, 2026-10-16: vite 8.3.4, react 19.3.1, typescript 7.0.2, tailwindcss 4.3.3, shadcn 4.21.5, @tanstack/react-router 1.170.44, @pkmn/dex 0.10.11, @pkmn/img 0.3.4). The gate is `npm run gate`: `tsc -b`.

Routes are declared in code in `src/router.tsx`, not with TanStack Router's file-based plugin: a handful of routes needs no generated route tree for `tsc` to check before a build. A page gets its route there; the home, `/`, has no page of its own and sends a signed-in reader on to the running series ([Series](#series)).

The server side is TypeScript too: a Hono app (`api/_lib/app.ts`) under `/api`, Better Auth for sign-in (`api/_lib/auth.ts`), and Postgres through Drizzle over `pg` (`api/_lib/db.ts`, schema in `api/_lib/schema.ts`), with `drizzle-kit` writing the migrations into `drizzle/` (scaffolded 2026-10-22: hono 4.13.13, better-auth 1.7.12, drizzle-orm 0.45.4, drizzle-kit 0.31.11, pg 8.23.1, @hono/node-server 2.1.5, tsx 4.23.15; @aws-sdk/client-s3 and @aws-sdk/s3-request-presigner 3.1156.0 on 2026-10-22). `api/index.ts` is the only Vercel Function: Vercel makes a function of every file in `api/` except those under a `_` folder, so the app lives in `api/_lib/`, and `vercel.json` sends every `/api/` path to it. Locally, `scripts/dev-api.ts` serves the same app on Node at `API_PORT` (8787), started and stopped by a small Vite plugin in `vite.config.ts` so that one `npm run dev` runs both, and Vite proxies `/api` to it. The browser talks to it through Better Auth's client (`src/lib/auth-client.ts`) and, for the site's own routes, `src/lib/api.ts`, which parses each answer with a zod schema from `shared/`, the folder both the browser and the API compile, so the two agree on every request and answer. `tsconfig.api.json` puts `api/`, `scripts/` and `shared/` under the gate, and their relative imports end in `.js` so that both `tsx` and Vercel's compiled output resolve them. The save export is the site's own TypeScript (`api/_lib/export/`), with no package of its own: a port of the retired Python export's Ruby Marshal reader and export ([Save Export](save-export.md)), a zip reader over `node:zlib`, and the export's game data as `data.json`, imported with `with { type: "json" }` (`resolveJsonModule` in `tsconfig.api.json`).

## Accounts

A player signs in with Discord, through Better Auth's Discord provider, registered only when `DISCORD_CLIENT_ID` and `DISCORD_CLIENT_SECRET` are set. Their first sign-in makes a `user` row named after their Discord display name, with a `discord` account, and `allowed` false, unless an admin invited them: an invite, made at `/admin/players` from a Discord user ID and a name (`POST /api/players`), is a `user` row, allowed, with the placeholder email `<discord id>@discord.invalid`, and a `discord` account whose `account_id` is that ID and which holds no token. Better Auth signs a Discord sign-in into the user that owns the account with its ID, so the invited player's first sign-in lands in that row, already allowed and already in any series an admin put them in. Every Discord sign-in sets the user's name, avatar and email from Discord (`overrideUserInfoOnSignIn`), so an invite's name and placeholder email last only until then. `SiteShell` (`src/components/site-shell.tsx`), the root route's component, guards every page but `/admin` and its pages: signed out, it shows the sign-in page (`src/pages/sign-in.tsx`); signed in but not allowed, the waiting page (`src/pages/waiting.tsx`), with the player's badge and name and its own sign-out; otherwise the header and the page. Neither page has the header. Every API route but `/api/auth/*` answers only a session that is allowed or an admin's (`api/_lib/access.ts`): 401 without a session, 403 "Waiting for an admin" for a player not allowed. The flag is read on every request, so allowing or removing a player takes effect on their next reload. An admin keeps the allowlist at `/admin/players` (`src/pages/admin-players.tsx`), which lists every player who has signed in or been invited, waiting first, an invite whose account holds no token yet marked "Invited", and allows or removes each one through `GET /api/players` and `POST /api/players/<id>/allowed`; any player is deleted with `DELETE /api/players/<id>`, an unused invite at one press and anyone else at a second ("Confirm delete"), which deletes their user row and with it their sessions, accounts, series places, saves and snapshots, then every object under their `saves/<series id>/<player id>/` in each series they were in, open uploads included; a delete refused because a hand-set change on another player's snapshot names them answers 409. Deleted, a Discord user who signs in again starts over as someone new, waiting (`api/_lib/players.ts`, schemas in `shared/players.ts`), both for admins only. Admins never touch Discord: account linking is off, so a Discord sign-in can never join an existing account, and a database hook refuses any account other than a password for an admin's user.

An admin is a separate username-and-password account, not a player: a `user` row with `admin` set and a `credential` account holding the password hash. `npm run admin:create <name>` (`scripts/admin-create.ts`) is the only way to make one outside the local stack, whose seed makes its own: it asks for the password twice without echoing it, never takes it as an argument, and writes both rows in one transaction, with the username lower-cased and a placeholder `<name>@admin.invalid` email, since Better Auth requires an email. Better Auth's sign-up is off (`disableSignUp`), so no route makes an account, and `admin` cannot be set through its API (`input: false`). Locally, `DEV_SIGN_IN=1` adds a test sign-in (`api/_lib/dev-sign-in.ts`), a Better Auth plugin whose `GET /api/auth/dev/sign-in?username=<name>` starts a session for a player who is not an admin and redirects home; unset, the plugin is not registered and the route does not exist. `npm run seed` (`scripts/seed.ts`) makes the local admin, the test players (Red and Blue allowed, Leaf waiting), a game with a stand-in zip, series 1 running on it and, since the profile, a finished series 2 ([How to Run and Deploy the Site](../how-to/run-and-deploy-the-site.md) has the details), and only against a database and a file store on `localhost` or `127.0.0.1`. `/admin` (`src/pages/admin.tsx`) shows a sign-in form, and an admin's session gets the admin home with sign-out. The admin home lists the admin pages as links, and the header's sign-out signs an admin out. The admin pages have no design of their own; they are built from the look's shared pieces (`Panel`, `fieldClass`, the quiet button, the lifting card). Every `/api/games` route answers only an admin's session (`api/_lib/admin.ts`): 401 without one, 403 for a player.

Their trainer numbers and names are sample data, and their Google Fonts link stands for the bundled fonts.

The look is a Gen 4–5 game screen, kept readable:

- **One dark theme,** a deep navy ground with a faint dot grid, navy panels with 3px slate borders and rounded corners. No light theme.
- **Two typefaces:** Jersey 10, a pixel face, for headings, labels, tabs, buttons and numbers; Nunito for running text.
- **Pixel art drawn in code** as crisp-edged SVG: the Poké Ball home mark, the icons (flag, monitor, people, download arrow, cartridge) and the series scenes.
- **A scene per series.** Each series has a background scene from a fixed set (so far a night sky and a daytime route), picked by the admin in the series form. Every scene moves a little in stepped, game-like animation: the night sky's stars, sparkles and lit windows blink; the route's clouds drift and its flowers blink. Under `prefers-reduced-motion` they stand still.
- **Sign-in and waiting are a Poké Ball:** the top half red with the site's name, a black band with a large Poké Ball on the seam, and the dark half below holding the Discord button or, for a player not yet allowed, their badge, the waiting message and sign-out. No header, no Pokémon, no animation. Discord's blurple is the one colour outside the look, on the Discord button alone.
- **The header:** the Poké Ball links home; tabs Series · PC · Teams (· Admin for admins) sit on the header's red bottom line, the open one filled red and joined to it; at the right, your badge and name, opening your profile, then sign-out. On a phone the bar shrinks to the Poké Ball, the open section's name and a three-line menu button whose dropdown lists the tabs, your profile and sign-out.
- **Players are boxed, never round:** a rounded-square badge with the player's initial, a dark border and a ring in the player's own colour.
- **Quiet controls:** buttons are translucent, in the pixel face, with a dark bottom edge; whatever is clickable as a whole (a series banner, a trainer's PC or Teams tile) lifts and takes a cyan border on hover. Red marks where you are, cyan what you can act on, yellow you and winners, amber a soft warning that never blocks (an old export's missing fields, a snapshot about to be replaced).
- No helper text explaining the UI. The UI is in English, since Showdown's names are. Desktop-first, with every view usable on a phone.

The site's design system is kept in the repository: the code (`src/index.css`'s tokens, the shell, the shared components) is its source of truth, and the [Site Design System](../reference/design-system.md) describes it, changing in the same commit as the code does. A new page follows [How to Add a Page to the Site](../how-to/add-a-page-to-the-site.md).

shadcn was initialised with its Nova preset on Radix, its palette replaced by the design's colours as the only theme, and its vendored components in `src/components/ui/` follow the same token rule. The design's fonts are bundled from Fontsource rather than loaded from Google Fonts, and the type icons come from duiker101's [Pokémon Type SVG Icons](https://github.com/duiker101/pokemon-type-svg-icons), free for any use, bundled in `src/lib/type-icons.ts`, so the only outside calls the site makes at runtime are for Showdown's sprites; everything else it fetches is its own `/api`.

The tab icon is a spiral notepad with a red and white Poké Ball drawn on it and a pencil writing on it: `public/favicon.svg`, plus `favicon-32.png` and `apple-touch-icon.png` rendered from it for browsers that take no SVG icon.

## Games

A game is a name and one zip of its files (`game` in `api/_lib/schema.ts`, with the file's key, name, size and upload time). At `/admin/games` (`src/pages/admin-games.tsx`) an admin creates a game by name, which must be unique, and uploads its zip; the page lists every game with its file's name, size and upload date, and downloads it. The file never passes through the API, since a Vercel Function's body is capped at a few MB and a game is about 600 MB:

1. `POST /api/games/<id>/upload` with the file's name and size aborts any multipart upload the game left open, starts a multipart upload for a new key, `games/<id>/<uuid>.zip`, and answers the key, the upload's id and the part size (`partSizeFor` in `shared/upload.ts`).
2. The browser splits the file into parts of that size and sends four at a time (`uploadParts` in `shared/upload.ts`, driven by `sendFile` in `src/lib/upload.ts`, which the save upload shares). For each part it asks `POST /api/games/<id>/upload/part` for a presigned `PUT` of that part, valid for an hour and signed for its exact size, and `PUT`s the part straight to the bucket, keeping the `ETag` the bucket answers (exposed by its CORS rule). One percentage shows the bytes sent across all parts.
3. A part that fails, or goes 30 seconds without sending a byte or getting its answer, is retried on its own with a freshly signed URL, up to six tries in all, after 1, 2, 4, 8 and 16 seconds. When a part runs out of tries, the other parts are cancelled and `DELETE /api/games/<id>/upload` aborts the multipart upload, tried three times; the page shows why the upload failed, and says so if the abort could not reach the bucket either, in which case the game's next upload aborts it in step 1. Aborting an upload the bucket no longer knows, because step 4 completed or aborted it, counts as done.
4. `POST /api/games/<id>/file` with the key, the upload's id and every part's number and `ETag` checks that the key belongs to the game and completes the multipart upload, aborting it if the bucket refuses. It then reads the object's real size from the bucket, records it and deletes the game's previous object.

Until step 4 completes, the bucket holds no object for the upload, only its parts, so a half-finished replacement leaves the old file in place and leaves no stray file behind. `npm run seed` puts its stand-in zip in the bucket through the same multipart calls and `uploadParts`, signing the parts in the script rather than through the API. The API's calls to the bucket give up after 5 seconds without a connection or 20 seconds without an answer, tried twice, so a bucket that cannot be reached fails a request rather than hanging it. A download is `GET /api/games/<id>/download`, a presigned `GET` valid for five minutes that saves under the uploaded file's name. Every games route is admin-only; a series' players download its game through the series page ([Series](#series)). The bucket is private: nothing in it has a public URL.

## Series

A series (`series` in `api/_lib/schema.ts`) has a unique number, a name, its game, its background scene (`night` or `route`), its ingestion mode (`manual`, players upload their saves, or `automatic`, the game sends them), its rules as Markdown, and a state: `draft`, `running` or `finished`. Its players are rows of `series_player`, and its milestones rows of `milestone`, in order (`position`), each named and marked `none`, `round` (a league round is played at it) or `tournament`. A partial unique index on `state` lets one series run at a time. The shapes the browser and the API share, and `startChecklist`, are in `shared/series.ts`.

**Admins** keep the series at `/admin/series` (`src/pages/admin-series-list.tsx`), which lists every series, newest first, and creates a draft from a number and a name, then opens its form at `/admin/series/<id>` (`src/pages/admin-series.tsx`): number, name, game (from `/admin/games`, marked when it has no file), ingestion, the scene with a preview of it under the series' name, the players (checkboxes over the allowlist), the milestones (named, marked, reordered, removed, added) and the rules, a Markdown text area that "Copy from" fills with another series' rules. The checklist under it shows what starting still needs: rules written, a game with its file, at least one milestone, and, while another series runs, that series finished. It is worked out from the form as it is being filled, by the same `startChecklist` the API runs, and Start, which saves the form first, enables once every item is done. Save keeps a draft without starting it, and a draft can be deleted. Once a series runs only its rules, its players and its milestones change, through Save (`PUT /api/admin/series/<id>/rules`, then `/players`, then `/milestones`), which adds any allowed player and refuses to drop one with a snapshot in it, and edits the milestones in place, by id, so a snapshot stays on its milestone through a rename, a new mark or a new order: a milestone is added, renamed, re-marked and moved freely, and removed only when no snapshot is at it ("Move or delete the snapshots at <milestone> first"); a finished series changes only its rules, through Save rules, and Finish, confirmed by a second press, ends it; a finished series stays finished. The routes are `GET` and `POST /api/admin/series`, `GET`, `PUT` and `DELETE /api/admin/series/<id>`, `PUT /api/admin/series/<id>/rules`, and `POST /api/admin/series/<id>/start` and `/finish` (`api/_lib/admin-series.ts`), every one admin-only; start refuses a draft whose checklist is not done, and the index refuses a second running series even if two starts race.

**Players** reach the running series from `/`, which sends a signed-in reader to its page, or to `/series` while none runs (`src/pages/home.tsx`). `/series` (`src/pages/series-list.tsx`, after `series-list.dc.html`) shows one banner per series that is running or finished, newest first, on its scene, with its name, its game and "Playing now" or "Finished"; the whole banner is a lifting link. `/series/<n>` (`src/pages/series.tsx`, after `series.dc.html`) is a header drawn on the series' scene with its name and its game in a box, with Download for the series' players and admins; the League as a work-in-progress placeholder; the Trainers, one row per player with their badge and their name (a link to their profile, [Snapshots → The player's profile](#snapshots)), "You" on the reader's own row, and the milestones as a track, the rounds tinted and numbered and the tournament a cup. The track shows the trainer at their progress, the milestone of their latest snapshot unless an admin set it by hand ([Snapshots → Admin overrides](#snapshots)), with no mark either way: the line and the nodes up to it in the player's colour, a reached round's ring red, and the player's badge bobbing on that node (standing still under `prefers-reduced-motion`); each milestone with a snapshot is ringed in faint cyan in its node's shape, brighter on hover, the shown snapshot's ring full cyan, and clicking a ring opens the row on that snapshot. On a phone the track only shows, and the open row picks its snapshot from a segmented control of the trainer's milestones above its tiles, in place of the Snapshots tile. Each row opens into PC, Teams, Fainted, Journey and, from `sm`, Snapshots tiles: under "At <milestone>", the PC tile counts the exported living Pokémon, the Fainted tile the permafainted ones, or the count an admin set by hand (in red above 0) and the Journey tile the play time ("37 h 19") of the shown snapshot, the latest until another is picked, the Snapshots tile lists their snapshots' milestones with the shown one outlined, and an Upload button where the reader may upload for that trainer ([Snapshots](#snapshots)), and under them, in amber, what the shown snapshot lacks when an old export made it ("Export missing: no IVs, EVs or stats · no moves"; below `sm`, under the Upload button); Teams reads "—", as do PC, Fainted and Journey for a trainer without a snapshot; the Fainted and Journey tiles link to the trainer's series page at `#fallen` and `#journey` ([Snapshots → The player's series page](#snapshots)); the PC tile, when there is a snapshot, links to the trainer's PC at the shown snapshot and each snapshot's milestone in the Snapshots tile to their PC at that snapshot ([Snapshots → The PC](#snapshots)), the tile lifting with a `primary` border on hover and the chip turning `primary`; and the rules, rendered from Markdown by `react-markdown` with GitHub tables (`remark-gfm`) and raw HTML skipped, in two columns on wide screens. A draft's page answers 404 to players and opens for admins. The routes are `GET /api/series`, `GET /api/series/<n>` and `GET /api/series/<n>/download` (`api/_lib/series.ts`), the last a five-minute presigned link to the game's zip for the series' players and admins, 403 for anyone else.

The scenes are `SceneArt` (`src/components/scene.tsx`): the boards' night sky and daytime route, drawn in code as crisp SVG rectangles on a pixel grid (360 by 65 for a page's header, 338 wide for a banner; on a phone a smaller crop, 98 by 55 and 88 wide) and scaled to cover their box from the bottom. Their stars, sparkles and windows blink and their clouds drift in stepped CSS animations (`scene-twinkle`, `scene-sparkle`, `scene-glow`, `scene-drift` in `src/index.css`), which stand still under `prefers-reduced-motion`. `SCENE_LOOK` beside it holds each scene's ground, title shadow and the colours of the chips and the game's box drawn over it.

## Snapshots

A player has one save per series (`save` in `api/_lib/schema.ts`, unique per series and player), and a save holds snapshots (`snapshot`), at most one per milestone, each the export of one `Partida N.rxdata` slot of a save zip, or else an old export's JSON read as far as it goes: the file's key, name and size in the bucket, the slot's entry in the zip (null for an export), the export as `data` (jsonb, the [Snapshot Format](../reference/snapshot.md)), an old export's missing-field report (`missing`, null for a zip; [Snapshot Format → Old Exports](../reference/snapshot.md#old-exports)), the slot's TM rolls (`tm_rolls`) and the key of its rolled zip (`rolled_key`), its Pokémon and fainted counts, who uploaded it (null when no one did, as for the seed) and when it was taken, and the admin overrides below. Every way a save comes in goes through one pipeline, `ingest` in `api/_lib/ingest.ts`: given a file already in the bucket, a slot and a milestone, it reads the file back; a zip's slot it exports and puts the rolled zip in the bucket, and an export (a `.json` key, no slot) it reads with `readExport`, with no TM rolls and no rolled zip; then it writes the snapshot, replacing the one at that milestone and deleting the replaced zip and rolled zip once no snapshot holds them; the manual upload below and `npm run seed` are its two sources so far, and nothing in it knows which one called it.

The export (`api/_lib/export/`, [Save Export](save-export.md)) is the retired Python export ported to TypeScript, with moves always exported: `marshal.ts` the save's Ruby Marshal reader and the side file's writer, `export.ts` the Pokémon, items, TMs and moves as the Python wrote them, TM compatibility rolled for what the slot's rolls lack (below), plus what the Python left out (the fallen, the party, all eight pockets, the trainer, play time, the Pokédex, the battle counts, the Hall of Fame, the used first encounters), `zip.ts` a zip reader and writer, and `save-zip.ts` the slots a zip holds (`Partida N.rxdata` in any folder, ordered by folder then number, with each one's saved time from the zip and its badges and Hall of Fame) and the export of one with its rolled zip. `generate_export_data.py` writes `data.json` beside them ([Save Export → Data Shipped With the Export](save-export.md#data-shipped-with-the-export)). On MIRAMEEE's save (a 15 MB `Partida 1.rxdata`, 2.1 MB zipped) the slots are listed in about 0.2 s and the export takes about 0.2 s.

**TM rolls.** A roll counts only once the game loads it and the player saves ([Save Export → Rolling TMs](save-export.md#rolling-tms)), so the site keeps what it rolled. The export starts from the slot's existing rolls, rolls each bag TM still missing for a Pokémon it exports, and `ingest` stores the result in the snapshot's `tm_rolls`, as `[species, [[move, compatible], …]]` pairs in the side file's order (jsonb would reorder an object's keys). Where the existing rolls come from depends on the zip: a zip the site already exported for that slot, the same key in the bucket, starts from the rolls a snapshot of it keeps, so exporting it again rolls nothing and its TM moves stay as they were; any other zip, a new upload, starts from its own `tm_compatibility_<slot>.dat`, else the save's copy, as the game loads them. The site never compares one zip's rolls with another's. The rolled zip is the player's zip entry for entry, as stored with each entry's name, DOS time and external attributes (extra fields dropped), the slot's side file replaced, or added beside the save when the zip has none, holding every roll in the Marshal bytes Ruby writes (the writer rewrites MIRAMEEE's 44,179-byte side file byte for byte). It goes in the bucket beside the zip, at `saves/<series id>/<player id>/<uuid>-rolled.zip`, and downloads under the uploaded zip's name through `GET /api/series/<n>/trainers/<player>/snapshots/<milestone>/zip`, which answers a link (`downloadUrl`) to the player and to admins and 403 to anyone else. The player extracts it into the save folder with the game closed, loads and saves, and their next upload holds the rolls: on MIRAMEEE's zip the export rolls 3,047 pairs, and the rolled zip exported again rolls none and gives the same TM moves.

**Uploading.** On the series page the Snapshots tile's Upload button opens the upload dialog (`UploadDialog`, `src/components/upload-dialog.tsx`, after the `upload-*.dc.html` boards): on a player's own row in a running manual series, on every row for an admin in any series that is not a draft, and nowhere else (`mayUpload` in `api/_lib/series-data.ts`, which the routes check too). The dialog takes a zip or an old export's `.json`, by drop or file pick ("Drop a save zip or an export"), and uploads it at once, through the same multipart calls as a game's zip ([Games](#games)) under `/api/series/<n>/trainers/<player>/`: `upload`, `upload/part`, `DELETE upload` and `file`, the zip at `saves/<series id>/<player id>/<uuid>.zip`, at most 100 MB, an export at `<uuid>.json`, at most 10 MB. While it goes up the milestone can be picked. `file` completes the upload, reads the zip back and answers its slots, each with the milestone it suggests (`suggestMilestone` in `shared/save-upload.ts`: a save in the Hall of Fame suggests the first milestone with "League" in its name, else N badges suggest "Gym N"), or refuses a zip with no slot ("No Partida save in this zip") and deletes it; for an export it answers its Pokémon count and missing-field report instead, or refuses one the site cannot read ("This file is not JSON", [Snapshot Format → Old Exports](../reference/snapshot.md#old-exports)) and deletes it. The dialog then shows the slots to pick from when there are several, the first picked, preselects the picked slot's suggestion unless a milestone was already chosen by hand, marks it "From the save · 8 badges" or "From the save · Hall of Fame", marks the milestones that have a snapshot, and warns in amber when the pick replaces one ("Replaces Post-League · 79 Pokémon"). Save (or "Replace <milestone>") calls `POST /api/series/<n>/trainers/<player>/snapshots`, which runs `ingest` and answers the milestone, the counts and whether it replaced one; an export that fails shows its reason in the dialog, which stays open on the pick. The done step shows "<milestone> saved" or "replaced", the Pokémon count, and for a zip a row with how many TM pairs the export rolled, the side file's name and "Download zip", for an export (`upload-done-json.dc.html`) an amber chip naming what it lacks ("Missing: IVs, EVs, stats · moves") and a grey one with how many entries were skipped, and "Open PC", which opens the player's PC at that snapshot, and the page reloads the series. On the series page, from `sm`, each snapshot chip of a player's own row, or of every row for an admin, carries a download button for its rolled zip. Below `sm` the dialog is a bottom sheet. An admin's dialog is titled "Upload for <player>" with their badge. Starting an upload aborts the player's open multipart uploads and deletes their files more than an hour old that no snapshot holds, as its zip or its rolled zip.

**Admin overrides.** An admin can set by hand the values a save gives (a player's progress in a series, a snapshot's fainted count, a snapshot's milestone) and delete any snapshot, in running and finished series; each value set by hand keeps who set it and when, and wins over the save's until an admin clears it. Progress is the save's (`progress_id`, `progress_set_by`, `progress_set_at` on `save`, the row made if the player has no snapshot yet): unset, it is the milestone of the latest snapshot; set, the track, the phone row's milestone and the profile's Reached show it, whatever later uploads bring. The fainted count is the snapshot's (`fainted_set`, `fainted_set_by`, `fainted_set_at`): set, it stands in for the export's count on the row's Fainted tile, in the Journey and in the profile's Fallen, while the Fallen list stays the export's; `ingest` replacing that snapshot keeps it. Moving a snapshot changes its milestone and records `moved_by` and `moved_at`, which a later upload replacing it clears, since its uploader then picked that milestone; a milestone that already holds one of the player's snapshots refuses it (409, "delete it first"). Deleting a snapshot deletes its zip and rolled zip once no other snapshot holds them, as replacing one does, so the seed's Gym 8 copy, which shares its zips with Post-League and Series 2's Tournament, deletes no file while those stand. Check constraints on both tables refuse a value set by hand without who and when. The routes are `PUT` and `DELETE /api/series/<n>/trainers/<player>/progress` (`{ milestone }`), `PUT` and `DELETE …/snapshots/<milestone>/fainted` (`{ count }`, 0 to 999), `POST …/snapshots/<milestone>/move` (`{ milestone }`) and `DELETE …/snapshots/<milestone>` (`api/_lib/overrides.ts`), each behind `requireAdmin`, answering 403 to players. On the series page an admin's open row ends in a dashed amber Admin panel (`TrainerAdmin`, `src/components/trainer-admin.tsx`): Progress, a select of the milestones with "From the save (<milestone>)" first; the shown snapshot's fainted count with Set and, when set by hand, Clear; and the shown snapshot's milestone with a select of the milestones without a snapshot, Move, and Delete, confirmed by a second press. Under Progress and the fainted count, "From the save", or "Set by hand by <admin> · <date> · save: <the save's value>" in amber; under the milestone, "Moved by <admin> · <date>" once it was moved, else nothing. `GET /api/series/<n>` answers each trainer's `progress`, and to admins alone each one's `sources` and each snapshot's, the save's value beside who set what and when (`shared/series.ts`).

## Data and Storage

Accounts and their sessions live in Postgres: Neon (Vercel Marketplace, free tier, resource `pkmn-site`, region `aws-eu-central-1`, Frankfurt) in production, with a `dev` branch for previews, and locally the Postgres of `compose.yaml`, which also runs MinIO as the local stand-in for the file store, with a `pkmn-site` bucket. Files (game zips under `games/`, save zips under `saves/`) live in private Backblaze B2 buckets, `pkmn-site-enbraile` for production and `pkmn-site-preview-enbraile` for previews, reached through their S3-compatible API with the AWS S3 SDK (`api/_lib/files.ts`), the same code that talks to MinIO locally. The schema holds Better Auth's `user` (with the site's `admin` and `allowed` flags), `session`, `account` and `verification` tables, the `game` table, the `series`, `series_player` and `milestone` tables, and the `save` and `snapshot` tables, and changes only by forward migrations generated into `drizzle/` (`npm run db:generate`) and applied with `npm run db:migrate`; there are no down migrations, and data is restored with Neon's point-in-time restore. Secrets (`DATABASE_URL`, `BETTER_AUTH_SECRET`, the Discord application's `DISCORD_CLIENT_SECRET`, the buckets' `S3_*` keys) live in Vercel's environment and in an untracked `.env.local`, never in the repository; `.env.example` names every variable.

Open Sheet's tabs and teams still stay in the reader's browser, in IndexedDB, and Team Analysis's drafts in `localStorage`, per browser and device, until the team builder moves them into accounts. Game data (names, descriptions, base stats, the type chart) is bundled from `@pkmn/dex` rather than fetched. Sprites load from Showdown's sprite server, `play.pokemonshowdown.com`, through `@pkmn/img`'s URLs.

## Hosting and Deploys

Vercel serves the site from the owner's Hobby account: the Vite build's static `dist/` and the API as a Vercel Function (`api/index.ts`) in the same project. `pkmn/site/vercel.json` runs the function in Frankfurt (`fra1`), beside the Neon database (`aws-eu-central-1`), sends `/api/` paths to the function and rewrites every other path to `/index.html` so deep links load the single-page app. `pkmn.enbraile.vip` is a DNS-only (grey-cloud) `CNAME` to the Vercel target in the `enbraile.vip` zone, which stays on the owner's Cloudflare account. If the record were proxied, traffic would go through Cloudflare's IPs again, which Spanish ISPs block during LaLiga matches.

Vercel's Git integration, connected to the GitHub repository in the Vercel dashboard with root directory `pkmn/site`, builds and deploys each push to `main` that touches `pkmn/site/`. Pushes that touch nothing there are skipped, and each branch push gets a public preview URL (Vercel Authentication is off for previews). A preview or `vercel.app` URL is a different origin from `pkmn.enbraile.vip`, so its IndexedDB and `localStorage` start empty. The project's environment variables are set per Vercel environment: `DATABASE_URL` (the Neon production branch for Production, the `dev` branch for Preview), `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL` (`https://pkmn.enbraile.vip` for Production), and the B2 file store's `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY`, whose bucket and key differ for Preview, so a preview never reaches the production files, and, for Production only, the Discord application's `DISCORD_CLIENT_ID` and `DISCORD_CLIENT_SECRET`. Previews leave `BETTER_AUTH_URL` unset, so Better Auth takes each request's own URL as its base. There are no secrets in the repository. Each deploy's build migrates its own environment's branch (`npm run db:migrate` after `npm run build`, `buildCommand` in `vercel.json`) before that deploy goes live. A bad deploy is undone with Vercel's Instant Rollback to the previous production deployment, or by reverting the commit, which redeploys.

The site writes no logs of its own: Vercel's build and deployment logs cover the deploy, the API's uncaught errors land in Vercel's function logs, there is no Web Analytics, and import and upload errors are shown to the reader.

## Decisions

- **A running series' milestones are edited in place:** renamed, re-marked, reordered and added, and removed only when no snapshot is at one. **Why:** the owner wants to change a started series' milestones and their order; saving a draft replaces every milestone, which on a running series would delete their snapshots with them (`snapshot.milestone_id` cascades), so a running series' save keeps each milestone's id. Reordering moves a player's progress with it, since progress is their latest milestone with a snapshot. _(owner, 2026-10-24; replaces a running series changing only its rules and players)_
- **The admin pages have no Admin button beside their title;** the header's Admin tab leads back to the admin home. _(owner, 2026-10-24)_
- **Deleting a player deletes everything they have,** their snapshots in every series and their save zips in the bucket included, after a second press; Remove only takes them off the allowlist. **Why:** the owner chose it over refusing to delete a player who has played, accepting that finished series lose that player's history. _(owner, 2026-10-24)_
- **The waiting page says only "Waiting for an admin",** without the line under it that `waiting.dc.html` and `waiting-phone.dc.html` draw ("An admin has to let you in before you can see the series."); the frozen boards keep it. _(owner, 2026-10-24)_
- **An admin invites a player by their Discord user ID, and a series starts with any number of players, taking more while it runs.** An invite is a real player, allowed, with their Discord account made ahead of their first sign-in; a running series' players change, but one with a snapshot in it stays. **Why:** the owner wants everything ready for a player before they sign in, and to start a series before every player has joined.
